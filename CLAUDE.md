## Project

MDEdit is a WPF desktop Markdown editor (.NET, `net10.0-windows`) built around the AvalonEdit text editor control. See `Requirements.md` for the full product spec.

**Line-based commands operate on every line a selection touches** — `ToggleLinePrefix` (bullet/numbered/blockquote), `TaskListItem`, and `Heading` in `MarkdownFormatter`. Five things there are easy to break:
- They iterate **line numbers, not offsets or `DocumentLine` references**, re-fetching each line in the loop. Safe only because none of these commands add or remove line breaks, so numbers stay valid across every edit; offsets don't. The loop runs **bottom-up** so an edit never shifts a line still to be visited.
- **Numbered lists have their own method, `NumberedList` — they cannot use `ToggleLinePrefix`**, which applies one fixed string to every line and so produced `1.` on all of them. `NumberedList` collects the target line numbers first and takes each marker from the target's *index*, making counting independent of the bottom-up iteration; an already-numbered line is renumbered in place rather than given a second marker. `MainWindow.BtnNumberList_Click` calls it directly — don't route it back through `InsertLinePrefix`.
- Multi-line selections **normalize rather than flip**: the prefix is removed only when *every* affected line has it, otherwise added to those lacking it, so a mixed block becomes uniform and a second press clears it. `TaskListItem` follows the same rule, cycling plain → all unchecked → all checked. Per-line flipping would leave a mixed block permanently mixed.
- Blank lines inside a multi-line selection are skipped, but the **single-line paths deliberately don't skip them** — inserting `- ` on an empty line is how a list gets started.
- Each multi-line command wraps its edits in `doc.RunUpdate()` for **one undo action**; without it a three-line change takes three Ctrl+Z presses. `SelectedLineNumbers` also excludes a line the selection merely ends *at* the start of, matching what the user sees highlighted.

Three categories, not two.

Requirements.md §10's first-run behavior is implemented: `MainWindow`'s constructor calls `MaybeShowReleaseNotesOnFirstRun()` whenever there's no startup file to open instead (that always wins — `StartupFile.Resolve(...)` non-null → `OpenFile`, else `MaybeShowReleaseNotesOnFirstRun()`). It shows the page once per **release**, comparing only `Major.Minor.Build` against `AppSettings.LastReleaseNotesVersionShown` via `Editing/ReleaseNotesGate.cs` (`GetReleaseVersion`/`ShouldShow`, unit-tested in `ReleaseNotesGateTests`) — never the full 4-part version or `Revision` alone, since `Revision` can repeat across different actual releases and would make the comparison unreliable in either direction. The "last shown" value is persisted *before* attempting to open the file, so a missing or unreadable `ReleaseNotes.md` fails silently once per release rather than retrying every launch forever. Help → Release Notes (`MenuOpenReleaseNotes_Click`) reaches it on demand, behaving exactly like File → Open (`CheckUnsavedChanges` guard, joins Recent Files, shows errors) — unlike the auto-open path, which passes `OpenFile`'s `addToRecentFiles`/`showErrorOnFailure` as `false`, since an automatic startup open is not user-initiated and must neither clutter the MRU list nor pop an error dialog on first launch.

**Save-As-instead-of-overwrite protection was rejected in favour of marking the installed file read-only via the OS attribute** (`MainWindow.EnsureReleaseNotesAreReadOnly`, called at both open sites, idempotent) — not via the ClickOnce pipeline: whether attributes survive ClickOnce's deploy mechanism (which renames payload files to `*.deploy` and reconstructs them client-side) is unverified and not worth depending on, whereas applying it at open time is cheap, self-heals after every update (each version lands in a fresh folder with default attributes), and needed zero publish-script changes. It composes for free: `FileService.Save`'s `File.WriteAllText` already throws `UnauthorizedAccessException` on a read-only file, so `ExecuteSave` needed one new `catch (UnauthorizedAccessException)` ahead of the generic one, giving a message pointing at Save As instead of the raw OS "Access to the path is denied".

- **`MDEdit.Tests/TestData/markdown-conformance-test.md`** — a standards-based CommonMark + extensions document written to the spec rather than to this implementation, so it deliberately contains constructs MDEdit does not support; its purpose is finding gaps, whether by a future functional test or by hand. `MDEdit.Tests.csproj` copies `TestData\**\*.md` to the output directory so a test can read it relative to its working directory. **It relies on significant trailing whitespace** (two-space hard breaks in §2 and §21) — don't reformat it, and note that editing it in MDEdit and saving may strip those.
  - **Known CommonMark/GFM conformance gaps, from walking that document against the detection code.** `Requirements.md` §11 scopes most of this as committed work and is the authority on what is in and out; this list is the engineering inventory behind it. §11 excludes the extension-only entries (footnotes, definition lists, heading IDs) and cross-line emphasis, so those stay recorded-but-undecided.
    - **Still absent, and the reason §11 stays *(planned)*:** setext headings; indented (4-space) code blocks; autolinks (`<https://url>`, `<email@x>`) and bare-URL auto-linking; the shortcut (`[text]`) and collapsed (`[text][]`) reference-link forms; and ATX closing sequences — `TryGetHeadingLevel` reads only the leading `#` run, so `### Heading ###` keeps its trailing hashes as literal text.
    - **Partially detected:** reference links — the `[text][ref]` usage form *is* marker-hidden (`LinkPatterns` in `MarkdownSyntax.cs`), but reference *definitions* (`[ref]: url "title"`) are never suppressed, sitting in the document as visible paragraph text instead of vanishing as a real renderer's would.
    - **Recorded but out of §11's scope:** footnotes, definition lists, heading IDs (`{#custom-id}`), HTML entity decoding (`&copy;` always shows as raw text — consistent with WYSIWYG never rewriting content, only marking up recognized syntax, but still a gap against a conforming renderer), and cross-line emphasis (`Markdown.xshd`'s `<Rule>` elements, and `FindEmphasisSpans` which mirrors them, are single-line only; only `<Span>` supports `multiline="true"`, used today for fenced code and HTML comments).
    - **Backslash escaping and the intraword-`_` rule are done** — the two entries that silently misrendered *ordinary text* rather than merely missing syntax, so they were taken first. Escaping spans two mechanisms covering openers and closers: `MarkdownSyntax.EscapeLength` is consumed at the top of **all four** scanner loops (emphasis, link, underline, emoji), so an escaped character is never offered to a pattern as a start position; escaped *closers* need the patterns' own content classes, now `(?:\\.|[^\\<delim>\n])+` — branches deliberately **disjoint**, since overlapping alternatives under a `+` is the catastrophic-backtracking shape this grammar's no-wildcard discipline exists to avoid. Intraword `_` is `(?<!\w)`/`(?!\w)` on the three `_` patterns only; **`*` deliberately gets no such guard**, since CommonMark restricts only `_` and `foo*bar*` *is* emphasis. Three boundaries are drawn on purpose and pinned by tests: **inline code stays escape-blind** (code spans outrank escapes, so a backslash in backticks is literal — hence the escape check runs *after* the code-span skip in `FindEmojiSpans`); **`LinkPatterns` keep plain content classes**, so an escaped `]` inside link text is unsupported, widening them would change what `LinkSpan.Url` carries, which `ImagePathResolver` and three generators read; and the `_` lookbehind is a simplification of the full left/right-flanking algorithm, which also weighs punctuation on each side.
      - **Known divergence, colour-only: `\\*bold*`** — a literal backslash followed by real emphasis. The lexer gets it right (the escape is spent on the backslash, so the `*` opens a run) because it *consumes* escapes as it scans; `Markdown.xshd` gets it wrong, since a `<Span>`'s `Begin`/`End` are separate patterns managing only a `(?<!\\)` lookbehind, which sees the adjacent backslash and refuses. Such a line hides its markers but isn't coloured. Accepted — a real fix needs delimiter-run parsing, which XSHD cannot express.
    - **Not a gap:** H4–H6 always *rendered* correctly (coloured, scaled by their own `EditorPreferences` entries, markers hidden) — `TryGetHeadingLevel` caps at 6 and `StyledElements.Heading(level)` clamps to match. Only the insertion commands stopped at 3; **the Format menu's Heading submenu and Ctrl+1–6 now both reach 6**, and `MarkdownFormatter.Heading` needed no change (`new string('#', level)` and a `^#{1,6}\s*` strip were already general). Ctrl+4/5/6 needed no `ReleaseConflictingEditorGestures` entry — **AvalonEdit declares no digit-key gesture at all**, checked against `AvalonEditCommands` and both command handlers at tag `v6.3.1`, whose only Control gestures are Ctrl+D and Ctrl+I. The binding loop starts at 1 because **Ctrl+0 is Zoom Reset**. **The toolbar still stops at 3** on purpose, 1–3 being much the most used; §3 records that split.

**`THIRD-PARTY-NOTICES.md` is standing maintenance, like the changelog.** MDEdit is **0BSD** (`LICENSE`), which asks nothing, but its two redistributed components are **MIT** and do: AvalonEdit (`ICSharpCode.AvalonEdit.dll`, in every ClickOnce payload) and **Tabler Icons, whose path geometry is *vendored* into `Resources/ToolbarIcons.xaml`** rather than referenced as a package — which is why it's easy to forget it carries terms at all. **Adding a dependency, or vendoring more assets, means adding its notice in the same change.** The obligation attaches to the *installed application*, not the repo, so a notice at the repo root alone wouldn't discharge it: `MDEdit.csproj` ships both beside the exe via `<Content Include="..\THIRD-PARTY-NOTICES.md" Link="THIRD-PARTY-NOTICES.md" />` and `<Content Include="..\LICENSE" Link="LICENSE.txt" />`. The `Link=` is load-bearing — without it the file lands in an `MDEdit\` subfolder mirroring its source path instead of beside the exe, where `AboutWindow` looks. The `.txt` rename keeps the repo root's extensionless `LICENSE` (what GitHub's licence detection expects) while giving the shipped copy an extension Windows can open. Neither is marked read-only the way `ReleaseNotes.md` is — nobody edits a licence, so there is nothing to protect and no reason to create a second stale-attribute problem for `ClearStaleReleaseNotesReadOnly` to undo. The .NET Desktop Runtime is a **prerequisite, not a bundled component** (`SelfContained=false`), so it needs no notice.

WYSIWYG is a **live-preview mode inside AvalonEdit itself**, not a WebView2/rendered-HTML view. The Markdown text is always the single source of truth; the toggle (View → Editor Mode → WYSIWYG) only changes how AvalonEdit *renders* it (larger heading fonts, syntax markers hidden except where the caret is). Chosen over a `contenteditable`/WebView2 approach specifically to avoid a lossy HTML→Markdown round-trip — there is no round-trip, so there's nothing to lose. A WebView2 *read-only* preview pane remains a possible separate addition, not a replacement.

Every construct Requirements.md lists as *implemented* is covered, tables included; what remains from §3 are commands and catalogue features, not rendering. See **Live-preview constructs** at the end of Architecture for the per-construct reveal-scope/replacement map and the checklist for adding another.

### ClickOnce deployment, versioning, and publishing

`docs/` is a live GitHub Pages site (`https://cowwarrior.github.io/MDEdit/`) serving a ClickOnce deployment — which is why the repo is public.

**The full publishing procedure lives in the `publish-clickonce` skill** (`.claude/skills/publish-clickonce/SKILL.md`), loaded on demand rather than every session: the 4-part version-numbering scheme, the `MDEdit/samples/ReleaseNotes.md` changelog entry that must be written and committed *before* publishing, and the script/config gotchas. **Read it before publishing, bumping a version, or editing `build/Publish-ClickOnce.ps1` or the pubxml** — several of those gotchas have cost a bad release once each.

Two facts kept here because they affect ordinary work: the version MDEdit reports is `<Major.Minor.Build from build/published-version.txt>.<git rev-list --count HEAD>`, so a local build's Revision drifts upward with every commit after a publish; and `MDEdit/samples/ReleaseNotes.md` is the user-facing changelog, updated once per published release, never per commit.

## Architecture

Single-window WPF application; almost all logic lives directly in `MainWindow.xaml.cs` rather than split across MVVM layers — there is no ViewModel.

- **`MainWindow.xaml` / `MainWindow.xaml.cs`** — the entire UI (menu, toolbar, status bar, editor) and its code-behind. Command routing uses standard WPF `RoutedUICommand`s (`ApplicationCommands.New/Open/Save/...`) plus custom `static readonly RoutedUICommand` fields (`SaveAsCommand`, `BoldCommand`, `ItalicCommand`) for actions with no WPF built-in. Heading shortcuts (Ctrl+1–6, one loop over `Key.D0 + level`) and the Word-compatible subscript/superscript shortcuts (Ctrl+Shift+`_` / Ctrl+Shift+`+`, i.e. `Key.OemMinus`/`Key.OemPlus` with Control+Shift — both characters are already Shift-ed) are wired in `RegisterKeyBindings` via `InputBindings` + a local `RelayCommand` rather than `CommandBinding`, there being no built-in command for them. Their menu `InputGestureText` is written by hand in XAML: WPF fills it in automatically only for a `RoutedUICommand`'s own gestures, never for `InputBindings`.
  - **`ReleaseConflictingEditorGestures()` must run before those bindings, and is not optional.** AvalonEdit declares gestures on its own editing commands — **Ctrl+I** is `IndentSelection`, **Ctrl+U** is `ConvertToLowercase` — which resolve against the `TextArea`, nearer the keyboard focus than this window, so they silently swallow the keystroke and MDEdit's Italic and Underline never fire. Ctrl+B was unaffected only because AvalonEdit claims no Ctrl+B, which made the failure look arbitrary. The fix clears those two commands' `InputGestures`; neither is exposed in MDEdit's UI. **Check this list before adding any new Ctrl-shortcut** — AvalonEdit also claims Ctrl+D (`DeleteLine`), Ctrl+Shift+U (`ConvertToUppercase`), and Insert (`ToggleOverstrike`), none of which MDEdit uses.
  - **New Window (§1, Ctrl+Shift+N) launches a second *process*, not a second `Window`** — `NewWindow()` is a `Process.Start` on `Environment.ProcessPath` and nothing more. A second process is already what Explorer produces when a file is opened while MDEdit is running, so it is proven, and it buys full independence free: own document, own `CheckUnsavedChanges` prompt, own `AppSettings`, own lifetime. **An in-process window was considered and rejected**, and not merely for the settings-collision hazard: `ApplyTheme` is split across two scopes — `ThemeService.Apply` sets `Application.ThemeMode` and swaps merged dictionaries **process-wide**, while the colorizer's `IsDark`, the active highlighting definition, the caret brush and the Highlight swatch are **per-window**. A theme switch in one in-process window would re-chrome the other's menus and toolbar while leaving its document text on the old palette — a visibly half-applied theme. Fixing that needs one shared `AppSettings` plus a changed-broadcast every window subscribes to (and unsubscribes from in `OnClosed`), i.e. a settings refactor; **that is the design to reach for if per-window independence ever stops being wanted.** Two consequences of the process choice: `settings.json` stays **last-writer-wins** between windows (not a regression — two MDEdits already behaved this way), and the new process runs the constructor's `else MaybeShowReleaseNotesOnFirstRun()` branch since it gets no command-line argument, so where the *first* window was launched with a file argument straight after an update, the second opens the release notes rather than a blank document. Accepted: the gate is doing what it says, just later than usual. Ctrl+Shift+N needed no `ReleaseConflictingEditorGestures` entry — WPF's `EditingCommands.ToggleNumbering` carries that gesture but registers it as a class input binding on `TextBoxBase`, which AvalonEdit's `TextArea` is not.
  - **Zoom (§6) is one idea: `ActiveModeStyles()` returns `ModeStyles.Scaled(_settings.ZoomLevel)` instead of the stored object.** Everything else follows, because every text size is already a multiple of `ModeStyles.BaseFontSize` — `StyleResolver.EmSize` resolves each element as `BaseFontSize * FontScale`, and `Editor.FontSize` (which every generator reads back as `GlobalTextRunProperties.FontRenderingEmSize`) is set from it too. Headings, code, table cells, the drawn task checkbox, bullets, emoji and image placeholders all scale with **no per-construct work**, preserving the relative sizes the user configured. Only two call sites changed (`ActiveModeStyles`, `LoadSyntaxHighlighting`); `SetZoom` then calls the existing `ApplyEditorPreferences()`, which already recompiles the four definitions and redraws, so **zoom has no redraw path of its own**.
    - **`Scaled` returns a copy and shares its `Elements` dictionary by reference.** Sharing is deliberate — the render path only reads it (`ModeStyles.Style(key)`, the one mutating accessor, is documented editing-only), so a live Preferences edit shows through with nothing to invalidate. Copying keeps zoom non-destructive, which the spec makes explicit; `PreferencesWindow`/`ModeStyleEditor` deliberately don't come through `ActiveModeStyles` at all, reading `_settings.EditorPreferences` directly, so they keep showing *configured* sizes while the editor renders zoomed ones.
    - **`AppSettings.ZoomLevel` is top-level, not in `EditorPreferences`** — the rule under `Services/SettingsService.cs` below; a view setting must not be reverted by a dialog that never showed it.
    - **`Editing/ZoomLevels` computes in whole-percent `int`, never `double`** (`0.7 / 0.1` floors wrong and `In` stalls); `Sanitize` deliberately doesn't grid-snap, preserving the 75%/125% presets.
    - **Ctrl+wheel coalesces its apply** (`Editor_PreviewMouseWheel`): at 10% steps a 100%→500% sweep is ~40 notches, each apply rebuilding four definitions, so the level and readout update immediately while the rebuild is posted once at `DispatcherPriority.Background` behind a queued flag — the trick `RemoteImageLoader` uses for image completions. `Preview`, not the bubbling event, or AvalonEdit's `ScrollViewer` scrolls first. No `ReleaseConflictingEditorGestures` entry needed; note Ctrl+OemPlus/OemMinus (zoom) versus Ctrl+**Shift**+OemPlus/OemMinus (super/subscript) are easy to confuse.
    - **Fixed pixel constants are the one thing that doesn't scale for free**, so six classes carry a `Zoom` property pushed from `UpdateLivePreviewState` alongside their `Enabled` flags: the shared blockquote indent family (blockquote generator, both list generators via `ListMarkerStyling`, task list, table rows) and `ImageElementGenerator`'s display clamp. **Both background renderers are deliberately absent, reading zoom back off the generator they draw under** — `TableGridRenderer` off `_tableRowGenerator`, `BlockquoteAccentBarRenderer` off `_blockquoteMarkerGenerator` — since each already holds that reference, so the drawn layer and the reserved space can't disagree (a second copy of a value that must agree is exactly how the accent bar's reveal bug happened; see the shared-gate bullet below). `DecodeHeightCap` and the 1px hairlines stay unscaled on purpose. **Accepted consequence at the bottom of the range**: `MarkdownHighlighting` rounds inline sizes to whole points, so below ~25% bold/italic/code/links converge on body text — headings, blockquote and hrule are unaffected, being colorizer-styled from an unrounded `double`.
  - Formatting operations (bold/italic/strikethrough/code = `WrapSelection`; headings = `InsertHeading`; lists/blockquote = `InsertLinePrefix`; code block = `InsertCodeBlock`; links = `InsertLink`) follow the §3 convention: wrap the selection if there is one, otherwise insert placeholder syntax and position the caret/selection for immediate typing. These are thin wrappers around `Editing/MarkdownFormatter.cs`; MainWindow supplies the `TextDocument` + current selection and applies the returned placement via `ApplyFormat`, which uses a single `Editor.Select(start, length)` call — **not** separate `SelectionStart`/`SelectionLength` assignments, since `TextEditor.SelectionStart`'s setter internally reuses whatever `SelectionLength` currently reports, which can be a stale, now-out-of-bounds value left from AvalonEdit's selection-anchor bookkeeping after `doc.Replace`. Reproducible by wrapping a selection reaching end-of-document; caused a real `ArgumentOutOfRangeException` crash, fixed and covered by `ApplyFormatSelectionTests`.
  - Live preview / WYSIWYG state: `_settings.LivePreview` (persisted) drives `UpdateLivePreviewState()`, which sets `Editor.FontFamily`/`Editor.FontSize` from the active mode's base (`_sourceFontFamily`/`_wysiwygFontFamily`, derived from `EditorPreferences` by `ApplyEditorPreferences`), calls `ApplyActiveModeStyles()` and `UpdateHighlighting(...)` — **the editor mode selects which of the four compiled highlighting definitions is live, so this call is not optional** — and flips `LivePreviewEnabled` on `MarkdownLineColorizer` plus `Enabled` on all thirteen element generators (heading, emphasis, code fence, image, link, underline, emoji, blockquote, bullet list, task list, numbered list, table row, horizontal rule) and the three background renderers (`BlockquoteAccentBarRenderer`, `TableGridRenderer`, `HorizontalRuleRenderer`). It also syncs the View → Editor Mode radio-style menu checkmarks (`MenuEditorModeSource`/`MenuEditorModeWysiwyg`, set manually like the Theme submenu — no native radio-group support is used anywhere in this codebase) plus the toolbar's `BtnEditorModeToggle` (a `ToggleButton`, the toolbar's first section ahead of a `Separator` and every other group — the only stateful toggle there, everything else being one-shot commands). Its `Click` handler reads back `IsChecked` rather than tracking a separate flag: WPF flips `IsChecked` before raising `Click`, so the handler already holds the state the click asked for.
    - `OnCaretPositionChanged` tracks `_lastCaretLine` (heading, code-fence, blockquote, bullet-list, task-list, horizontal-rule reveal — line-grained) and `_lastCaretOffset` (emphasis, image, link, underline, emoji — span-grained, since a caret move within one line can cross a span boundary), redrawing just the old and new line via `TextView.Redraw(DocumentLine)` whenever the offset changes at all; generator state is updated *before* those redraws so both lines render against the new caret position. Code-block fences and tables are the exceptions, being per-block constructs whose reveal region can sit well outside those two lines — so it also calls `RedrawEnclosingFenceLines()` (just the block's two fence lines, the only ones whose appearance changes) and `RedrawEnclosingTableLines()` (the *whole* block — crossing a table's boundary flips every row between grid and raw source) for both the old and new caret line. Blockquotes and horizontal rules deliberately don't get block-wide treatment despite sharing the reserve-hide/draw-separately split: only the caret's own line reveals its raw text, and a horizontal rule occupies exactly one line anyway. `ResetLivePreviewCaretTracking()` re-syncs all thirteen generators after `NewDocument`/`OpenFile` reset the caret to line 1 (called wherever `UpdateHighlighting` is, for the same "just loaded a different document" reason).
  - Document dirty-state (`_isDirty`), title bar, and status bar are kept in sync through `MarkDirty()` / `UpdateTitle()` / `UpdateStatusBar()` / `UpdateDocumentStats()`, called after edits, caret moves, and file operations.
  - **The status bar is a plain `Border` + `Grid`, deliberately not `StatusBar`/`StatusBarItem` — don't "restore" the proper control.** The themed one rendered *no text at all* in either theme: this app opts into the experimental Fluent `ThemeMode` (see `ThemeService`), and Fluent's `StatusBarItem` wants more vertical room than the fixed `Height="22"` allowed, clipping the content away entirely. The symptom is total invisibility, including literal XAML text, which reads like a data-binding or layout-docking bug and sends you the wrong way — the docking was fine throughout (the editor `Border` follows the status bar in the root `DockPanel`, so the editor is the `LastChildFill` child and `Dock="Bottom"` works). Two details keep it working: `MinHeight` rather than `Height`, so content can never be clipped again; and `TextElement.Foreground` rather than `Foreground`, because `Border` has no `Foreground` property and the plain form silently does nothing. **`MinHeight` cuts both ways now that the bar carries the zoom controls (§6)** — it grows rather than clips, so a control with loose padding silently makes the strip taller instead of failing visibly; the zoom buttons are 18×18 with tight padding for that reason. The divider above it is the editor `Border`'s `BorderThickness="0,1"`, not the status bar.
  - Status bar (§9) is split into **two** update methods on purpose. `UpdateStatusBar()` does caret position and selection size — cheap, and runs on every caret move. `UpdateDocumentStats()` does size and character count, walking the whole document for a UTF-8 byte count, so it runs only on `TextChanged` and once at construction. **Don't merge them**: the byte count on the caret path would materialize `Document.Text` on every arrow-key press. Selection is additionally hooked to `TextArea.SelectionChanged`, since a selection can change without the caret moving. The byte count is the size a *save* would produce, including `Encoding.UTF8.GetPreamble().Length`, since `FileService` writes through `File.WriteAllText`, which emits the BOM; without it the count would disagree with Explorer by exactly 3 bytes. Filename and dirty marker are deliberately absent (the title bar has both). The character count goes through `Editing/CharacterCounter.Count`, not raw `TextLength`, so each line break can be charged a user-chosen weight (`AppSettings.LineBreakCharWeight`, 0/1/2, from View → Line Breaks Count — `SetLineBreakCharWeight`/`ApplyLineBreakCharWeight`) instead of whatever that break actually is. It sums each `DocumentLine.DelimiterLength` (0, 1, or 2), subtracts that real total from `TextLength`, and adds back `lineBreakCount * weight` — so mixed endings in one document are charged identically under one weight rather than each keeping its actual width. Default is 2, matching a literal CRLF, so upgrading from a version without the setting changes nothing displayed.
  - `CheckUnsavedChanges()` is the single choke point for the save/discard/cancel prompt before New, Open, and Close.
  - **The startup file comes from `Editing/StartupFile.Resolve`, which reads `args[1]` *and* the `ClickOnce_ActivationData_0` environment variable — the second is not optional.** A double-clicked `.md` goes through the ClickOnce association (`rundll32 dfshim.dll,ShOpenVerbExtension …`), which activates the app through ClickOnce and passes the file **only** as launcher activation data, never on the command line; reading `args[1]` alone opened a blank window on every installed machine. Either a plain path or a `file:` URI is accepted, since the docs don't say which the variable carries. `StartupFileTests` pins it.
  - `ApplySettings()` applies loaded `AppSettings` (word wrap, line numbers) on startup; the menu click handlers save back to `SettingsService` immediately on toggle, not just on close.
  - MRU (File → Recent Files, §1): the list is `AppSettings.RecentFiles` (persisted), the list *logic* is `Editing/RecentFiles.cs` (pure, unit-tested), and the menu is built at runtime by `RebuildRecentFilesMenu()` — `MenuRecentFiles` is declared empty in XAML and regenerated on every change, so there is nothing static to keep in sync. Entries are added by `AddToRecentFiles`, called from `OpenFile` (inside the `try`, so a file that failed to open never lands in the list) and `ExecuteSaveAs`; plain `Save` doesn't, that path already being in the list. `OpenRecentFile` checks `File.Exists` *before* `CheckUnsavedChanges` — a stale entry shouldn't make the user answer a save prompt for a file that isn't there — and offers to drop the entry when missing. Two details to preserve: file names are inserted with `"_"` doubled (WPF eats a single underscore as an access-key marker, mangling names like `my_notes.md`), and the full path goes in the `ToolTip` since file names alone are frequently ambiguous. `ApplySettings()` runs the persisted list through `RecentFiles.Sanitize` rather than trusting it — `settings.json` is hand-editable, and the cap may have changed between versions.
- **`AboutWindow.xaml` / `.xaml.cs`** — small owned dialog for Help → About. Shows `Resources/AppIcon.png`, not the `.ico` (WPF's `Image` renders a multi-res `.ico` from its smallest embedded frame and upscales it, blurry above ~32px), plus assembly version and build date read via reflection (`AssemblyMetadataAttribute` key `"BuildDate"`, stamped by `MDEdit.csproj`). It links to the shipped `LICENSE.txt` and `THIRD-PARTY-NOTICES.md` but **deliberately doesn't open them itself**: it records the path in `RequestedDocumentPath` and closes, and `MenuAbout_Click` opens it after `ShowDialog()` returns — the read-back convention `EmojiPickerWindow.SelectedShortcode` also uses. Two load-bearing reasons: MainWindow owns `OpenFile` along with the `CheckUnsavedChanges` guard and error reporting, so this becomes an ordinary user-initiated Open (matching `MenuOpenReleaseNotes_Click`); and shelling the file to its default handler would launch a **second MDEdit instance**, MDEdit being the `.md` handler on any ClickOnce install.
- **`PreferencesWindow.xaml` / `.xaml.cs` + `ModeStyleEditor.cs`** — View → Preferences (§6), the second owned dialog, but unlike `AboutWindow` every change applies live: there is no Apply step. The window is only a shell — a `TabControl` with WYSIWYG and Source tabs plus OK/Cancel/Reset — and **each tab's contents are built by one `ModeStyleEditor` instance, the same class twice**, so the tabs cannot drift apart. Built **imperatively in code-behind**, following `RebuildRecentFilesMenu()`: this codebase has no MVVM/data-binding layer anywhere else, so a dialog is the wrong place to introduce one.
  - **Layout is master–detail, not a grid.** Twenty elements × (family, size, weight, italic, decoration, four colors) doesn't fit a readable table, and splitting attributes across tabs would separate an element's font from its color. Left: a `ListBox` of `StyledElements.All`, whose items are an `ElementItem` record carrying key *and* label — the list displays labels but must round-trip keys, and a label→key lookup breaks the moment two labels coincide. Right: the selected element's settings plus a live sample.
  - **There is deliberately no separate "base font" row.** The base *is* the `normal` element, first in the list, so each value has exactly one place it is set. That makes the detail panel bimodal, and `SelectElement` is where the shapes diverge: for `normal` the font combo has no `(inherit)` entry and writes `BaseFontFamily`, the size box holds **absolute points** rather than a multiplier (unit label and resolved-size readout adjusting to match), and Decoration plus the Background swatches are disabled via `SetEnabled`, which also sets `ToolTipService.ShowOnDisabled` — a disabled control swallows mouse events, tooltip included, so the explanation would otherwise never be readable. "Reset this element" restores `BaseFontFamily`/`BaseFontSize` too when `normal` is selected, or the one element whose reset matters most would half-work.
  - **`ModeStyles` reaches each editor as a `Func<ModeStyles>`, never a captured reference.** Cancel and Reset replace `AppSettings.EditorPreferences` wholesale, so a reference captured at construction would leave the editor writing into an object nothing renders from — the hazard `ApplyEditorPreferences` avoids by always re-reading. Same for the theme, passed as a `Func<bool>` so the sample renders in whichever theme is actually in effect.
  - Font drop-downs list **monospaced families above a `Separator`, then every installed family** (`Editing/FontCatalog`), with `(inherit — <base family>)` first on the per-element combo. The current value is inserted when it isn't a plain installed-font match — the code font's default is a fallback stack (`"Cascadia Code, Consolas, Courier New"`), never a single `Fonts.SystemFontFamilies` entry, so without that the shipped default showed blank. The `Separator` is `IsEnabled = false`: it is its own container in an `ItemsControl`, so nothing else stops it becoming `SelectedItem`.
  - **Italic is a tri-state `CheckBox` (indeterminate *is* inherit); weight and decoration are four-entry combos** whose first entry is `(inherit)`. Decoration is one control rather than two checkboxes because AvalonEdit cannot render underline and strikethrough together — see `Editing/StyleResolver`. Size is a multiplier with the resolved point size beside it, because XSHD-driven element sizes round to whole points and 1.10 vs 1.15 giving the same result otherwise reads as a bug.
  - Colour swatches open `System.Windows.Forms.ColorDialog` (fully qualified at the call site — see the `MDEdit.csproj` note on why). **Clear works on a light/dark pair, not one half**: inheriting one and pinning the other has no sensible rendering.
    - The picker's custom slots persist for the session via **`static` `_customColors`** (read back *before* the non-OK early return; values are COLORREF `0x00BBGGRR`, not RGB) — rationale in its doc comment in `ModeStyleEditor`.
  - **Cancel and Reset to Default both *replace* `AppSettings.EditorPreferences` wholesale rather than mutating it property-by-property.** Cancel restores a `JsonSerializer` round-trip snapshot taken when the window opened (`EditorPreferences` is a plain data class, so no hand-written `Clone()` is needed); Reset assigns a fresh `new EditorPreferences()`. Both are safe specifically because `ApplyEditorPreferences` always reads `_settings.EditorPreferences` fresh at the start of every call rather than holding an earlier reference — if it did, replacing the object wholesale would silently stop taking effect.
  - `MenuPreferences_Click` constructs the window with the live `_settings`/`ApplyEditorPreferences` and calls `SettingsService.Save(_settings)` once after `ShowDialog()` returns, regardless of OK/Cancel — the "save after the dialog returns" shape every other settings write here uses.
  - **Two changes to how an unmodified install renders were accepted deliberately** and shouldn't be "fixed" back: `blockquote` and `horizontalRule` pin `FontWeight = Normal` (the old `ColorLine` calls forced it, so `> **bold**` rendered flat — pinned to preserve that, but now reachable, so anyone wanting the emphasis to survive can set it to inherit); and the drawn WYSIWYG bullet honours the List marker colour, so it is blue rather than plain foreground. The second is the one accepted break of the "unmodified install renders identically" bar, taken because the drawn "•" contradicting the raw blue "-" was exactly the inconsistency folding the list generators in was meant to end.
- **`EmojiPickerWindow.xaml` / `.xaml.cs`** — Format → Emoji / the toolbar's 🙂 button (§3), the third owned dialog. Simpler than the other two: a pure chooser with no settings/document dependency, so no Cancel/Reset snapshot logic. Builds one `Button` per `EmojiCatalog.All` entry imperatively into a `WrapPanel` — the `PreferencesWindow.BuildColorGrid`/`RebuildRecentFilesMenu` imperative-child-per-item convention, not an `ItemsControl`/`DataTemplate` — re-filtered live by `SearchBox.TextChanged` on a substring match against the shortcode, not a parsed category from `Emoji.txt`'s `#` comments (out of scope for v1). Picking an entry (click, or Enter over the filtered list) sets `SelectedShortcode` and `DialogResult = true` and closes — pick-and-close, not a stay-open multi-insert session. `MainWindow.BtnEmoji_Click` reads it back and applies `MarkdownFormatter.InsertEmoji` through the usual `ApplyFormat` path, replacing this handler's previous `WrapSelection(":", ":")` stand-in entirely.
- **`Services/FileService.cs`** — tracks `CurrentPath` and does the disk I/O (`LoadFile`, `Save`, `SaveAs`, `Reset`). Always UTF-8.
- **File associations follow Windows' default-apps rules: MDEdit registers as a *candidate* and the user chooses in Settings — it never writes a default.** Two halves:
  - **The pubxml's `FileAssociation` items (`.md`/`.markdown` only) own the `MDEdit.Document` ProgID and its open command**, `rundll32 dfshim.dll,ShOpenVerbExtension {guid} %1`. That command names the deployment, not a version folder, so **it is the only thing that keeps double-click working across updates** (and it activates through ClickOnce, so double-clicks check for updates). Its price is that the file arrives as activation data, not `args[1]` — see the startup-file bullet under `MainWindow.xaml.cs`. `.txt` is deliberately not in the pubxml: a manifest association asks nobody.
  - **`Services/DefaultAppsService.EnsureRegistered()` runs every launch** and adds `OpenWithProgids` for `.md`/`.markdown`/`.txt`, `Software\MDEdit\Capabilities`, and a `RegisteredApplications\MDEdit` entry — **all naming the ProgID only, never a path**, so nothing it writes can go stale. It writes only differing values, and does nothing unless the ProgID's command passes `DefaultAppsGate.IsUpdateProofCommand` (so dev builds register nothing). A one-time first-run question (`AppSettings.DefaultAppsPromptShown`) and Help → Set Default Apps both open `ms-settings:defaultapps?registeredAppUser=MDEdit`.
  - **`FileAssociationService` and Help → Register File Associations were removed (2026-11-21); don't reintroduce anything that writes an exe path or an extension's default value.** It wrote a version-specific path that went stale on every update and, sharing the ProgID, overwrote ClickOnce's command. Windows 8+ also ignores or blocks apps setting defaults directly (`UserChoice` is hash-protected).
- **`Services/SettingsService.cs`** — persists `AppSettings` (`WordWrap`, `ShowLineNumbers`, `Theme`, `LivePreview`, `LoadRemoteImages`, `ConvertEmojiOnSave`, `RecentFiles`, `LastReleaseNotesVersionShown`, `DefaultAppsPromptShown`, `LineBreakCharWeight`, `ZoomLevel`, `EditorPreferences`) as JSON at `%AppData%\MDEdit\settings.json`. Falls back to defaults on a missing/corrupt file rather than failing startup.
  - **The top-level-vs-`EditorPreferences` rule, stated once here and referred to from each setting's own bullet:** `EditorPreferences` is replaced *wholesale* by PreferencesWindow's Cancel/Reset, so any setting that dialog never shows must sit **top-level**, or a dialog the user cancelled would silently revert it. Three settings are top-level for this reason — `LoadRemoteImages` (privacy, §5), `ZoomLevel` (view, §6), `ConvertEmojiOnSave` (edits document content, §1) — each a different flavour of the same hazard: silently resuming network requests, silently resizing the document, silently changing what gets written to disk. `AppSettingsTests` pins the defaults-to-off invariant for the two that carry one.
  - `EditorPreferences` (§6) holds **two independent `ModeStyles`, `Wysiwyg` and `Source`** — a base font family and size plus a `Dictionary<string, ElementStyle>` of per-element overrides, keyed by `Editing/StyledElements`' stable string keys. Four things about it are load-bearing:
  - **Every `ElementStyle` property is nullable and null means inherit.** "Unset" must be distinguishable from "set to whatever the base happens to be", or changing the base font would stop propagating to any element the user once touched and reverted. The shape maps 1:1 onto AvalonEdit's own semantics (verified against `HighlightingColorizer.ApplyColorToElement`, tag `v6.3.1`), which rebuilds a typeface from the element's *current* one for whichever fields are null.
  - **`FontWeight` is a string, not a bool**, so `SemiBold` stays expressible — headings 4–6 are SemiBold, and a Bold checkbox would have defaulted them to Normal and rendered them lighter. **`Decoration` is one field, not two booleans**, because AvalonEdit cannot render underline and strikethrough together. **`FontScale` is a multiplier, not points**, so one base-size change rescales everything.
  - **`WysiwygDefaults()` is written as `SourceDefaults()` plus named deltas** — the five heading scales, the two code font families, the hyperlink underline, and strikethrough dropping its grey — rather than a second full table, so the modes can't silently drift apart when a colour changes. Hyperlinks underline in WYSIWYG only, because there the `[text](url)` markers are hidden and the link text reads as a document's link, while in source the visible syntax already says "link". **Strikethrough now actually strikes in both modes** (before §6 it was grey text and nothing more — AvalonEdit could always draw the strike, nothing asked it to); the modes differ only in colour, WYSIWYG dropping the grey so struck text reads at ordinary document colour rather than doubly deleted, source keeping it as a second cue while reading raw syntax.
  - **The code palette is the one default that deliberately does not match its pre-§6 value** (green `#00FF33` on black in light, amber `#FFB000` in dark, versus the old `#C7254E` on `#FEF2F2`). Everywhere else "an unmodified install renders identically" still holds and is pinned by tests. Every old special case became an ordinary default: source mode is all-mono because its base is; heading scaling is WYSIWYG-only because source leaves `FontScale` null; code stays mono in WYSIWYG because that mode pins the family. `EditorPreferencesTests` pins all of it, including that the two tables differ *only* by those named deltas.
  - **`Version` is stamped by `SettingsService.Save` and read by nothing — deliberate, not dead code.** The one-time fold of a pre-per-element `settings.json` (`Migrate()`, the ~22 legacy flat properties, the frozen `V1` baseline table) **was removed on 2026-08-01** together with `EditorPreferencesMigrationTests.cs`: ~500 lines protecting at most 13 settings (2 fonts + 11 colour pairs, all the old flat dialog ever exposed) across a single transition that cannot recur, for an installed base the owner sized as "just me / a couple of people". Per-element styling hadn't shipped when it was cut — last publish was `1.0.5.72` — so no upgrade path was broken. **Do not reintroduce it**; if a future schema change needs a migration, write that one against `Version`, which is why the stamp survives. Dropping the stamp too would leave every file written from now on unidentifiable.
    - **Removal is safe because an unrecognized property is simply ignored by System.Text.Json**, so an old file loads onto current defaults rather than throwing — a one-time visual reset, not data loss. That is now the *entire* recovery story, pinned by `AppSettingsTests.PrePerElementFile_LoadsOntoCurrentDefaults`. A `[JsonExtensionData]` sink or `UnmappedMemberHandling.Disallow` would turn it back into a `JsonException`, which `Load` catches into a **total** reset of every setting, not just the presentation ones.
    - **`Version` still has no property initializer.** System.Text.Json leaves an initializer in place when the property is absent from the JSON, so defaulting it to `CurrentVersion` would make an unstamped file claim to be current — destroying the one distinction the field preserves. Stamping on write is also what it honestly means: the schema the *file* was written with.
    - **Changed defaults reach existing `settings.json` files via a defaults-revision counter**, separate from the schema `Version`. **Bump `EditorPreferences.CurrentDefaultsRevision` whenever you change a shipped default value** — forget it and the change reaches nobody, silently. Bump `Version` only when the *shape* changes. It works because `ModeStyles.TouchedElements` records which elements the user set (`ElementStyle`'s null-means-inherit can't express "never set"); `ModeStyleEditor.Changed()` is its single writer and `Reset(key)` **clears** the mark — don't collapse the two. `UpgradeToCurrentDefaults()` must run `InferTouchedElements` *before* re-applying, or a pre-tracking file (empty set) loses every customization. A frozen baseline-defaults table was rejected (it would resurrect the deleted `Migrate()`). Details in `SettingsService.cs`; `DefaultsRevisionTests` pins it.
    - **Real `settings.json` files are PascalCase**: `Save` calls `JsonSerializer.Serialize` with no options, and deserialization is case-sensitive by default. A camelCase test fixture silently fails to bind — it cost one red test here. `SettingsService.Deserialize(string)` exists so this path is testable without touching `%AppData%`.

- **`MarkdownLineColorizer.cs`** — an AvalonEdit `DocumentColorizingTransformer` on `TextView.LineTransformers`, handling *line-level* styling XSHD span/rule matching can't express well: heading colour/weight by `#` count, blockquote italics (via `MarkdownSyntax.TryGetBlockquoteMarkerLength`, shared with `BlockquoteMarkerElementGenerator` so the two can't disagree on what counts as a blockquote line), horizontal rules. It holds the **active mode's `ModeStyles`** (pushed by `ApplyActiveModeStyles` — which mode is live is MainWindow's business) plus `IsDark`, resolving each element through `StyleResolver.Resolve` and caching per element key; **both setters clear that cache**, which is the whole invalidation story. `ApplyLineStyle` applies only the non-null members of the resolved style, so "inherit" in Preferences means the run keeps what it had. `Resolve` is public because `HorizontalRuleRenderer` and `BlockquoteAccentBarRenderer` read their brush through a reference to this instance rather than holding a copy — the drawn rule/bar and the raw text revealed under the caret can never disagree, and per-mode colours made two copies materially easier to desynchronise. This runs alongside (not instead of) the XSHD highlighting, and none of it is gated by `LivePreviewEnabled` — headings/blockquotes/hrules are styled this way in either editor mode. **`HeadingScale` is gone**: heading sizing is a per-mode default (source leaves `FontScale` null), which also retired the live-preview gate that sat on it.
  - It owns the **revealed-source font swap** (`ApplyRevealedSourceFont`, live-preview-gated, fed `CaretLine`/`CaretOffset` + `SourceFontFamily` by MainWindow): revealed markdown renders in the mono source font at two grains matching the reveal scopes exactly — **whole line** for the caret's line when it carries a line-scoped construct (heading/blockquote/bullet/task/numbered/horizontal-rule) and for every line of a table whose block contains the caret; **per span** for whichever inline runs the caret is inside on its own line (emphasis, links, underline, emoji), using the same inclusive-of-both-edges rule as the marker generators so the mono region and the revealed markers can't disagree. The per-span swap is acceptable precisely because the span's layout already shifts at that instant (its markers appear), so the font change rides the same transition; plain prose lines stay in the document font so paragraphs don't jiggle while arrowing through them. It runs *before* the styling pass and **returns whether it swapped the whole line**, which `ApplyLineStyle` uses to skip its own family override — otherwise a revealed heading would snap back to the document font the instant the caret reached it. Only the *family* is suppressed; size, weight and style still apply, matching how reveal behaved before per-element fonts. Code needs nothing here: WYSIWYG's `inlineCode`/`codeBlock` elements pin the mono family (`HighlightingColorizer.ApplyColorToElement` applies `HighlightingColor.FontFamily` at render time), which is the entire reason the WYSIWYG font flip needs no code-block handling anywhere.
  - `StyleScriptSpans` is the one *span*-level thing this class does: it raises/lowers superscript and subscript content via `SetBaselineAlignment` and shrinks it by `ScriptScale`, and is deliberately **not** gated on `LivePreviewEnabled` — the baseline shift *is* the construct, the way bold renders bold in source mode. Heading/blockquote/hrule lines `return` before reaching it, so a script inside one renders plain; accepted, since those lines style themselves as a unit and a later per-span change would fight the line-wide typeface.
- **`Editing/` folder** — UI-free classes factored out to be unit-testable and to anchor the live-preview implementation. **Live-preview constructs** at the end of this section summarizes the generators in one table and gives the checklist for adding another:
  - **`StyledElements.cs`** — the canonical list of the twenty styleable elements (§6): stable persisted key, Preferences label, and matching `Markdown.xshd` colour name (null for the nine not styled through XSHD — `normal`, headings, blockquote, horizontal rule). **`normal` is first and is the odd one**: default body text rather than a Markdown construct, so its family and size are the mode's `BaseFontFamily`/`BaseFontSize` rather than fields of its own `ElementStyle` (a size expressed as a multiplier of itself would be circular), and its weight/italic/foreground are applied to the *editor control* by `MainWindow.ApplyNormalTextStyle` rather than through either construct-styling path. Decoration and background are deliberately not offered for it — see that method. **Keys are stable strings, never enum ordinals**: they are persisted as dictionary keys, so a reordered enum would silently remap a user's settings onto the wrong elements. `Heading(int level)` is the single level→key mapping, clamping above 6 to match `TryGetHeadingLevel`; building `$"heading{level}"` at a call site would work today and break silently the moment a key is renamed. `listMarker` is the one element on *both* rendering paths — see the list-generator bullet.
  - **`StyleResolver.cs`** — turns a persisted `ElementStyle` (hex strings, named weights, a named decoration, a size multiplier) into the WPF values both rendering paths need, as a `ResolvedStyle` whose null members mean inherit. Shared deliberately: styling reaches the editor through two unrelated mechanisms (`MarkdownHighlighting` writing onto the highlighting definition, `MarkdownLineColorizer` onto visual line elements), which must never disagree about what a stored value means. Every mapping returns null for an unrecognized value rather than throwing — `settings.json` is hand-editable, and a typo should cost that one override, not the ability to open a document. Brushes **and the empty "no decorations" collection** are frozen: they're cached and shared across every visual line using the element, and an unfrozen `Freezable` also carries thread affinity (which made a test fail before it was frozen).

WPF exposes no fixed-pitch flag and doesn't surface the OS/2 table's `isFixedPitch`, so this *measures*: a family is monospaced when `i`/`W`/`M`/`.` all advance identically per `GlyphTypeface.AdvanceWidths`. Four probe characters rather than two so a family matching on one pair isn't misfiled, plus a zero-width guard.   - **`MarkdownSyntax.cs`** — shared line-construct detection. `MarkdownLineColorizer` and the marker-hiding generators both call into this rather than each having their own parsing, so they can never disagree about what counts as a given construct. **Extend this file first when adding live-preview support for another construct.**
    - **Block constructs** — `TryGetHeadingLevel` (ATX heading + marker length); `TryGetBlockquoteMarkerLength` (leading `` `>` `` run including nested `` `> > ` ``, plus a `depth` out param used to draw one indent bar per level); `IsFenceDelimiterLine`/`TryGetEnclosingFenceBlock`; `IsHorizontalRule` (whole-line `---`/`* * *` — moved here from `MarkdownLineColorizer`'s private helper so bullet detection can exclude hrule lines by the exact definition the colorizer styles them with); and the table family — `IsTableRowLine`/`IsTableDelimiterLine` (deliberately stricter than GFM: both outer pipes required at column 0, three-dash minimum in delimiter cells, so "a | b" prose never renders as a table row), `TryGetTableBlock` (header + directly-adjacent delimiter with matching cell count + every contiguous row line below; the *topmost* valid header in the contiguous run wins, so row-shaped prose above a real table is excluded rather than poisoning the pairing), and `GetTablePipeOffsets`/`GetTableCells`/`GetTableAlignments` (escape-aware `\|` splitting and the delimiter row's colon alignments — pipe offsets are shared with the colorizer's pipe dimming so the two can't disagree).

    - **String-based inline rendering** — `FormatInline(string)` is the one entry point taking a *string* rather than a `DocumentLine`, because a table cell is a substring with no document offset of its own. It layers the four inline scanners into `InlineRun`s (text + an `InlineStyles` flags enum) with markers removed and emoji substituted; see the `TableRowElementGenerator` bullet for why measurement must consume the same runs rendering does.
    - **Inline spans** — `FindEmphasisSpans` (bold/italic/bold+italic/strikethrough/highlight/superscript/subscript/inline-code runs, as `EmphasisSpan { Start, End, MarkerLength }`); `FindUnderlineSpans` (`<u>…</u>`, as `UnderlineSpan { Start, ContentStart, ContentEnd, End }` — its own scan, being HTML rather than an emphasis marker); `FindScriptSpans` (just the superscript/subscript runs as `ScriptSpan { ContentStart, ContentEnd, IsSuperscript }` — same scan, filtered by `EmphasisKind`); and `FindLinkSpans` (links/images, as `LinkSpan { Start, TextStart, TextEnd, End }`).
    - *Emphasis lexer* — `FindEmphasisSpans` mirrors `Markdown.xshd`'s exact patterns and precedence (bold+italic before bold before italic; character-class exclusion instead of wildcard quantifiers, to avoid catastrophic backtracking) via a tiny `\G`-anchored, non-overlapping single-pass lexer, so the two never drift apart. Inline code's content is never recursed into — it's literal per CommonMark's code-over-emphasis precedence, which the lexer's leftmost-wins scan also provides at the top level, same as AvalonEdit's earliest-match rule resolution.
    - *Mixed-delimiter nesting* — the lexer recurses one level into each match's inner content to find a nested run of the *opposite* delimiter (`_**bold**_`, `**_italic_**` — CommonMark forbids nesting the same delimiter inside itself, so this is the standard way authors combine bold+italic as two runs instead of `***text***`). It falls out free with no extra filtering, since a match's content can never contain its own delimiter (excluded by the pattern's own content class), so re-scanning that content with the same pattern list can only find an other-delimiter run; the same mechanism covers strikethrough wrapping or wrapped by emphasis (`~~**text**~~`, `**~~text~~**`).
    - *Mutual skip-awareness* — `FindEmphasisSpans` and `FindLinkSpans` each try the other's pattern table first at every scan position (without recording a match, just to advance past it), mirroring how `Markdown.xshd`'s Link rule is a flat `<Rule>` with no nested `RuleSet` unlike Bold/Italic's `<Span>`: `[**bold**](url)` is one opaque link with no separately-coloured nested Bold, and `**[link](url)**` one opaque Bold run, in both the real highlighter and here. Both scanners also skip a leading bullet-list marker first (`LeadingBulletMarkerLength`), mirroring the XSHD's rule order where ListMarker precedes every emphasis/link rule, so on `* item*` the leading `* ` is a list marker rather than the opener of an italic run swallowing the whole line.

The reserve-space/draw-separately split exists because an `InlineObjectElement` is confined to its own line's content flow: the vertical gap between lines belongs to `TextView`'s layout, not to any single line's content, so no per-line element, however tall, can make adjacent bars touch — confirmed in `TextView.cs`, which measures inline embedded objects with an *infinite* constraint (`Element.Measure(new Size(double.PositiveInfinity, double.PositiveInfinity))`) rather than the line's actual height. It processes one nesting level at a time (`for level in 1..maxDepth`, each its own contiguous-run scan) rather than all levels in one pass, so a depth transition mid-blockquote (`"> a"` then `">> b"`) keeps level 1's bar continuous while level 2's covers only the deeper sub-run.   - **`EmojiElementGenerator.cs`** — per-span reveal with a *visible* replacement (the emoji character), the first generator to combine those. Replaces the whole `:joy:` run rather than hiding markers around content — unlike emphasis, there's no inner text to keep.
  - **`UnderlineMarkerElementGenerator.cs`** — `LinkMarkerElementGenerator`'s two-independently-sized-regions approach applied to `<u>`/`</u>`, same per-span reveal. Hides the tags only; the underline comes from the XSHD's `Underline` colour, so this class needs no theme wiring.
  - **`LinkMarkerElementGenerator.cs`** — per-span reveal applied to links/images, but with an **asymmetric** hidden region: `[` (or `![`) as prefix and `](url)`/`][ref]` as suffix, the URL/reference portion having no fixed width the way `**`/`_` do — so it constructs two independently-sized `InlineObjectElement`s per link (`LinkSpan.TextStart - Start` and `LinkSpan.End - TextEnd`) rather than reusing one `MarkerLength` at both ends. Since local image rendering landed it is also the fall-through for every image span `ImageElementGenerator` declines (remote, unresolvable, reference-form) — it needed zero changes for that.
  - **`ImagePathResolver.cs`** — the pure decline-half of image rendering, with **two deliberately disjoint entry points** sharing one private `Normalize` (trim, `<...>` unwrap, trailing-quoted-title strip): `TryResolve` returns an absolute *local* path and declines every scheme, so a URL can never reach `File.OpenRead`; `TryResolveRemote` accepts *only* http/https by whitelist and so declines every local path. A declined result **always means "fall through to `LinkMarkerElementGenerator`", never "broken"**. The whitelist — not `Uri.TryCreate`'s success — decides remoteness, because `Uri.TryCreate` happily turns `C:\x.png` and `\\server\share\x.png` into absolute URIs with scheme `file`; the mirror image of the local side's "deliberately not `Uri.TryCreate`, which claims `C:\x.png` with scheme `c`". Kept as two entry points rather than one `ImageTarget` union so a declined remote span is the structural default reached by writing no code, instead of a `switch` arm someone could get wrong.
  - **`ImageElementGenerator.cs`** — per-span reveal with a *visible* replacement (the decoded picture), the first inline element that **isn't text-sized** — the line grows to fit it. Owns `RemoteEnabled` (the single remote gate), the shared `DecodeFrozen`, and the two placeholder kinds. See the image bullets under **Live-preview constructs** for the full design.
  - **`RemoteImageLoader.cs`** — the app's **only** networking code, and its first async/`HttpClient`/`CancellationToken` code (the second-ever `Dispatcher.BeginInvoke`, after MainWindow's OS-theme marshal). Holds the URL-keyed four-state cache (absent/InFlight/Loaded/Failed as one record rather than a dictionary plus a parallel in-flight set, with `Failed` terminal until `Invalidate()` so a dead URL isn't re-requested on every scroll), the shared static `HttpClient`, the generation + cancellation guarding, the UI-thread-only mutation rule that removes the need for a lock, and the coalesced `Background`-priority redraw. Its class comment carries the privacy guarantee in full — read it before touching anything here.
  - **`HorizontalRuleElementGenerator.cs`** — per-**line** reveal (caret elsewhere hides the line, caret on it reveals the raw `---`/`* * *`), but the hidden range is the **whole line** — a rule has no marker-prefix-vs-content split, so it reuses the fence idiom rather than the heading/blockquote partial-prefix one. The drawn rule lives in `HorizontalRuleRenderer`: a rule has no content of its own to size a rendered element from (unlike a bullet's "•" or a table's measured columns), so it must span whatever width is on screen, which only a background renderer answers. `IsRendered` is the single shared gate both classes call, so the hidden text and the drawn line can't disagree.
  - **`HorizontalRuleRenderer.cs`** — draws the rule across every visible line the generator is hiding, reading its brush from `MarkdownLineColorizer.Resolve(StyledElements.HorizontalRule)` through a constructor-supplied reference so the drawn line and the revealed raw text read as the same colour. (It held its own `HRuleBrushLight`/`Dark` pair before per-element styling, as `BlockquoteAccentBarRenderer` did.) Unlike the other two renderers it is deliberately **pinned to the viewport rather than tracking `HorizontalOffset`**: a rule has no document-relative anchor worth preserving under horizontal scroll (it represents "the whole row"), so it fills what is currently on screen instead of appearing to scroll away when the user scrolls right to read a long line elsewhere.
  - **`TableRowElementGenerator.cs`** — per-**block** reveal like code fences (caret anywhere in the table reveals the whole thing as raw source, so editing always happens on raw text and column widths never shift under the caret), with whole-line **visible** replacement: each header/body row becomes a run of fixed-width `TextBlock` cells (header bold, delimiter-row colons honoured as `TextAlignment`), and the delimiter row is hidden whole via the fence idiom **and collapsed to zero height by `TableDelimiterCollapser`** — hiding its content alone left a full-height blank band reading as an empty row. Column widths are a whole-table property (the reason tables never fit the per-line/per-span shapes): the widest cell per column, measured via `FormattedText` with the editor's own typeface, computed once per table into a `TableLayout` and cached. **Any** document change clears the whole cache (`ReferenceEquals` on `TextDocument.Version`) rather than tracking which table a change touched, so a stale width can't survive an edit; a **font change** (the WYSIWYG flip) also clears it, detected by comparing the captured typeface/em-size, since the version key can't see a font swap that changes every measured width without touching the document. The text properties for measurement are captured on every `GetFirstInterestedOffset` call because `TableGridRenderer.Draw` can reach `ComputeLayout` outside any construction context. `ColumnCount` is the max cell count across *all* rows, not the delimiter's — a body row with extra cells gets extra columns, because **rendering must never hide cell content**. `TryGetRenderedTable` is the single shared is-it-rendered/what-size gate for this class and the renderer. Rows carry a left `Margin` of `BlockquoteMarkerElementGenerator.IndentPerLevel` (referenced, not duplicated), and `TableGridRenderer` offsets its `x0` by the same constant, so the grid sits at the same pixel depth as bullets and blockquote content with the drawn lines exactly under the cells.
  - **`TableDelimiterCollapser.cs`** — **the one place live preview touches view state rather than only rendering**: it collapses the delimiter row's line via `TextView.CollapseLines` (a zero-size element alone leaves a full-height blank band). Its class and member comments carry the full reasoning — read them before touching it. The rules that have each crashed once:
    - **The span and the collapse are two halves of one operation.** The header row's element must run to the delimiter line's `EndOffset` *and* that line must be collapsed; either alone either throws `"Trying to build visual line from collapsed line"` or leaves the gap.
    - **The generator spans off `TableDelimiterCollapser.IsCollapsed` (the applied set), never by re-deriving `TryGetRenderedTable`** — and anything that can stop a table rendering (caret move, edit, live-preview toggle) must `Refresh()` **synchronously**. Only the bootstrap refresh is posted.
    - **Every change to the collapsed set is followed by `TextView.Redraw()`** — cached `VisualLine`s aren't invalidated by `CollapseLines`.
    - **Constructed right after `InitializeComponent()`, before `ApplyEditorPreferences()`**, which reaches it via `ResetLivePreviewCaretTracking`. None of these failures is reachable from the test suite.
    - **`Reset()` is called from `ResetLivePreviewCaretTracking`** because a replaced document leaves the tracked sections pointing at lines that are gone. `CollapsedLineSection.Uncollapse` does nothing when already uncollapsed, so a section whose lines were deleted underneath it needs no special handling.
  - **`TableGridRenderer.cs`** — the `IBackgroundRenderer` half of table rendering: header shading, a horizontal line at every row-band edge, and vertical column lines as continuous strokes across the table's visible lines — the same generator/renderer split as blockquotes, for the same reason. Like all three pairs (see the shared-gate bullet above), it holds a reference to the `TableRowElementGenerator` and asks `TryGetRenderedTable` per visible line, so the reveal decision and the column geometry can't diverge between the drawn grid and the row elements — including drawing nothing over a revealed (raw) table.
- **`Resources/Markdown.xshd`** — the XSHD grammar for *inline* Markdown highlighting (bold/italic/strikethrough/highlight/inline code/links/images/fenced code blocks/HTML comments/list markers). Embedded as a resource and loaded via `Assembly.GetManifestResourceStream("MDEdit.Resources.Markdown.xshd")` from `MarkdownHighlighting.Build`. **Its `<Color>` elements carry no visual attributes at all — names only** (§6): every colour, weight, style, decoration, family and size is written onto them at load time from `EditorPreferences`. That is required for "inherit" to mean inherit — `Build` clears each property before applying the user's style, so a value left in the file would be either dead weight or, if the clearing were ever removed, a value silently resurfacing for an element the user had explicitly cleared. `MarkdownXshdTests.MarkdownXshd_DeclaresNoVisualAttributes` pins it, since a re-added attribute would read as configuration while changing nothing. Comments in the file note deliberate regex constraints ("no wildcard quantifiers", "min 2 chars") tuned to avoid catastrophic backtracking and crashes in AvalonEdit's regex engine — preserve that style when editing rules.
  - Bold and Italic are `<Span>` elements rather than flat `<Rule>`s specifically so a nested `<Rule>` inside each can recognize the *opposite* delimiter family wrapped inside it (`**_text_**`, `_**text**_`) and colour it `BoldItalic` explicitly — not `Italic`/`Bold` alone, which would risk the nested match's colour overriding rather than combining with the outer span's weight/style. Flat same-family nesting (`**text**` inside `**text**`) is unsupported and out of scope: CommonMark itself requires mixing delimiter families to nest emphasis unambiguously, so this covers the real cases. `MarkdownXshdTests.MarkdownXshd_LoadsWithoutError` loads the file through the real `HighlightingLoader`, not just a build-time XML check, so a malformed grammar fails `dotnet test` rather than surfacing only when a `.md` file is opened.
  - Emphasis matching is single-line only — `<Rule>` elements and the content-class patterns cannot cross line breaks; only `<Span>` supports `multiline="true"` (used for fenced code blocks and HTML comments). Making bold/italic span lines would mean converting them to multiline Spans and making `MarkdownLineColorizer` and the marker generators aware of spans starting on one line and ending on another (they are strictly per-`DocumentLine`) — materially bigger than the mixed-nesting fix, not yet done.
  - Highlighting is swapped by file extension in `UpdateHighlighting(path)`: `.md`/`.markdown` get the Markdown XSHD, anything else (including `.txt`) gets none, per §4.
- **`Resources/AppIcon.ico` / `AppIcon.png`** — both `<Resource>` items (WPF pack-URI-resolvable, distinct from the `EmbeddedResource` used for the XSHD grammar). The `.ico` (multi-res, generated from the `.png`) drives `<ApplicationIcon>` and MainWindow's titlebar icon; the `.png` is used only in `AboutWindow`, for the reason noted there.
- **`Resources/ToolbarIcons.xaml`** — toolbar icon geometry (§8), a plain `ResourceDictionary` of `Geometry` resources from Tabler Icons' outline set (tabler.io/icons, MIT) — stroke geometry in a 24x24 viewBox, not filled silhouettes, which is why `MainWindow.xaml`'s implicit `Path` style in `ToolBar.Resources` sets `Stroke`/`StrokeThickness="2"`/round line caps rather than `Fill`, matching the source SVGs. No csproj entry needed: as with `Themes/*.xaml`, the SDK's default glob treats every `.xaml` as a `Page`. Merged once into `App.xaml`'s `MergedDictionaries` alongside the theme dictionary but — unlike it — never touched by `ThemeService.Apply`'s swap, which only matches sources named `Themes/Light.xaml`/`Dark.xaml`; icon geometry is theme-independent, only the `Stroke` brush (`DynamicResource AppChromeForegroundBrush`) changes with theme.
  - Every formatting toolbar button renders one of these instead of the `TextBlock` label it used to, including the WYSIWYG/Source `ToggleButton` — whose `Path.Data` and `ToolTip` are set imperatively in `UpdateLivePreviewState()` rather than by a XAML trigger, matching how this button's checked state is already synced from code-behind. They deliberately show the mode a click would switch *to*, not the current one: `IconEye` + "Toggle to WYSIWYG view" while in Source, `IconEyeClosed` + "Toggle to code view" while in WYSIWYG — a closed eye reads more clearly than reusing the Inline Code button's `</>` glyph for an unrelated purpose on the same toolbar, which is what shipped first and was corrected.
  - Highlight's icon uses the default `AppChromeForegroundBrush` stroke like every other icon — it briefly pinned its own yellow accent the way its old swatch `TextBlock` did, but that read as inconsistent once every button was an outline icon rather than a filled letter. What the old swatch's colour *did* carry over is the swatch itself: the icon sits inside a small `Border` (`x:Name="BtnHighlightSwatch"`) whose `Background` is set imperatively in `ApplyTheme()` from `EditorPreferences.HighlightBackgroundLight`/`Dark` — not a fixed colour — so it always matches what the user picked in Preferences. It updates live on both a theme switch and a Preferences change, since `ApplyEditorPreferences` calls `ApplyTheme()` at the end of every run; this is the imperative-property-push pattern the colorizer's brushes use, not a `DynamicResource`, since `EditorPreferences` values are settings data rather than static theme-dictionary entries.
  - The WYSIWYG toggle also pins `Background`/`BorderBrush` to `Transparent` as local values, specifically to beat the Fluent theme's default `IsChecked` accent fill (`Application.ThemeMode` otherwise paints a checked `ToggleButton` with the OS accent colour — purple on the machine this was found on): a local value outranks the theme's trigger/visual-state value in WPF's property precedence, so this works without touching the Fluent template. `IconSettings` is the toolbar's trailing entry in its own final section, its `Button` reusing `MenuPreferences_Click` directly rather than a wrapper, the two being meant as identical actions reached from two places.
- **`Resources/SearchPanelStyle.xaml`** — the Find panel's illegibility fix, and a real multi-cause bug worth understanding before touching this area: three independent problems stacked, each masking confirmation that the previous fix had worked. It is a full `Style`+`ControlTemplate` override for AvalonEdit's `SearchPanel` *and* its `DropDownButton`, replacing the fixed `SystemColors`/hardcoded PNG icons of AvalonEdit's default template (none of which track this app's theme) with the app's own look; the built-in Prev/Next `Image` controls became the same Stroke-`Geometry`-`Path` convention `ToolbarIcons.xaml` uses. Only two named parts are load-bearing (`PART_searchTextBox`, `PART_dropdownPopup`, per `SearchPanel.OnApplyTemplate`); everything else was free to restyle, and everything themed got an `x:Name` for the reason below. Merged once in `App.xaml`.
  1. **`DynamicResource` doesn't reliably resolve inside this template.** The colors written in this XAML are a fallback, not what works. **The real fix is `MainWindow.ApplySearchPanelColors()`**: it resolves each brush once via `this.FindResource(...)` (from `MainWindow`, properly connected to `Application.Resources`) and assigns it as a local value via `Template.FindName` — the "resolve from a properly-connected element, then push as a local value" pattern `BtnHighlightSwatch` and the colorizer's brushes already use.
  2. **Calling that push once, right after `SearchPanel.Install`, wasn't enough — confirmed live, not inferred:** a temporary diagnostic (a one-time `MessageBox` dumping `Style`/`Template`, whether named parts resolved, the resolved brush values, and `Application.Resources.MergedDictionaries`) showed everything *already correct* at that point, yet the icons still rendered blank. Cause: `SearchPanel.Open()`/`Close()` add and remove the panel's adorner from the `TextArea`'s `AdornerLayer` on demand — `layer.Add(adorner)` happens only inside `Open()`, and `IsClosed = true` (the default, set at the end of `AttachInternal`) means the adorner isn't in the layer at all until the user's first Ctrl+F. Anything pushed before that (window `Loaded` and `ContentRendered` were both tried) doesn't survive the adorner's later first real connection. **The fix is `_searchPanel.IsVisibleChanged`**, which fires on every actual `Open()`/`Close()`, so colors are re-pushed onto the panel that's about to render. (The separate `ApplyTheme()` call site still matters, for a theme switch while Find is open.)
  3. **Even with correct, high-contrast colors confirmed live**, the Prev/Next/Close buttons still rendered with no visible border and no visible icon except on hover. Cause: Fluent's default `Button` template doesn't paint its `ContentPresenter` in the resting state at all — a reveal-on-hover design with nothing to do with colour. `DropDownButton`'s arrow stayed visible throughout the investigation for exactly one reason: it already had a fully custom `ControlTemplate`, never relying on Fluent's default. **The fix is `ChromeFlatButtonStyle`**, a plain `Border`+`ContentPresenter` template with no Fluent involvement, applied to all three buttons. It was named `SearchPanelFlatButtonStyle` until the status bar's zoom buttons (§6) hit the identical problem and reused it — this dictionary is merged in `App.xaml`, so the key resolves from `MainWindow.xaml` with no extra plumbing. **Any new button on the app chrome needs it**; Fluent's default renders it invisible until hovered.
     - **The style also carries `Background`/`BorderBrush`/`Foreground` defaults, and that is a fix, not tidiness.** It originally declared only the template, whose `TemplateBinding`s therefore resolved against Fluent's own `Button` defaults — fine for the search panel, whose buttons get real values pushed as *local* values, but the zoom buttons set nothing and rendered unthemed. Adding Setters fixes every future chrome button at the root and cannot disturb the search panel, since a local value outranks a style setter. **This is the third time Fluent's defaults have won simply by being the only value present**, after the checked `ToggleButton`'s accent fill and the invisible resting-state content this template exists to fix — when a chrome control looks wrong under theming, check whether anything is setting the property at all before hunting for a resource-resolution problem.
  - `SearchPanelStyleTests` checks that every named part resolves via `Template.FindName` — a typo wouldn't throw, `ApplySearchPanelColors` would just silently skip that element — but by design it can't catch causes 2 or 3: both manifest only in an actually-shown, actually-*opened* window with a real Fluent theme applied, which no headless test here constructs. Diagnosing those took shipping temporary, self-removing `MessageBox` diagnostics and iterating with a person running the app — the standing rule that this project's code isn't launched or driven for verification held throughout; a live diagnostic report from the user running it themselves is what the rule leaves room for.

Both halves fall back to the SDK default rather than failing the build when git or the file is unavailable. An `<AssemblyMetadata Include="BuildDate">` item stamps the current UTC time on every build, needed because deterministic builds (the SDK default) zero the PE header timestamp that used to serve this. Three `<Content>` items ship files beside the exe: `samples\**\*.md`, plus `..\THIRD-PARTY-NOTICES.md` and `..\LICENSE` linked as `LICENSE.txt` — see the licensing paragraph under **Project** for why those are an obligation and why `Link=` matters.

It runs `attrib -R` on `$(OutDir)samples\*.md` — not the `Attrib` MSBuild task, which isn't registered in the .NET SDK's default task set — and is hung on `BeforeTargets="_CopyOutOfDateSourceItemsToOutputDirectory"`, the specific target performing that copy (confirmed with `dotnet build -v:n`), because neither `BeforeTargets="Build"` nor `"CopyFilesToOutputDirectory"` runs early enough: `Build` has no tasks of its own, so a hook on it fires only after its whole dependency chain, including the real copy, has completed. A real ClickOnce install never hits this, every published version landing in a brand-new folder.

### Live-preview constructs

Each construct's generator makes two independent choices: **reveal scope** (how much of the document has to contain the caret before the raw syntax comes back) and **replacement** (what gets rendered where the hidden characters were). In every case the characters still occupy their document offsets — selection, undo, and the saved file are unaffected; only rendering changes.

| Construct | Generator | Reveal scope | Replacement |
| --- | --- | --- | --- |
| Heading | `HeadingMarkerElementGenerator` | per-line | zero-size hide (`"# "` prefix) |
| Emphasis, highlight | `EmphasisMarkerElementGenerator` | per-span | zero-size hide (symmetric marker) |
| Link | `LinkMarkerElementGenerator` | per-span | zero-size hide (asymmetric prefix + suffix) — also handles reference-form and unresolvable images, and every remote image while View → Load Remote Images is off, i.e. every span `ImageElementGenerator` declines |
| Image | `ImageElementGenerator` | per-span | visible rendered element (the picture, natural size clamped by `MaxImageHeight`; drawn broken-image placeholder + alt text on load failure; loading placeholder while a remote fetch is in flight; unresolvable — and every remote image while the opt-in is off — declines to `LinkMarkerElementGenerator`) |
| Underline | `UnderlineMarkerElementGenerator` | per-span | zero-size hide (asymmetric `<u>` + `</u>`) |
| Emoji | `EmojiElementGenerator` | per-span | visible rendered element (the emoji character) |
| Code fence | `CodeBlockFenceElementGenerator` | per-block | zero-size hide (whole line) |
| Blockquote | `BlockquoteMarkerElementGenerator` | per-line | blank spacer, bar drawn by `BlockquoteAccentBarRenderer` |
| Bullet list | `BulletListMarkerElementGenerator` | per-line | visible rendered element ("•" glyph) |
| Task list | `TaskListMarkerElementGenerator` | per-line | visible **drawn** element (a checkbox, replacing bullet *and* box) |
| Numbered list | `NumberedListMarkerElementGenerator` | per-line | visible rendered element (same `"1. "` text, for indent only) |
| Table | `TableRowElementGenerator` | per-block | visible rendered element (whole line → fixed-width cells, each built from `MarkdownSyntax.FormatInline`'s styled runs so inline constructs render inside them; delimiter row hidden; grid drawn by `TableGridRenderer`) |
| Horizontal rule | `HorizontalRuleElementGenerator` | per-line | whole-line zero-size hide; line drawn by `HorizontalRuleRenderer` |

**Image rendering (§5) was scoped in two phases, both now done** — local images (`ImageElementGenerator` + `ImagePathResolver`), then remote `http(s)://` images behind an opt-in (`RemoteImageLoader`):

- It was the first inline element that isn't text-sized: the containing line grows to fit the picture, which works because AvalonEdit measures inline objects with an *infinite* constraint and `InlineObjectRun` reports the object's height as its baseline — so `MaxHeight` on the WPF `Image` (`MaxImageHeight`, 300px) is the sizing clamp, natural size below it, and no line-height API is involved. A wide image doesn't word-wrap (no inline object can — same as a table row); the raw text is always reachable via the caret reveal.
- **The decline-vs-placeholder contract** is the rule everything follows: `ImageElementGenerator` *declines* a span (falling through to `LinkMarkerElementGenerator`'s marker-hiding, exactly the pre-image rendering) whenever the target isn't its to render — any `scheme://` URL including `file://`, a relative path with no document directory (an unsaved document's image is *unresolvable*, not missing — it may become right the moment the user saves), or an unparseable path. The drawn broken-image placeholder (Border + Polyline shapes per the task-list-checkbox precedent, alt text beside the icon, styled from `GlobalTextRunProperties` so it needs no theme wiring) is reserved for a genuinely *resolved* local path that failed to load.
- The two generators coordinate by **registration order, which is load-bearing**: `_imageGenerator` is registered immediately before `_linkMarkerGenerator` (both advertise an image span's `Start`; AvalonEdit breaks the tie by registration order), a rendered image consumes the whole `[Start, End)` span so the link generator never sees inside it, and a declined span falls through with zero changes needed in `LinkMarkerElementGenerator`.
- `FindLinkSpans` carries `IsImage` + `Url` on `LinkSpan` (the `EmojiSpan` carry-the-payload precedent; `Url` is null for reference links, never rendered as images). `LinkPatterns` became the `EmphasisPatterns`-style tuple table to carry the flag.
- Decoded bitmaps are cached by resolved full path and frozen (shareable across visual lines — a fresh `Image` element per `ConstructElement` call is mandatory, since `TextView` takes inline objects as visual children). The cache is deliberately **not** `TextDocument.Version`-keyed like the table layout cache, which would re-decode every image on every keystroke; it clears only when `DocumentDirectory` changes, which is also how cached failures (null entries, so a missing file isn't re-probed per redraw) recover. Known v1 limitation: an image edited on disk won't refresh until a different document is opened. Oversized sources get `DecodePixelHeight = DecodeHeightCap` (2× the display clamp), applied only when the source is taller, since unconditional decode-scaling would upscale small images.
- The document-path feed is the **sixth MainWindow wiring touchpoint** and the first generator fed anything from `FileService`: `UpdateHighlighting(path)`, already the single funnel for every path change, sets `_imageGenerator.DocumentDirectory` under a change-guard and forces a full `TextView.Redraw()` when it actually changed. The redraw is required, not defensive: Save As gives an unsaved document's relative images a base directory, and nothing else repaints then (verified — `ExecuteSaveAs` triggers no redraw when the extension didn't change).
- The colorizer needed nothing: revealed raw `![alt](path)` already gets the per-span mono-font swap because `ApplyRevealedSourceFont` consumes the same `FindLinkSpans`, and a rendered span has no visible text left to style.
- **Remote images are gated on `AppSettings.LoadRemoteImages` (View → Load Remote Images), off by default** — the explicit product call phase 2 was waiting on, since fetching a remote URL just from having the document open discloses to its host that it was opened (the tracking-pixel concern email clients guard against). The setting is **top-level, deliberately not in `EditorPreferences`** — the rule under `Services/SettingsService.cs`; a privacy setting must not be revertible by a dialog that never showed it. The menu item carries the rationale in a `ToolTip`, the only place it reaches the user.
- **The guarantee the design is built around: with the opt-in off, MDEdit issues no network request of any kind for a document's content** — structural, not a runtime check. `HttpClient` appears only in `RemoteImageLoader.cs`, that class is instantiated once (target-typed `= new()` in `ImageElementGenerator` — grep the bare type name), and `GetOrStartFetch` has one call site behind the single `RemoteEnabled` gate in `IsRenderable`. **Don't add a second gate, a second instance, or a second `HttpClient` user.** `RemoteImageLoader`'s class comment carries the full argument plus the threading rules (`ConfigureAwait(false)`, UI-thread-only cache mutation, coalesced `Background`-priority redraw) and the network hygiene (static client, no cookies/credentials, honest User-Agent, streamed byte cap) — read it before touching the class.
- Late arrivals redraw via an `Action` MainWindow pushes (`_imageGenerator.RequestRedraw`), full-view because the loader is URL-keyed. `Invalidate()` (generation counter + cancellation) is called from `LoadRemoteImages` (both directions) and `DocumentDirectory` only — **deliberately not** from the live-preview `Enabled` setter or on edits, either of which would refetch constantly. Placeholder design and rejected alternatives (spinner, "Loading…" text) are in `ImageElementGenerator`.

Reveal scope drives the redraw work in `OnCaretPositionChanged`: per-line and per-span need only the old and new caret line redrawn (span-grained constructs additionally need `_lastCaretOffset`, since a caret move within one line can cross a span boundary), while per-block is the one scope whose reveal region can sit far outside those two lines — hence `RedrawEnclosingFenceLines` and `RedrawEnclosingTableLines`.

**Adding another construct** — the established order of work:

1. Add detection to `Editing/MarkdownSyntax.cs` first, and unit-test it there. Never re-implement detection inside a generator or the colorizer.
2. Pick a reveal scope and replacement from the table above, matching an existing construct wherever the new one behaves the same way.
3. Write the generator in `Editing/` as a `VisualLineElementGenerator` with an `Enabled` flag and caret state, modeled on the closest existing one.
4. Register it on `TextView.ElementGenerators` in `MainWindow`. **Registration order is load-bearing whenever two generators can advertise the same offset** — AvalonEdit breaks that tie by order alone, so the one that may *consume* the span comes first and the fall-through second, and neither can tell the other exists. `_imageGenerator` before `_linkMarkerGenerator` is the worked example (a rendered image swallows the whole span; a declined one falls through to marker hiding), with a comment at the registration site saying so. A construct whose offsets can't overlap anything else's can be registered anywhere.
5. Flip its `Enabled` in `UpdateLivePreviewState()`.
6. Re-sync its caret state in `ResetLivePreviewCaretTracking()` — otherwise it renders against a stale caret after New/Open.
7. Update `OnCaretPositionChanged` only if the scope isn't line-local; a per-block construct needs its own enclosing-region redraw the way fences do.
8. If the construct needs colour/weight/size rather than just marker hiding, that half belongs in `MarkdownLineColorizer`, consuming the same `MarkdownSyntax` method.

**The extended-syntax constructs** — how each maps onto the shapes above. All of them fit, except tables:

- **Highlight** (`==text==`) confirmed the prediction: adding `(new Regex(@"\G={2}[^=\n]+={2}"), 2, true)` to `EmphasisPatterns` gave it per-span marker hiding through the existing `EmphasisMarkerElementGenerator` for free, and a `Highlight` colour + rule in `Markdown.xshd` (plus a `DarkHighlightColors` entry) gave it the background. No new generator, no caret/redraw wiring. **Prefer this route for any remaining symmetric inline marker** — a new generator is the wrong instinct there.
- **Superscript and subscript** (`X^2^`, `H~2~O`) took the same free ride plus one addition: they needed the colorizer to style a *span* rather than a whole line, which it had never done. That required telling runs apart, and `MarkerLength` can't — `^`/`~` are one character, exactly like italic's `_`. Hence `EmphasisKind` on the pattern table and `FindScriptSpans`, which **shares `FindEmphasisSpans`' single scan** (both project from `ScanLine`) rather than re-parsing, so the baseline styling and the marker hiding can't disagree. The `~` vs `~~` collision is handled purely by pattern order — subscript sits *below* strikethrough in `EmphasisPatterns`, and moving it would silently break strikethrough, so `MarkdownSyntaxScriptTests` pins that.
- **Task lists** are a variant of the bullet-list generator — per-line reveal, visible rendered element. Three non-obvious things:
  - `TryGetTaskListMarker` bounds the bullet character *through* the closing `]` (all five characters of `- [ ]`), and the generator replaces that whole range with **one** checkbox glyph. `BulletListMarkerElementGenerator` therefore has to check for a task and return −1, or a task line renders "• ☐ todo" — two markers for one construct. A task line genuinely *is* a bullet line, so the exclusion belongs in the generator, not in `TryGetBulletListMarker`.
  - **The checkbox is drawn (a `Border` plus a `Polyline` tick), not a glyph — don't "simplify" it back.** U+2610/U+2611 (☐/☑) were the first attempt and looked wrong: the editor font carries neither, so WPF font fallback resolved each character independently and the two states came out visibly different sizes. Drawing makes both identical by construction, removes the dependency on any font having the glyphs, and still scales with `FontRenderingEmSize` and follows the theme's foreground brush. This is the only generator drawing shapes rather than hosting text; the reason is glyph availability, not preference.
  - The command is the first three-way one: `MarkdownFormatter.TaskListItem` toggles an existing task, adds `[ ] ` to a plain bullet (inserting the full prefix would give `- [ ] - foo`), and otherwise inserts `- [ ] `. Being a document mutation it lives in `MarkdownFormatter`, not the generator.
- **Emoji** was the first generator to pair *per-span* reveal with a *visible* replacement — the other visible-replacement generators are all per-line. Three things easy to re-litigate by accident:
  - **The catalogue is what makes detection safe.** The BCL has no shortcode table, so one ships as an embedded `Resources/Emoji.txt` (curated ~240 entries, not the full ~1,800 — everything here is versioned in git and carried in the ClickOnce payload; extending it is a data edit, and no code depends on the size). Because only catalogued names count, `10:30:45` and `3:4:5` can never be mistaken for emoji — a stronger guarantee than the pattern-only constructs get, so **don't "simplify" this into a bare regex**.
  - **Emoji render monochrome, not in colour**, verified in this app: WPF's text stack has no COLR/CPAL colour-font support. A platform limit, not a bug to keep re-investigating; colour would need an image-based rendering route entirely. Documented in §5 so users aren't surprised.
  - `FindEmojiSpans` skips only inline code (a shortcode in backticks is literal); it deliberately does *not* skip emphasis or links, so `**:joy:**` still renders — the same container reasoning as `FindUnderlineSpans`. `InlineCodePattern` is shared with `EmphasisPatterns` rather than duplicated, and **must stay declared above it**: static fields initialize in declaration order, so moving it below leaves the emphasis table holding a null regex at runtime, not merely a warning.
- **The emoji picker** needed no new generator — a catalogue feature, not a rendering one. `EmojiCatalog` gained `All`, an ordered `IReadOnlyList<(string Shortcode, string Emoji)>` built in the same `Load()` pass as the lookup dictionary (not a projection of `Dictionary` enumeration order, which isn't a documented guarantee); `TryGet`/`Count` are unchanged. See the `EmojiPickerWindow` bullet in Architecture for the window itself. `MainWindow.BtnEmoji_Click` inserts the pick via `MarkdownFormatter.InsertEmoji`, which replaces any existing selection outright (the `Table`/`CodeBlock` shape, not `Wrap`'s fold-in-place one) and leaves the caret right after the shortcode, matching where it would land had the user typed it.
- **Convert emoji to shortcodes (§3)** was likewise a catalogue feature. `EmojiCatalog.TryGetShortcode` is the **reverse** map, and is not the forward one inverted: aliases collide (`+1` and `thumbsup` both give 👍, `-1` and `thumbsdown` both 👎), so **first-listed-in-file wins** — `Emoji.txt` is hand-ordered with the preferred name first, so reordering the file is how you change the answer, and no second list encodes the preference. It's built from the ordered list *after* the forward pass, so a shortcode redefined later contributes its final emoji.
  - **`MarkdownSyntax.FindEmojiCharacterSpans` is the detection half** — the mirror of `FindEmojiSpans`, skipping inline code for the same reason. **Longest match wins at each position**, because a variation-selector form (❤️) has its bare base character (❤) as a prefix and shortest-first would strand the selector. `EmojiCatalog.CouldStartEmoji` rejects positions in O(1) first, since otherwise the scan builds a substring per candidate length at *every* character of the document.
  - **`MarkdownFormatter.ConvertEmojiToShortcodes` is the first operation here that rewrites content** rather than adding or removing syntax. Replacements are collected first and applied **last-to-first**, since a shortcode is longer than the character it replaces and a forward pass would invalidate every subsequent offset; the whole run sits inside one `doc.RunUpdate()`, so one Ctrl+Z undoes it rather than hundreds.
  - **Fenced blocks are skipped in the formatter, not the scanner**, because whether a line is inside one is a document-wide property no line-local scan can see. It checks the O(1) `IsFenceDelimiterLine` before the document-walking `TryGetEnclosingFenceBlock` and then skips to the block's end, so each block costs one walk rather than one per line inside it.
  - **Menu-only, no toolbar button** (Format → Convert Emoji to Shortcodes): it rewrites existing content rather than inserting syntax at the cursor, so it doesn't belong among the toolbar's one-shot insert commands. The command is idempotent, pinned by a test — a second run must find nothing left to convert.
  - **The automatic form is `AppSettings.ConvertEmojiOnSave` (View → Convert Emoji on Save, §1), off by default and calling the *same* command.** `ConvertEmojiOnSaveIfEnabled` runs from both `ExecuteSave` and `ExecuteSaveAs` immediately before the document text is read — in Save As *after* the dialog, so cancelling leaves the document untouched — and always passes a zero-length range, i.e. the whole document regardless of selection: an automatic pass has no reason to respect what happens to be highlighted. Routing through the one command is what stops the manual and automatic forms diverging. **Top-level, not in `EditorPreferences`** — the rule under `Services/SettingsService.cs`; a setting that edits document content must not be revertible by a dialog that never showed it. **Off by default is a data-integrity invariant, not a taste call**, with its own named test beside `LoadRemoteImages`'s. Undo behaviour is a consequence rather than a bug: the conversion is one `RunUpdate` step, so Ctrl+Z reverses it and leaves the document dirty again — honest, since the file on disk really does differ from the buffer. It sits in **View** with the other persisted toggles despite not being a view option, chosen over pairing it with the Format command; the menu is where every other toggle in this app lives.
- **Underline is the odd one: it is not Markdown at all.** Markdown has no underline syntax in any dialect (underlining being reserved for links by convention), so §3 specs it as literal inline HTML — `<u>text</u>` — riding on Markdown's pass-through of inline HTML. It is the only formatting command that emits HTML. Its markers are **asymmetric** (`<u>` is 3 characters, `</u>` is 4), so `EmphasisSpan`'s symmetric `MarkerLength` can't describe it and the `EmphasisPatterns` free ride was unavailable: it needed `UnderlineSpan` (mirroring `LinkSpan`'s four offsets), `FindUnderlineSpans`, and `UnderlineMarkerElementGenerator` on `LinkMarkerElementGenerator`'s template, plus the full five-touchpoint MainWindow wiring. The underline *effect* is a one-line XSHD `<Color underline="true">` — `XshdColor.Underline` is supported, and `MarkdownXshdTests` proves the grammar still loads. Deliberately strict: lowercase `<u>` only, no attributes, no whitespace in the tag, and the content class stops at `<` so a nested tag ends the run — this editor does not parse HTML, and anything looser starts guessing.
  - Unlike the emphasis and link scanners, which skip past each other's matches, `FindUnderlineSpans` is **not** skip-aware and shouldn't be: underline is a *container*, not an opaque run, so `<u>**bold**</u>` is meant to keep its bold. Both scanners find their own runs independently, and their markers never share an offset, so the generators can't collide. Verified by tests in both directions.
- **Tables were the one construct that genuinely didn't fit the existing shapes** — a grid's column widths depend on every row, so the layout is a whole-table property rather than line- or span-local. The solution: `MarkdownSyntax` table detection, `TableRowElementGenerator` + `TableGridRenderer` (the blockquote generator/renderer split applied a second time), and pipe/delimiter dimming in `MarkdownLineColorizer` reusing the hrule element's resolved colour. **Deliberately no XSHD rule**: XSHD matching is line-local and can't know whether a `|` line has a matching delimiter below it, so an XSHD table rule would colour row-shaped prose — the same reason headings/blockquotes/hrules are colorizer-styled. Three v1 boundaries are deliberate:
  - **Inline formatting inside cells renders** (§5); cell text used to be verbatim. The row element consumes the whole line, so the inline generators never run there and `TableRowElementGenerator` does that work itself via **`MarkdownSyntax.FormatInline(string)`**, string-based because a cell is a substring of a line with no document offset. It reuses the very scanners the line-based entry points do (`FindLinkSpans`/`FindUnderlineSpans`/`FindEmojiSpans` were split into `ScanLinks`/`ScanUnderlines`/`ScanEmoji` string cores for exactly this), which stops a cell disagreeing with identical text written outside a table. It returns `InlineRun(Text, InlineStyles)` — a **flags** enum, because the constructs compose — with markers removed and emoji substituted; nesting composes free, since the emphasis scan reports nested runs flat and each ORs its style over its own content range. **Both measurement and rendering must go through those runs**: measuring raw text while displaying marker-free text misaligns every column by the width of the hidden markers, which is precisely why this couldn't be done before. `ComputeLayout` sums a `FormattedText` per run (one typeface each — bold and code are wider), `BuildRow` builds `TextBlock.Inlines`, and `FormatFor` produces the visual properties for both, so a column can never be measured against a typeface it doesn't render with.
    - **Styles are read through `MarkdownLineColorizer.Resolve`** via a constructor-supplied reference — the arrangement the two renderers use, for the same reason: only the colorizer knows which editor mode is live. That makes this the third class needing `_colorizer`, so like the other two it is **built in `MainWindow`'s constructor, not a field initializer** (C# forbids one field initializer referencing another), and must be constructed *before* `_tableGridRenderer`, which takes it.
    - **`MarkdownLineColorizer.StyleGeneration` exists for this and is deliberately pulled, not pushed.** Column widths depend on resolved element styles, so retuning the code font in Preferences moves every measured width **without touching the document or the base font** that the layout cache's other two keys watch. The counter bumps wherever the colorizer drops its own resolved cache, and the generator compares it as a third cache key. A push from `ApplyActiveModeStyles` would be one more thing to remember at every restyling site, and forgetting it would surface only as subtly misaligned columns.
    - **Bold+italic layers as the `boldItalic` element, not Bold then Italic** — that element exists precisely so the pair styles as one thing, and layering would let Italic's weight override Bold's. Decorations are **unioned** rather than replaced: `ElementStyle` has a single `Decoration` field because *AvalonEdit* cannot render underline and strikethrough together, but a WPF `Run` has no such limit, so a struck hyperlink in a cell shows both cues.
    - **Two deliberate boundaries**, pinned by tests: an **image renders as its alt text**, not a picture (a decoded bitmap inside a fixed-width measured cell is a separate problem, and alt text is a description rather than a link, so it carries no link styling); and **backslash escapes keep their visible backslash**, matching how they render everywhere else — hiding it is a whole-editor change, not a table one.
  - **Reveal is whole-table.** Per-row Typora-style reveal was considered and deferred: with the rest of the table still rendered while one row is edited, every keystroke changes a column max-width and forces a whole-block redraw, and the raw row's text can't line up with the rendered columns anyway.
  - **A row wider than the viewport doesn't word-wrap** — a single inline object can't. The raw text is always reachable via the per-block reveal.
  - The insert-table *command* (§3) is independent of all of this — `MarkdownFormatter.Table` plus a Format-menu entry and a toolbar button (no keyboard shortcut, matching Link/Code Block/Code — none of the toolbar's insert commands have one), following the insert-and-position-caret convention: a 2-column, 3-body-row starter with "Header 1" selected for immediate typing, the placeholder-selection idiom `Link`'s "link text" uses. One addition beyond that precedent: since `IsTableRowLine` requires each row to start at column 0, `Table` normalizes onto its own lines — a leading newline when the cursor isn't at the start of its line, a trailing one when it isn't at the end — so the table renders correctly regardless of where the cursor was. `CodeBlock` has the same latent limitation and was deliberately left as-is; normalizing there too is out of scope.

## Git workflow

- Before running `git commit` (and before `git push`), show the proposed commit message and wait for explicit confirmation — do not commit or push on the same turn as drafting the message without that check-in. Exception: once the user has given an explicit go-ahead (supplied the commit message themselves, or said "commit and push"), that covers the rest of that task, including incidental fixes needed to complete it (e.g. a build error hit mid-publish) — don't stop to re-confirm those, just use a reasonable one-line message and proceed. Only a genuinely new or separate change needs fresh confirmation.
- Commit messages are one line only, unless the change genuinely warrants a body.

## Conventions

- Nullable reference types are enabled; keep new code nullable-aware.
- File-scoped namespaces (`namespace MDEdit;`) are used throughout.
- Keep formatting-insertion behavior consistent with the "wrap selection / insert-and-position-caret" pattern already established for existing commands.
