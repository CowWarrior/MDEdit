**This file is large and deliberately stays one file — don't propose splitting it into nested
`CLAUDE.md` files to save context.** That was measured on 2026-07-31 against the previous 12
sessions: `MDEdit/` and `MDEdit/Resources/` were touched in **100%** of them, `MDEdit/Services/` in
83%, `MDEdit/Editing/` in 67%. A nested file loads as soon as any file under its directory is
touched, so in this repo it would load anyway almost every session and save nothing while making the
content harder to find. Extracting a genuinely separate, occasional *task* is different and does
work — see the `publish-clickonce` skill. Content also isn't padding: it's mostly gotchas, rejected
alternatives, and design rationale that reading the code cannot reconstruct, which is exactly what
maintenance work needs.

## Project

MDEdit is a WPF desktop Markdown editor (.NET, `net10.0-windows`) built around the AvalonEdit text editor control. See `Requirements.md` for the full product spec (document management, editing, Markdown formatting commands, syntax highlighting, keyboard shortcuts, toolbar, status bar).

**Line-based commands operate on every line a selection touches** — `ToggleLinePrefix` (bullet/numbered/blockquote), `TaskListItem`, and `Heading` in `MarkdownFormatter`. Four things about that implementation are deliberate and easy to break:
- They iterate **line numbers, not offsets or `DocumentLine` references**, re-fetching each line inside the loop. That is only safe because none of these commands add or remove line breaks, so numbers stay valid across every edit; offsets do not. The loop runs **bottom-up** so an edit never shifts a line still to be visited.
- **Numbered lists have their own method, `NumberedList` — they cannot use `ToggleLinePrefix`.** That method applies one fixed string to every line, so `"1. "` came out as `1.` on all of them. `NumberedList` collects the target line numbers first and takes each marker from the target's *index*, so counting is independent of the bottom-up iteration; a line already numbered is renumbered in place rather than given a second marker. `MainWindow.BtnNumberList_Click` calls it directly — don't route it back through `InsertLinePrefix`.
- Multi-line selections **normalize rather than flip**: the prefix is removed only when *every* affected line already has it, otherwise it's added to the ones that lack it — so a mixed block becomes uniform and a second press clears it. `TaskListItem` follows the same rule and cycles plain → all unchecked → all checked. Per-line flipping would leave a mixed block permanently mixed.
- Blank lines inside a multi-line selection are skipped, but the **single-line paths deliberately don't skip them** — inserting `- ` on an empty line is how a list gets started.
- Each multi-line command wraps its edits in `doc.RunUpdate()`, which groups them into **one undo action**; without it a three-line change would take three Ctrl+Z presses. `SelectedLineNumbers` also excludes a line the selection merely ends *at* the start of, matching what the user sees highlighted.

A few things are still spec'd in Requirements.md as *(planned)* — **not yet implemented, and not bugs**: a §3 **convert-emoji-to-shortcodes** command (catalogue work, needs no new generator — see below), rendering inline formatting inside WYSIWYG table cells (§5), a §2 **Find and Replace** command (Ctrl+H — check `ReleaseConflictingEditorGestures` first, as with any new Ctrl gesture; **the matching half already exists and shouldn't be rebuilt**: AvalonEdit's `ISearchStrategy.FindAll` and `ISearchResult.ReplaceWith` are public API, and `SearchPanel` itself is find-only, so what's missing is UI, not search. That means the replace fields land in `Resources/SearchPanelStyle.xaml`'s `ControlTemplate` override, and every new named part needs adding to both `MainWindow.ApplySearchPanelColors` and `SearchPanelStyleTests` — which is the one automated check that a part name still resolves, since `Template.FindName` returns null silently rather than throwing. Note the spec requires Replace All to be **one undo step**, i.e. `doc.RunUpdate()`, the same grouping the multi-line formatting commands use. Worth knowing before starting: the theme-switch-closes-the-panel bug documented under Find below is unfixed, and any replace UI inherits it), a §6 **Zoom** command (must scale on top of `EditorPreferences`' base sizes rather than writing to them — the spec makes non-destructiveness explicit; check `ReleaseConflictingEditorGestures` before wiring Ctrl+= / Ctrl+- / Ctrl+0, since AvalonEdit claims several Ctrl gestures and silently swallows the ones it owns), and §11 **Markdown Conformance** (backslash escaping and the intraword-`_` flanking rule first, since those two silently misrender ordinary text; then setext headings, indented code blocks, autolinks, the remaining reference-link forms, and ATX closing sequences — see the gap inventory under `markdown-conformance-test.md` below). (Additional sample documents beyond `ReleaseNotes.md` were previously listed here and have been **dropped** as not worth building — don't reintroduce them.) **New Window (§1) was the most recently completed** — see the New Window bullet under `MainWindow.xaml.cs` in Architecture for why it launches a second *process* and what that costs. Per-element text styling (§6) came before it; its plan of record, including the decisions taken and the ones deliberately deferred, is `docs/plans/per-element-fonts.md` — note that `docs/` is the live GitHub Pages site, so that file is publicly served. Image rendering (§5) came before it — both phases, local and remote — and the emoji picker (§3) before that. Highlight `==text==` was the first *extended* construct to land, and is the worked example for the catalogue-only ones: it needed **no new generator at all**, only a pattern added to `EmphasisPatterns` plus an XSHD color/rule, because its shape is identical to the emphasis family's.

Two Markdown documents exist for this, in different projects because they serve different purposes:

- **`MDEdit/samples/ReleaseNotes.md`** — the product introduction, and the **user-facing changelog**: its "Recent changes" section is updated before every publish (see **Publishing a new version** under ClickOnce deployment below — this is a standing requirement, not a nicety), **one short entry per published release, never one per commit**, with each release's changes as a bullet list rather than one paragraph.
  - **It also carries "Known issues" and "Planned" sections, and both are standing maintenance, not one-offs** (added 2026-08-01 at the owner's request). Whenever a bug is found, fixed, or a planned feature ships, that section is updated in the same change — a stale known-issues list is worse than none, because it tells users a fixed bug is still broken and erodes trust in the rest of the page. **Known issues** lists defects a user would actually hit while writing, in plain language with a workaround where one exists; it is deliberately *not* the full CommonMark-gap list from this file (that would read as a catalogue of things MDEdit cannot do). **Planned** carries only items spec'd as *(planned)* in `Requirements.md` — never deferred or undecided work, since listing those commits you publicly to work that was parked on purpose. Undecided ideas have their own home: **`Requirements.md`'s unnumbered "Potential future directions" section**, which is explicitly not a commitment and must not be promoted into either Planned list until it has been decided and rewritten as a numbered requirement. Three categories, not two — *(planned)* is scoped and agreed, "potential" is neither.
  - **`README.md` duplicates both sections, and the two must be updated together — this was accepted knowingly, not overlooked.** A GitHub visitor evaluating MDEdit won't dig into `MDEdit/samples/`, and a README that hides what's broken behind a link is the weaker document; the cost is that these are now the only prose deliberately maintained in two places. Treat "edit `ReleaseNotes.md`'s known-issues or planned list" and "edit `README.md`'s" as one action. The wording differs slightly by audience (README addresses someone deciding whether to install; ReleaseNotes addresses someone who already did), so copy the *substance*, not the sentences. Deliberately written using only constructs MDEdit supports *today* so it renders correctly in WYSIWYG — no tables, task lists, or emoji. Keep it to what is *distinctive* about MDEdit: the greeting is a short "thanks for installing" line, not a feature tour — there is no usage/keyboard-shortcut/file-association walkthrough here, so don't reintroduce that kind of content when adding changelog entries. `MDEdit.csproj` ships it via `<Content Include="samples\**\*.md" CopyToOutputDirectory="PreserveNewest" />`, so it lands in `samples\` beside the exe and ClickOnce carries it in the payload, at `MainWindow.GetReleaseNotesPath()`'s `Path.Combine(AppContext.BaseDirectory, "samples", "ReleaseNotes.md")` — confirmed against a real ClickOnce publish log to land in the same relative place in the deployed version folder.

Requirements.md §10's first-run behavior is implemented: `MainWindow`'s constructor calls `MaybeShowReleaseNotesOnFirstRun()` whenever there's no file-association/command-line argument to open instead (that always wins — the `if (args.Length > 1) OpenFile(args[1]) else MaybeShowReleaseNotesOnFirstRun()` split). It shows the page once per **release**, comparing only `Major.Minor.Build` against `AppSettings.LastReleaseNotesVersionShown` via `Editing/ReleaseNotesGate.cs` (`GetReleaseVersion`/`ShouldShow`, unit-tested in `ReleaseNotesGateTests`) — deliberately never the full 4-part version or `Revision` alone, since per the versioning scheme above, `Revision` can repeat across different actual releases and would make the comparison unreliable in either direction. The "last shown" value is persisted *before* attempting to open the file, so a missing or unreadable `ReleaseNotes.md` fails silently exactly once per release rather than retrying on every launch forever. Help → Release Notes (`MenuOpenReleaseNotes_Click`) reaches it on demand, behaving exactly like File → Open (`CheckUnsavedChanges` guard, joins Recent Files, shows errors normally) — unlike the auto-open path, which passes `OpenFile`'s new `addToRecentFiles`/`showErrorOnFailure` parameters as `false` for both, since an automatic open on startup is not a user-initiated action and must neither clutter the MRU list nor pop an error dialog on first launch.

**The Save-As-instead-of-overwrite protection was deliberately rejected in favor of marking the installed file read-only via the OS attribute** (`MainWindow.EnsureReleaseNotesAreReadOnly`, called at both open sites, idempotent) — not the ClickOnce build/publish pipeline: whether attributes survive ClickOnce's deploy mechanism (which renames payload files to `*.deploy` and reconstructs them on the client) is unverified and not worth depending on, whereas applying it at open time is cheap, self-heals after every update (each new version lands in a fresh folder with default attributes), and needed zero publish-script changes. This composes for free with existing code: `FileService.Save`'s `File.WriteAllText` already throws `UnauthorizedAccessException` on a read-only file, so `ExecuteSave`'s `catch` only needed one new `catch (UnauthorizedAccessException)` clause ahead of the generic one, giving a message that points at Save As instead of surfacing the raw OS "Access to the path is denied" text.
- **`MDEdit.Tests/TestData/markdown-conformance-test.md`** — a standards-based CommonMark + extensions document written to the spec rather than to this implementation, so it deliberately contains constructs MDEdit does not support. Its purpose is finding gaps, whether read by a future functional test or opened by hand. `MDEdit.Tests.csproj` copies `TestData\**\*.md` to the output directory, so a test can read it relative to its own working directory. **It relies on significant trailing whitespace** (two-space hard breaks in §2 and §21) — don't reformat it, and be aware that editing it in MDEdit and saving may strip those.
  - **Known CommonMark/GFM conformance gaps, found by walking this document against the detection code.** **Most of this list is now committed work — `Requirements.md` §11 (*Markdown Conformance*, planned) scopes it**, so treat that section as the authority on what is in and out; this list stays as the detailed engineering inventory behind it. §11 deliberately excludes the extension-only entries below (footnotes, definition lists, heading IDs) and cross-line emphasis, so those remain recorded-but-undecided:
    - Not detected at all: setext headings, indented (4-space) code blocks, footnotes, definition lists, autolinks (`<https://url>`, `<email@x>`), bare-URL auto-linking, heading IDs (`{#custom-id}`), HTML entity decoding (`&copy;` etc. always show as raw text — consistent with WYSIWYG here never rewriting content, only marking up recognized syntax, but still a gap against a "conforming renderer").
    - Partially detected: reference-style links — the `[text][ref]` usage form *is* marker-hidden (`LinkPatterns` in `MarkdownSyntax.cs`), but the shortcut (`[text]`) and collapsed (`[text][]`) forms aren't, and reference *definitions* (`[ref]: url "title"`) are never suppressed — they sit in the document as visible paragraph text instead of vanishing the way a real renderer's would.
    - Cross-line emphasis (bold/italic spanning a line break) isn't detected — `Markdown.xshd`'s `<Rule>` elements (and `FindEmphasisSpans`, which mirrors them) are single-line only; only `<Span>` supports `multiline="true"`, used today for fenced code/HTML comments.
    - Two are silently-wrong renders of ordinary text, not just missing extra syntax, and are probably the most worth prioritizing if any of this list gets picked up: **backslash-escaping is absent everywhere** (`EmphasisPatterns` matches `*`/`_`/etc. by character with no awareness of a preceding `\`, so `\*not emphasis\*` still renders as italic), and **intraword `_` wrongly triggers italics** (CommonMark's flanking rule keeps `_` from opening/closing emphasis mid-word specifically so `snake_case_identifier` stays plain — `MarkdownSyntax`'s single-`_` pattern has no such guard, so `_case_` inside it gets italicized).
    - ATX closing sequences (`### Heading ###`) aren't stripped — `TryGetHeadingLevel` only reads the leading `#` run, so the trailing `###` stays as literal heading text.
    - **Not a gap, despite looking like one**: H4–H6 headings render correctly today (colored, scaled up to level 6 by their own `EditorPreferences` entries, markers hidden) — `TryGetHeadingLevel` caps at 6, not 3, and `StyledElements.Heading(level)` clamps to match. Only the *insertion commands* (Ctrl+1/2/3, the toolbar/Format menu) stop at heading 3, matching Requirements.md §3's stated command scope exactly.

**`THIRD-PARTY-NOTICES.md` is standing maintenance, the same way the changelog is.** MDEdit itself is **0BSD** (`LICENSE`), which asks nothing of anyone, but its two redistributed components are **MIT** and do: AvalonEdit (`ICSharpCode.AvalonEdit.dll`, in every ClickOnce payload) and **Tabler Icons, whose path geometry is *vendored* into `Resources/ToolbarIcons.xaml`** rather than referenced as a package — which is exactly why it's easy to forget it carries terms at all. **Adding a dependency, or vendoring more assets, means adding its notice in the same change.** The obligation attaches to the *installed application*, not the repo, so a notice sitting only at the repo root wouldn't discharge it: `MDEdit.csproj` ships both files beside the exe via `<Content Include="..\THIRD-PARTY-NOTICES.md" Link="THIRD-PARTY-NOTICES.md" />` and `<Content Include="..\LICENSE" Link="LICENSE.txt" />`. The `Link=` on each is load-bearing — without it the file lands in a `MDEdit\` subfolder mirroring its source path instead of beside the exe, where `AboutWindow` looks for it. The rename to `.txt` keeps the repo root's extensionless `LICENSE` (what GitHub's licence detection expects) while giving the shipped copy an extension Windows can open. Neither is marked read-only the way `ReleaseNotes.md` is — nobody edits a licence, so there is nothing to protect and no reason to create a second stale-attribute problem for `ClearStaleReleaseNotesReadOnly` to undo. The .NET Desktop Runtime is a **prerequisite, not a bundled component** (`SelfContained=false`), so it needs no notice at all.

WYSIWYG is implemented as a **live-preview mode inside AvalonEdit itself** — not a WebView2/rendered-HTML view. The Markdown text is always the single source of truth; the toggle (View → Editor Mode → WYSIWYG) only changes how AvalonEdit *renders* that same text (larger heading fonts, syntax markers hidden except where the caret is). This was a deliberate choice over a `contenteditable`/WebView2 approach specifically to avoid a lossy HTML→Markdown round-trip — there is no round-trip, so there's nothing to lose. A WebView2 *read-only* rendered preview pane remains a possible separate future addition, not a replacement for this.

Every construct Requirements.md lists as *implemented* is covered, tables included; what remains from §3 are commands and catalogue features, not rendering. See **Live-preview constructs** at the end of Architecture below for the per-construct reveal-scope/replacement map and the checklist for adding another; the mechanism is built incrementally, one construct at a time.

Release builds (`dotnet build -c Release` / `dotnet publish -c Release`) are Authenticode-signed automatically via an `AfterTargets="Build"` MSBuild target in `MDEdit.csproj` that runs `build/Sign.ps1`. ## Architecture

The app is a single-window WPF application; almost all logic lives directly in `MainWindow.xaml.cs` rather than being split across MVVM layers — there is no ViewModel.

- **`MainWindow.xaml` / `MainWindow.xaml.cs`** — the entire UI (menu, toolbar, status bar, editor) and its code-behind. Command routing uses standard WPF `RoutedUICommand`s (`ApplicationCommands.New/Open/Save/...`) plus custom ones declared as `static readonly RoutedUICommand` fields (`SaveAsCommand`, `BoldCommand`, `ItalicCommand`) for actions with no WPF built-in. Heading shortcuts (Ctrl+1/2/3) and the Word-compatible subscript/superscript shortcuts (Ctrl+Shift+`_` / Ctrl+Shift+`+`, i.e. `Key.OemMinus`/`Key.OemPlus` with Control+Shift — both characters are already Shift-ed) are wired in `RegisterKeyBindings` via `InputBindings` + a local `RelayCommand` rather than `CommandBinding`, since there's no built-in command for them. Their menu `InputGestureText` is written by hand in XAML: WPF fills that in automatically only for a `RoutedUICommand`'s own gestures, never for `InputBindings`.
  - **`ReleaseConflictingEditorGestures()` must run before those bindings, and is not optional.** AvalonEdit declares gestures on its own editing commands — **Ctrl+I** is `IndentSelection` and **Ctrl+U** is `ConvertToLowercase` — and those resolve against the `TextArea`, which sits nearer the keyboard focus than this window, so they silently swallow the keystroke and MDEdit's Italic and Underline never fire. Ctrl+B was unaffected only because AvalonEdit claims no Ctrl+B, which is what made the failure look arbitrary. The fix clears those two commands' `InputGestures`; neither is exposed in MDEdit's UI. **Check this list before adding any new Ctrl-shortcut** — AvalonEdit also claims Ctrl+D (`DeleteLine`), Ctrl+Shift+U (`ConvertToUppercase`), and Insert (`ToggleOverstrike`), none of which MDEdit currently uses.
  - **New Window (Requirements.md §1, Ctrl+Shift+N) launches a second *process*, not a second `Window` in this one — `NewWindow()` is a `Process.Start` on `Environment.ProcessPath` and nothing more.** That is the mechanism MDEdit already ships (Explorer runs `"MDEdit.exe" "%1"` via `FileAssociationService`), so it is proven, and it buys full independence for free: own document, own `CheckUnsavedChanges` prompt, own `AppSettings`, own lifetime. **An in-process window was considered and rejected**, and the reason isn't just the settings-collision hazard — it's that `ApplyTheme` is split across two scopes: `ThemeService.Apply` sets `Application.ThemeMode` and swaps the app's merged dictionaries **process-wide**, while the colorizer's `IsDark`, the active highlighting definition, the caret brush and the Highlight swatch are **per-window**. A theme switch in one in-process window would therefore re-chrome the other's menus and toolbar while leaving its document text on the old palette — a visibly half-applied theme. Fixing that means one shared `AppSettings` plus a changed-broadcast every window subscribes to (and unsubscribes from in `OnClosed`), which is a settings refactor, not this feature; **that is the design to reach for if per-window independence ever stops being wanted.** Two consequences of the process choice worth knowing: `settings.json` stays **last-writer-wins** between windows (not a regression — two MDEdits already behaved this way), and the new process runs the constructor's `else MaybeShowReleaseNotesOnFirstRun()` branch since it gets no command-line argument, so on the one path where the *first* window was launched with a file argument straight after an update, the second window opens the release notes rather than a blank document. Accepted: the gate is doing exactly what it says, just later than usual. Ctrl+Shift+N needed no entry in `ReleaseConflictingEditorGestures` — WPF's `EditingCommands.ToggleNumbering` does carry that gesture, but registers it as a class input binding on `TextBoxBase`, which AvalonEdit's `TextArea` is not.
  - Formatting operations (bold/italic/strikethrough/code = `WrapSelection`; headings = `InsertHeading`; lists/blockquote = `InsertLinePrefix`; code block = `InsertCodeBlock`; links = `InsertLink`) all follow the same convention described in Requirements.md §3: wrap the selection if there is one, otherwise insert placeholder syntax and position the caret/selection for immediate typing. These are now thin wrappers around `Editing/MarkdownFormatter.cs` (see below); MainWindow just supplies the `TextDocument` + current selection and applies the returned caret/selection placement via `ApplyFormat`, which sets it with a single `Editor.Select(start, length)` call — not separate `SelectionStart`/`SelectionLength` assignments, since `TextEditor.SelectionStart`'s setter internally reuses whatever `SelectionLength` currently reports, which can be a stale, now-out-of-bounds value left over from AvalonEdit's selection-anchor bookkeeping after `MarkdownFormatter`'s `doc.Replace` (reproducible by wrapping a selection that reaches end-of-document; caused a real `ArgumentOutOfRangeException` crash, fixed and covered by `ApplyFormatSelectionTests`).
  - Live preview / WYSIWYG state: `_settings.LivePreview` (persisted) drives `UpdateLivePreviewState()`, which sets `Editor.FontFamily`/`Editor.FontSize` from the active mode's base (`_sourceFontFamily`/`_wysiwygFontFamily`, both derived from `EditorPreferences` by `ApplyEditorPreferences`), calls `ApplyActiveModeStyles()` and `UpdateHighlighting(...)` — **the editor mode now selects which of the four compiled highlighting definitions is live, so this call is not optional** — and flips `MarkdownLineColorizer.LivePreviewEnabled`, `HeadingMarkerElementGenerator.Enabled`, `EmphasisMarkerElementGenerator.Enabled`, `CodeBlockFenceElementGenerator.Enabled`, `ImageElementGenerator.Enabled`, `LinkMarkerElementGenerator.Enabled`, `UnderlineMarkerElementGenerator.Enabled`, `EmojiElementGenerator.Enabled`, `BlockquoteMarkerElementGenerator.Enabled`, `BulletListMarkerElementGenerator.Enabled`, `TaskListMarkerElementGenerator.Enabled`, `NumberedListMarkerElementGenerator.Enabled`, `TableRowElementGenerator.Enabled`, `HorizontalRuleElementGenerator.Enabled`, `BlockquoteAccentBarRenderer.Enabled`, `TableGridRenderer.Enabled`, and `HorizontalRuleRenderer.Enabled`, and syncs the View → Editor Mode radio-style menu checkmarks (`MenuEditorModeSource`/`MenuEditorModeWysiwyg`, set manually like the Theme submenu — no native radio-group support used elsewhere in this codebase either) plus the toolbar's own `BtnEditorModeToggle` (a `ToggleButton`, the toolbar's first section, ahead of a `Separator` and every other group — the only stateful toggle on the toolbar, everywhere else being one-shot commands). Its `Click` handler (`BtnEditorModeToggle_Click`) reads back `IsChecked` rather than tracking a separate flag: WPF flips a `ToggleButton`'s `IsChecked` before raising `Click`, so by the time the handler runs it already holds the state the click just asked for, the same as the two Editor Mode menu handlers apply a fixed value each. `OnCaretPositionChanged` tracks both `_lastCaretLine` (heading, code-fence, blockquote, bullet-list, task-list, and horizontal-rule reveal, line-grained) and `_lastCaretOffset` (emphasis, image, link, underline, and emoji reveal, span-grained — a caret move within the same line can still move into/out of one of those runs) and redraws just the old and new line via `TextView.Redraw(DocumentLine)` whenever the offset changes at all; generator state is updated *before* those redraws so both lines render against the new caret position. Code-block fences and tables are the exceptions to "just the old/new caret line" — both are per-block constructs whose reveal region can sit well outside those two lines — so `OnCaretPositionChanged` additionally calls `RedrawEnclosingFenceLines()` (redraws just the block's two fence lines, the only lines whose appearance changes there) and `RedrawEnclosingTableLines()` (redraws the *whole* block — crossing a table's boundary flips every row between grid and raw source) for both the old and new caret line. Blockquotes and horizontal rules deliberately do *not* get this block-wide treatment despite the accent bar/drawn rule sharing the reserve-hide/draw-separately split with fences and tables — only the caret's own line reveals its raw text, matching the simpler per-line pattern; a horizontal rule occupies exactly one line to begin with, so there is no block to redraw beyond it. `ResetLivePreviewCaretTracking()` re-syncs all thirteen generators after `NewDocument`/`OpenFile` reset the caret to line 1 (called wherever `UpdateHighlighting` is, for the same "just loaded a different document" reason).

  - **The status bar is a plain `Border` + `Grid`, deliberately not `StatusBar`/`StatusBarItem` — don't "restore" the proper control.** The themed one rendered *no text at all*, in either theme: this app opts into the experimental Fluent `ThemeMode` (see `ThemeService`), and Fluent's `StatusBarItem` wants more vertical room than the fixed `Height="22"` allowed, so the content was clipped away entirely. Symptom is total invisibility, including literal XAML text, which makes it look like a data-binding or layout-docking bug and sends you the wrong way — the docking was fine throughout (the editor `Border` follows the status bar in the root `DockPanel`, so the editor is the `LastChildFill` child and `Dock="Bottom"` works). Two details keep it working: `MinHeight` rather than `Height`, so content can never be clipped again; and `TextElement.Foreground` rather than `Foreground`, because `Border` has no `Foreground` property and the plain form silently does nothing. The divider line above it comes from the editor `Border`'s `BorderThickness="0,1"`, not from the status bar.
  - Status bar (Requirements.md §9) is split into **two** update methods on purpose. `UpdateStatusBar()` does caret position and selection size — cheap, and it runs on every caret move. `UpdateDocumentStats()` does size and character count, which means walking the whole document for a UTF-8 byte count, so it runs only on `TextChanged` and once at construction. **Don't merge them**: putting the byte count on the caret path would materialize `Document.Text` on every arrow-key press. Selection is additionally hooked to `TextArea.SelectionChanged`, because a selection can change without the caret moving. The byte count is the size a *save* would produce — it includes `Encoding.UTF8.GetPreamble().Length`, since `FileService` writes through `File.WriteAllText`, which emits the BOM; without that it would disagree with Explorer by exactly 3 bytes. The filename and dirty marker are deliberately absent from the status bar (the title bar has both). The character count itself goes through `Editing/CharacterCounter.Count`, not raw `Editor.Document.TextLength`, so it can charge each line break a user-chosen weight (`AppSettings.LineBreakCharWeight`, 0/1/2, set from View → Line Breaks Count — `MainWindow.SetLineBreakCharWeight`/`ApplyLineBreakCharWeight`) instead of whatever that line break actually is in the raw text. The computation sums each `DocumentLine.DelimiterLength` (0, 1, or 2 — an LF, a CRLF, or none) across the document, subtracts that real total from `TextLength`, and adds back `lineBreakCount * weight` — so mixed line endings in one document (an LF-only line next to a CRLF one) are still charged identically under one weight, rather than each keeping its own actual width. Default is 2, matching a literal CRLF, so upgrading from a version without this setting doesn't change what's displayed.
  - `CheckUnsavedChanges()` is the single choke point for the "save/discard/cancel" prompt required before New, Open, and window Close.

Entries are added by `AddToRecentFiles`, called from `OpenFile` (inside the `try`, so a file that failed to open never lands in the list) and from `ExecuteSaveAs`; plain `Save` doesn't, since that path is already in the list. `OpenRecentFile` checks `File.Exists` *before* `CheckUnsavedChanges` — a stale entry shouldn't make the user answer a save prompt for a file that isn't there — and offers to drop the entry when missing. Two details worth preserving when editing the menu build: file names are inserted with `"_"` doubled (WPF eats a single underscore as an access-key marker, mangling names like `my_notes.md`), and the full path goes in the `ToolTip` since file names alone are frequently ambiguous. `ApplySettings()` runs the persisted list through `RecentFiles.Sanitize` rather than trusting it — `settings.json` is hand-editable, and the cap may have changed between versions.

- **`PreferencesWindow.xaml` / `.xaml.cs` + `ModeStyleEditor.cs`** — View → Preferences (Requirements.md §6), the second owned dialog after `AboutWindow`, but unlike it, every change applies live: there's no separate Apply step. Everything is built **imperatively in code-behind**, following `MainWindow.RebuildRecentFilesMenu()`: this codebase has no MVVM/data-binding layer anywhere else, so a dialog is the wrong place to introduce one.
  - **Layout is master–detail, not a grid.** Twenty elements × (family, size, weight, italic, decoration, four colors) does not fit a readable table, and splitting the attributes across tabs would separate one element's font from its color. Left: a `ListBox` of `StyledElements.All`, whose items are an `ElementItem` record carrying key *and* label — the list displays labels but has to round-trip keys, and a label→key lookup breaks the moment two labels coincide. Right: the selected element's full settings plus a live sample.

That makes the detail panel bimodal, and `SelectElement` is where the two shapes diverge: for `normal` the font combo has no `(inherit)` entry and writes `BaseFontFamily`, the size box holds **absolute points** rather than a multiplier (with the unit label and the resolved-size readout adjusting to match), and Decoration plus the Background swatches are disabled via `SetEnabled`, which also sets `ToolTipService.ShowOnDisabled` — a disabled control swallows mouse events, tooltip included, so the explanation would otherwise never be readable. "Reset this element" restores `BaseFontFamily`/`BaseFontSize` too when `normal` is selected, or the one element whose reset matters most would half-work.

Same for the theme, passed as a `Func<bool>` so the sample renders in whichever theme is actually in effect rather than always showing the light palette.

The current value is inserted when it isn't a plain installed-font match — the code font's default is a fallback stack (`"Cascadia Code, Consolas, Courier New"`), never a single entry in `Fonts.SystemFontFamilies`, so without that the shipped default showed blank. The `Separator` is `IsEnabled = false`: it is its own container in an `ItemsControl`, so nothing else stops it becoming `SelectedItem`.

Decoration is one control rather than two checkboxes because AvalonEdit cannot render underline and strikethrough together — see `Editing/StyleResolver`. Size is a multiplier with the resolved point size shown beside it, because sizes for the XSHD-driven elements round to whole points and 1.10 vs 1.15 producing the same result otherwise reads as a bug.

Both are safe specifically because `MainWindow.ApplyEditorPreferences` always reads `_settings.EditorPreferences` fresh at the start of every call rather than holding a reference captured earlier — if it did, replacing the object wholesale would silently stop taking effect.
  - `MenuPreferences_Click` in `MainWindow.xaml.cs` constructs the window with the live `_settings`/`ApplyEditorPreferences` and calls `SettingsService.Save(_settings)` once after `ShowDialog()` returns, regardless of OK/Cancel — the same "save after the dialog returns" shape as every other settings write in this codebase.
  - **Two changes to how an unmodified install renders were accepted deliberately** when this landed, and shouldn't be "fixed" back: `blockquote` and `horizontalRule` pin `FontWeight = Normal` (the old `ColorLine` calls forced it, so `> **bold**` rendered flat — pinned to preserve that, but now reachable, so anyone who wants the emphasis to survive can set it to inherit); and the drawn WYSIWYG bullet now honours the List marker colour, so it is blue rather than plain foreground. - **`Services/SettingsService.cs`** — persists `AppSettings` (`WordWrap`, `ShowLineNumbers`, `Theme`, `LivePreview`, `LoadRemoteImages`, `RecentFiles`, `LastReleaseNotesVersionShown`, `LineBreakCharWeight`, `EditorPreferences`) as JSON at `%AppData%\MDEdit\settings.json`. `LoadRemoteImages` (Requirements.md §5, View → Load Remote Images) is deliberately **top-level rather than an `EditorPreferences` field**: that object is replaced wholesale by PreferencesWindow's Cancel/Reset, and a privacy setting must not be revertible by a dialog that never showed it — see `AppSettingsTests` for the defaults-to-off invariant. Falls back to defaults on a missing/corrupt file rather than failing startup. `EditorPreferences` (Requirements.md §6) holds **two independent `ModeStyles`, `Wysiwyg` and `Source`** — a base font family and size plus a `Dictionary<string, ElementStyle>` of per-element overrides, keyed by `Editing/StyledElements`' stable string keys. Four things about it are load-bearing:
  - **Every `ElementStyle` property is nullable and null means inherit.** "Unset" has to be distinguishable from "set to whatever the base happens to be", or changing the base font would stop propagating to any element the user once touched and reverted. The shape maps 1:1 onto AvalonEdit's own semantics (verified against `HighlightingColorizer.ApplyColorToElement`, tag `v6.3.1`), which rebuilds a typeface from the element's *current* one for whichever fields are null.
  - **`FontWeight` is a string, not a bool**, so `SemiBold` stays expressible — headings 4–6 are SemiBold, and a Bold checkbox would have defaulted them to Normal and rendered them lighter. **`Decoration` is one field, not two booleans**, because AvalonEdit cannot render underline and strikethrough together. **`FontScale` is a multiplier, not points**, so one base-size change rescales everything.
  - **`WysiwygDefaults()` is written as `SourceDefaults()` plus named deltas** — the five heading scales, the two code font families, the hyperlink underline, and strikethrough dropping its grey — rather than a second full table, so the modes can't silently drift apart when a colour changes. Hyperlinks underline in WYSIWYG only, because there the `[text](url)` markers are hidden and the link text reads as a document's link, while in source the visible syntax already says "link". **Strikethrough now actually strikes in both modes** (before §6 it was grey text and nothing more — AvalonEdit could always draw the strike, nothing ever asked it to); the modes differ only in colour, WYSIWYG dropping the grey so struck text reads at ordinary document colour rather than doubly deleted, source keeping it as a second cue while reading raw syntax.
  - **The code palette is the one default that deliberately does not match its pre-§6 value** (green `#00FF33` on black in light, amber `#FFB000` in dark, versus the old `#C7254E` on `#FEF2F2`). Everywhere else "an unmodified install renders identically" still holds and is pinned by tests. Every old special case became an ordinary default: source mode is all-mono because its base is; heading scaling is WYSIWYG-only because source leaves `FontScale` null; code stays mono in WYSIWYG because that mode pins the family. `EditorPreferencesTests` pins all of it, including a test asserting the two tables differ *only* by those named deltas.
  - **`Version` is stamped by `SettingsService.Save` and read by nothing — that is deliberate, not dead code left behind.** The one-time fold of a pre-per-element `settings.json` (`Migrate()`, the ~22 legacy flat properties, and the frozen `V1` baseline table) **was removed on 2026-08-01**, together with `EditorPreferencesMigrationTests.cs`: ~500 lines protecting at most 13 settings (2 fonts + 11 colour pairs, all the old flat dialog ever exposed) across a single transition that cannot recur, for an installed base the owner sized as "just me / a couple of people". Per-element styling had not shipped when it was cut — last publish was `1.0.5.72` — so no upgrade path was actually broken. **Do not reintroduce it**; if a future schema change needs a migration, write that one against `Version`, which is exactly why the stamp survives. Dropping the stamp too would leave every file written from now on unidentifiable.
    - **Removal is safe because an unrecognized property is simply ignored by System.Text.Json**, so an old file loads and lands on current defaults rather than throwing — a one-time visual reset, not data loss. That is now the *entire* recovery story, so it is pinned by `AppSettingsTests.PrePerElementFile_LoadsOntoCurrentDefaults`. Adding a `[JsonExtensionData]` sink or `UnmappedMemberHandling.Disallow` would turn it back into a `JsonException`, which `Load` catches into a **total** reset of every setting, not just the presentation ones.
    - **`Version` still has no property initializer.** System.Text.Json leaves an initializer in place when the property is absent from the JSON, so defaulting it to `CurrentVersion` would make an unstamped file claim to be current — destroying the one distinction the field exists to preserve. Stamping on write is also what it honestly means: the schema the *file* was written with.
    - **Real `settings.json` files are PascalCase**: `Save` calls `JsonSerializer.Serialize` with no `JsonSerializerOptions`, and deserialization is case-sensitive by default. A camelCase test fixture silently fails to bind — it cost one red test here. `SettingsService.Deserialize(string)` exists so this whole path is testable without touching `%AppData%`.

- **`MarkdownLineColorizer.cs`** — an AvalonEdit `DocumentColorizingTransformer` registered on `Editor.TextArea.TextView.LineTransformers`. Handles *line-level* styling that XSHD span/rule matching can't express well: heading color/weight by `#` count, blockquote italics (via `MarkdownSyntax.TryGetBlockquoteMarkerLength`, shared with `BlockquoteMarkerElementGenerator` so the two never disagree on what counts as a blockquote line), horizontal rules. It holds the **active mode's `ModeStyles`** (pushed by `MainWindow.ApplyActiveModeStyles` — which mode is live is MainWindow's business, not this class's) plus `IsDark`, and resolves each element through `Editing/StyleResolver.Resolve`, caching the result per element key; **both setters clear that cache**, which is the whole invalidation story. `ApplyLineStyle` applies only the non-null members of the resolved style, so "inherit" in Preferences means the run keeps whatever it already had. `Resolve` is public because `HorizontalRuleRenderer` and `BlockquoteAccentBarRenderer` read their brush through a reference to this instance rather than holding their own copy — the drawn rule/bar and the raw text revealed under the caret can never disagree, and per-mode colours made two copies materially easier to desynchronise. This runs alongside (not instead of) the XSHD highlighting below, and none of it is gated by `LivePreviewEnabled` — headings/blockquotes/hrules are styled this way regardless of editor mode. **`HeadingScale` is gone**: heading sizing is now a per-mode default (source mode simply leaves `FontScale` null), which also retired the live-preview gate that used to sit on it. This class also owns the **revealed-source font swap** (`ApplyRevealedSourceFont`, live-preview-gated, fed `CaretLine`/`CaretOffset` + `SourceFontFamily` by MainWindow): revealed markdown renders in the mono source font, at two grains matching the reveal scopes exactly — **whole line** for the caret's line when it carries a line-scoped construct (heading/blockquote/bullet/task/numbered/horizontal-rule) and for every line of a table whose block contains the caret; **per span** for whichever inline runs the caret is inside on its own line (emphasis, links, underline, emoji), using the same inclusive-of-both-edges rule as the marker generators so the mono region and the revealed markers can never disagree. The per-span swap is acceptable precisely because the span's layout already shifts at that same instant (its markers appear) — the font change rides the same transition; plain prose lines deliberately stay in the document font so paragraphs don't jiggle while arrowing through them. It runs *before* the styling pass and **returns whether it swapped the whole line**, which `ApplyLineStyle` uses to skip its own family override — otherwise a revealed heading would snap straight back to the document font the instant the caret reached it. Only the *family* is suppressed; size, weight and style still apply, matching how reveal behaved before per-element fonts existed. Code needs nothing here — the WYSIWYG mode's `inlineCode`/`codeBlock` elements pin the mono family (AvalonEdit's `HighlightingColorizer.ApplyColorToElement` applies `HighlightingColor.FontFamily` at render time — verified against its source), which is the entire reason the WYSIWYG font flip needs no code-block handling anywhere. `StyleScriptSpans` is the one *span*-level thing this class does (everything else styles a whole line): it raises/lowers superscript and subscript content via `SetBaselineAlignment` and shrinks it by `ScriptScale`, and is deliberately **not** gated on `LivePreviewEnabled` — the baseline shift *is* the construct, the same way bold renders bold in source mode. Heading/blockquote/hrule lines `return` before reaching it, so a script inside one of those renders plain; that's accepted, since those lines style themselves as a single unit and a later per-span change would fight the line-wide typeface.
- **`Editing/` folder** — UI-free classes factored out specifically to be unit-testable (see `MDEdit.Tests` above) and to anchor the live-preview implementation. The generator bullets below explain each construct in detail; **Live-preview constructs** at the end of this section summarizes them in one table and gives the checklist for adding a new one:
  - **`StyledElements.cs`** — the canonical list of the twenty text-styleable elements (Requirements.md §6): stable persisted key, Preferences label, and the matching `Markdown.xshd` colour name (null for the nine not styled through XSHD — `normal`, headings, blockquote, horizontal rule). **`normal` is first, and is the odd one**: it is default body text rather than a Markdown construct, so its family and size are the mode's `BaseFontFamily`/`BaseFontSize` rather than fields of its own `ElementStyle` (a size expressed as a multiplier of itself would be circular), and its weight/italic/foreground are applied to the *editor control* by `MainWindow.ApplyNormalTextStyle` rather than through either construct-styling path. Decoration and background are deliberately not offered for it — see that method. **Keys are stable strings, never enum ordinals**: they are persisted as dictionary keys in `settings.json`, so a reordered enum would silently remap a user's settings onto the wrong elements. `Heading(int level)` is the single level→key mapping, clamping above 6 to match `TryGetHeadingLevel`; building `$"heading{level}"` at a call site would work today and break silently the moment a key is renamed. `listMarker` is the one element on *both* rendering paths — see the list-generator bullet below for why.
  - **`StyleResolver.cs`** — turns a persisted `ElementStyle` (hex strings, named weights, a named decoration, a size multiplier) into the WPF values both rendering paths need, as a `ResolvedStyle` whose null members mean "inherit". Shared deliberately: styling reaches the editor through two unrelated mechanisms (`MarkdownHighlighting` writing onto the highlighting definition, `MarkdownLineColorizer` writing onto visual line elements), and they must never disagree about what a stored value means. Every mapping returns null for an unrecognized value rather than throwing — `settings.json` is hand-editable, and a typo should cost that one override, not the ability to open a document. Brushes **and the empty "no decorations" collection** are frozen: they are cached and shared across every visual line using the element, and an unfrozen `Freezable` also carries thread affinity (which is what made a test fail before it was frozen).
  - **`MarkdownHighlighting.cs`** — compiles `Resources/Markdown.xshd` into a definition styled for one editor mode and one theme; four exist at a time (light/dark × source/WYSIWYG). Clears every styleable property before applying the element's style — see the `Markdown.xshd` bullet for why that is load-bearing. Only elements with an `XshdColorName` are handled here.
  - **`FontCatalog.cs`** — the installed font families offered in Preferences, and which are fixed-width. WPF exposes no fixed-pitch flag and does not surface the OS/2 table's `isFixedPitch`, so this *measures*: a family is monospaced when `i`/`W`/`M`/`.` all advance by the same width per `GlyphTypeface.AdvanceWidths`. Four probe characters rather than two so a family matching on one pair isn't misfiled, plus a zero-width guard. Handles a comma-separated fallback stack (the shipped default code font is one) and returns false rather than throwing for an unknown or unreadable family — one damaged font must not stop Preferences opening.
  - **`ListMarkerStyling.cs`** — builds the `TextBlock` that stands in for a list marker in WYSIWYG, shared by the bullet and numbered generators because they are one styleable element; two copies would be two chances for a numbered list to stop matching the bulleted list above it.
  - **`StatusFormatter.cs`** — status-bar number formatting (`FormatFileSize`/`FormatCharacterCount`/`FormatSelectionCount`). Each takes an optional `IFormatProvider` defaulting to `CurrentCulture`, so the UI localizes the decimal separator and thousands grouping while tests pin `InvariantCulture`.
  - **`RecentFiles.cs`** — MRU list transformations (`Add`/`Remove`/`Sanitize`), returning a new `List<string>` rather than mutating, with `MaxEntries` as the single cap. Paths are normalized with `Path.GetFullPath` and compared `OrdinalIgnoreCase` so one file reached by different spellings (case, `.`/`..`, a relative command-line argument) collapses to one entry. Persistence and the menu belong to MainWindow; this file is pure list logic, covered by `RecentFilesTests`.
  - **`MarkdownFormatter.cs`** — the actual logic behind every formatting command (`Wrap`, `Heading`, `ToggleLinePrefix`, `CodeBlock`, `Link`, `Table`), operating on an AvalonEdit `TextDocument` plus a plain `SelectionRange` struct rather than the live `TextEditor`, so tests can drive it without a window.
  - **`MarkdownSyntax.cs`** — shared line-construct detection. `MarkdownLineColorizer` (coloring/sizing) and the marker-hiding generators both call into this rather than each having their own regex/parsing, specifically so they can never disagree about what counts as a given construct. **Extend this file first when adding live-preview support for another construct** — colorizer and generator(s) should both consume it.
    - **Block constructs** — `TryGetHeadingLevel` (ATX heading + marker length); `TryGetBlockquoteMarkerLength` (leading `` `>` `` run, including nested `` `> > ` ``, plus a `depth` out param — the nesting level, used to draw one indent bar per level; see the `BlockquoteMarkerElementGenerator` bullet below); `IsFenceDelimiterLine`/`TryGetEnclosingFenceBlock` (fenced-code-block detection — see the `CodeBlockFenceElementGenerator` bullet below); `IsHorizontalRule` (whole-line `---`/`* * *` detection — moved here from `MarkdownLineColorizer`'s private helper so bullet detection can exclude hrule lines using the exact same definition the colorizer styles them with); the table family — `IsTableRowLine`/`IsTableDelimiterLine` (deliberately stricter than GFM: both outer pipes required at column 0, three-dash minimum in delimiter cells — "a | b" prose must never render as a table row), `TryGetTableBlock` (header + directly-adjacent delimiter with matching cell count + every contiguous row line below; the *topmost* valid header in the contiguous run wins, so row-shaped prose sitting above a real table is excluded rather than poisoning the pairing), and `GetTablePipeOffsets`/`GetTableCells`/`GetTableAlignments` (escape-aware `\|` splitting and the delimiter row's colon alignments — pipe offsets are shared with `MarkdownLineColorizer`'s pipe dimming so the two can't disagree).
    - **List markers** — `TryGetBulletListMarker`/`TryGetNumberedListMarker` are line-start-only with optional nesting indent, deliberately stricter than `Markdown.xshd`'s unanchored ListMarker rules since replacing a mid-sentence `"a - b"` dash or `"version 1. note"` with list rendering would corrupt prose.
    - **Inline spans** — `FindEmphasisSpans` (bold/italic/bold+italic/strikethrough/highlight/superscript/subscript/inline-code runs on a line, as `EmphasisSpan { Start, End, MarkerLength }`), `FindUnderlineSpans` (`<u>…</u>`, as `UnderlineSpan { Start, ContentStart, ContentEnd, End }` — its own scan, since it's HTML rather than an emphasis marker), and `FindScriptSpans` (just the superscript/subscript runs, as the `ScriptSpan { ContentStart, ContentEnd, IsSuperscript }` the colorizer needs — same scan, filtered by `EmphasisKind`) and `FindLinkSpans` (links/images, as `LinkSpan { Start, TextStart, TextEnd, End }` — see the `LinkMarkerElementGenerator` bullet below).
    - *Emphasis lexer* — `FindEmphasisSpans` mirrors `Markdown.xshd`'s exact patterns and precedence (bold+italic before bold before italic; character-class exclusion instead of wildcard quantifiers, to avoid catastrophic backtracking — same reasoning as the XSHD comments) via a tiny `\G`-anchored, non-overlapping single-pass lexer, so the two never drift apart. Inline code's content is never recursed into — it's literal per CommonMark's code-over-emphasis precedence, which the lexer's leftmost-wins scan also provides at the top level, same as AvalonEdit's earliest-match rule resolution.
    - *Mixed-delimiter nesting* — the lexer recurses one level into each match's inner content to find a nested run of the *opposite* delimiter (e.g. `_**bold**_`, `**_italic_**` — CommonMark forbids nesting the same delimiter inside itself, so this is the standard way authors combine bold+italic as two runs instead of `***text***`). This falls out for free with no extra filtering, since a match's content can never contain its own delimiter (excluded by the pattern's own content class), so re-scanning that content with the same pattern list can only ever find an other-delimiter run; the same mechanism covers strikethrough wrapping/wrapped-by emphasis (`~~**text**~~`, `**~~text~~**`).
    - *Mutual skip-awareness* — `FindEmphasisSpans` and `FindLinkSpans` each try the other's pattern table first at every scan position (without recording a match, just to advance past it), mirroring how `Markdown.xshd`'s Link rule is a flat `<Rule>` with no nested `RuleSet` (unlike Bold/Italic's `<Span>`): `[**bold**](url)` is one opaque link with no separately-colored nested Bold, and `**[link](url)**` is one opaque Bold run with no separately-colored nested Link, in both the real syntax highlighter and here. Both scanners also skip a leading bullet-list marker before scanning (`LeadingBulletMarkerLength`) — mirroring the XSHD's rule order, where ListMarker precedes every emphasis/link rule, so on `* item*` the leading `* ` is a list marker rather than the opener of an italic run swallowing the whole line.
    - *Document-wide exception* — `TryGetEnclosingFenceBlock` is the one method here that isn't purely line-local: fence pairing (which same-kind `` ``` ``/`~~~` line closes which) is a document-wide parity property, so it walks from the start of the document. Callers check the O(1) `IsFenceDelimiterLine` first so this cost is only paid for actual fence lines, not the majority of lines in a document.
  - **`HeadingMarkerElementGenerator.cs`** — an AvalonEdit `VisualLineElementGenerator` (registered on `Editor.TextArea.TextView.ElementGenerators`) that hides a heading's `"# "` marker text using a zero-size `InlineObjectElement`, on every line except the one the caret is currently on (**per-line** reveal — a heading marker only ever exists at a line's start, so line-granularity is sufficient). The marker characters still occupy their document offsets (selection/undo/the saved file are unaffected) — only the visual rendering collapses them to nothing.
  - **`EmphasisMarkerElementGenerator.cs`** — same zero-size-`InlineObjectElement` hiding technique, but **per-span** reveal instead of per-line: several bold/italic runs can share one line, so only the specific run the caret is inside (inclusive of both edges, so landing exactly on a boundary doesn't flicker) stays visible; hiding every marker on the line just because the caret is elsewhere on it would be distracting mid-sentence. This was the template for `LinkMarkerElementGenerator`.
  - **`BlockquoteMarkerElementGenerator.cs`** — same per-line reveal convention as `HeadingMarkerElementGenerator` (only the caret's own line shows its `` `>` `` marker, even for a multi-line blockquote — deliberately *not* the fence pair's per-block reveal, since a blockquote marker's meaning and `MarkdownLineColorizer`'s italic styling are entirely local to its own line), but the **replacement isn't zero-width** like every other marker generator: the hidden marker is replaced with a blank horizontal spacer sized `depth × IndentPerLevel` (`LeadingIndent`/`LeadingGap`/`BarWidth`/`TrailingGap`/`IndentPerLevel` are `internal const`s on this class — the knobs to tweak if the indent/bar sizing needs adjusting; `LeadingIndent` is a one-time shift of the whole construct, tuned by eye so the level-1 bar lines up with the list generators' "•" glyphs), reserving room for the accent bar(s) `BlockquoteAccentBarRenderer` draws separately. This class only reserves space; it does not draw anything itself (`Height = 0` on the spacer, same zero-visual-height idiom the other generators use for a plain hide). This split reserve-space/draw-separately approach is blockquote-specific, not a general template — no other construct uses it.
  - **`BlockquoteAccentBarRenderer.cs`** — an AvalonEdit `IBackgroundRenderer` (registered on `Editor.TextArea.TextView.BackgroundRenderers`, not `ElementGenerators`) that draws the actual accent bar(s) as one continuous vertical line per nesting level, spanning every consecutive run of blockquote lines currently visible — not one short bar per document line. This split (reserve indent space in the element generator, draw the bar separately here) exists because an `InlineObjectElement` is confined to its own line's content flow: the vertical gap between lines (line spacing/leading) belongs to `TextView`'s own layout, not to any single line's content, so no per-line element, however tall, can ever make adjacent bars touch — confirmed by checking `TextView.cs`, which measures inline embedded objects with an *infinite* constraint (`Element.Measure(new Size(double.PositiveInfinity, double.PositiveInfinity))`) rather than the line's actual height. A background renderer instead draws directly in the `TextView`'s shared pixel space (`Draw(TextView, DrawingContext)`, layer `KnownLayer.Background`), using `TextView.VisualLines` (the currently-visible `VisualLine`s) plus `VisualTop`/`Height`/`VerticalOffset`/`HorizontalOffset` to convert document-relative positions into on-screen coordinates, so it can draw a single rectangle from the top of the first line in a run to the bottom of the last with no gap. It processes one nesting level at a time (`for level in 1..maxDepth`, each its own contiguous-run scan) rather than all levels in one pass, so a depth transition mid-blockquote (e.g. `"> a"` followed by `">> b"`) still renders level 1's bar as continuous through the transition while level 2's bar only covers the deeper sub-run. Reads the same `LeadingIndent`/`LeadingGap`/`BarWidth`/`IndentPerLevel` constants from `BlockquoteMarkerElementGenerator` so the drawn bar always lines up with the space reserved there. The bar's colour is **read from `MarkdownLineColorizer.Resolve(StyledElements.Blockquote)`** through a constructor-supplied reference to the colorizer — the same arrangement `HorizontalRuleRenderer` uses, for the same reason. It used to hold its own `LightBarBrush`/`DarkBarBrush` pushed in by `ApplyEditorPreferences`; per-element styling made that untenable, since the colour now varies by editor mode as well as theme and only the colorizer knows which mode is live. Two copies of a colour that must agree is one copy too many.
  - **`TaskListMarkerElementGenerator.cs`** — bullet-list variant for `- [ ]`/`- [x]`, replacing bullet and box together with a single drawn checkbox at the shared `IndentPerLevel` depth. Never mutates the document; toggling is `MarkdownFormatter.TaskListItem`'s job.
  - **`BulletListMarkerElementGenerator.cs` / `NumberedListMarkerElementGenerator.cs`** — per-line reveal like `HeadingMarkerElementGenerator`, but the third replacement variant after zero-size hide and blank spacer: a **visible rendered element** (an `InlineObjectElement` hosting a `TextBlock` built by the shared `ListMarkerStyling.CreateMarkerBlock` — it starts from `CurrentContext.GlobalTextRunProperties`, so an unset style follows the editor's own typeface/size/foreground with no wiring, then applies whatever the `listMarker` element overrides). That style arrives as a `MarkerStyle` property pushed by `MainWindow.ApplyActiveModeStyles`, and it is **required, not decorative**: the marker is *replaced* here rather than coloured in place, so the XSHD `ListMarker` colour that styles the raw `-` in source mode never reaches this glyph — without the push, the element's settings would appear to do nothing in WYSIWYG. Note this is why the WYSIWYG bullet is blue rather than plain foreground, a deliberate change from how it rendered before §6. Bullets replace the single `-`/`*`/`+` marker character with a "•" glyph — a plain hide was deliberately rejected: unlike a heading's `# `, the bullet marker *is* the construct's visual, so collapsing it would leave list items indistinguishable from plain text. Numbered markers replace their digits+`.` range with the **exact same text** — `1. ` already renders identically to its source form, so the element exists only to carry the indent. Both set `Margin` left to `BlockquoteMarkerElementGenerator.IndentPerLevel` (referenced, not duplicated) so list items sit at the same pixel depth as blockquote content. The following space and any leading nesting indent remain real rendered text (nested items get the source whitespace's natural width on top of the fixed indent, not a quantized per-level depth).
  - **`CodeBlockFenceElementGenerator.cs`** — same zero-size-`InlineObjectElement` technique again, but on the **whole line** (a fence line like `` ```csharp `` has no separate "marker prefix" vs. "content" the way a heading does — the entire line *is* the marker) and with **per-block** reveal: both the opening and closing fence of a code block stay visible whenever the caret is anywhere inside that block (on either fence line or any content line between), not just when the caret is literally on a fence line — otherwise the fences would flicker away while simply typing code in the middle of the block. This is the first live-preview construct where what's hidden and what triggers a redraw aren't confined to the caret's own line, since a fence pair can be many lines apart; see the `MainWindow.OnCaretPositionChanged`/`RedrawEnclosingFenceLines` note above.
  - **`EmojiCatalog.cs`** — shortcode→emoji lookup, loaded once (lazily) from the embedded `Resources/Emoji.txt`. Missing resource yields an empty catalogue rather than throwing, so a packaging slip degrades to "no emoji" instead of taking the editor down; `MarkdownSyntaxEmojiTests` asserts a non-trivial entry count so that degradation can't pass silently.
  - **`EmojiElementGenerator.cs`** — per-span reveal with a *visible* replacement (the emoji character), the first generator to combine those. Replaces the whole `:joy:` run rather than hiding markers around content — unlike emphasis, there's no inner text to keep.
  - **`UnderlineMarkerElementGenerator.cs`** — `LinkMarkerElementGenerator`'s two-independently-sized-regions approach applied to `<u>`/`</u>`, with the same per-span reveal. Hides the tags only; the underline itself comes from the XSHD's `Underline` color, so this class needs no theme wiring.
  - **`LinkMarkerElementGenerator.cs`** — `EmphasisMarkerElementGenerator`'s per-span reveal convention applied to links/images, but with an **asymmetric** hidden region instead of a symmetric marker: `[` (or `![`) as the prefix and `](url)`/`][ref]` as the suffix, since the URL/reference portion has no fixed width the way `**`/`_` do — so this constructs two independently-sized `InlineObjectElement`s per link (`LinkSpan.TextStart - Start` and `LinkSpan.End - TextEnd`) rather than reusing one `MarkerLength` at both ends. Since local image rendering landed it is also the fall-through for every image span `ImageElementGenerator` declines (remote, unresolvable, reference-form) — it needed zero changes for that; see the image bullets under **Live-preview constructs** below.
  - **`ImagePathResolver.cs`** — the pure decline-half of image rendering, with **two deliberately disjoint entry points** sharing one private `Normalize` (trim, `<...>` unwrap, trailing-quoted-title strip): `TryResolve` returns an absolute *local* path and declines every scheme, so a URL can never reach `File.OpenRead`; `TryResolveRemote` accepts *only* http/https by whitelist and so declines every local path. A declined result **always means "fall through to `LinkMarkerElementGenerator`", never "broken"**. The whitelist — not `Uri.TryCreate`'s success — is what decides remoteness, because `Uri.TryCreate` happily turns `C:\x.png` and `\\server\share\x.png` into absolute URIs with scheme `file`; that's the mirror image of the local side's "deliberately not `Uri.TryCreate`, which claims `C:\x.png` with scheme `c`" note. Kept as two entry points rather than one `ImageTarget` union specifically so a declined remote span is the structural default reached by writing no code, instead of a `switch` arm someone could get wrong. Unit-tested in `ImagePathResolverTests`.

Holds the URL-keyed four-state cache (absent/InFlight/Loaded/Failed, one record rather than a dictionary plus a parallel in-flight set, with `Failed` terminal until `Invalidate()` so a dead URL isn't re-requested on every scroll), the shared static `HttpClient`, the generation + cancellation guarding, the UI-thread-only mutation rule that removes the need for a lock, and the coalesced `Background`-priority redraw. Its class comment carries the privacy guarantee in full — read it before touching anything here. Its two pure guards (`IsAcceptableImageContentType`, `ReadCappedAsync`) are unit-tested in `RemoteImageLoaderTests`; nothing else here is, by the generator-testing rule.
  - **`HorizontalRuleElementGenerator.cs`** — per-**line** reveal like `HeadingMarkerElementGenerator`/`BlockquoteMarkerElementGenerator` (caret elsewhere hides the line, caret on the line reveals the raw `---`/`* * *` text), but the hidden range is the **whole line** — a horizontal rule has no separate marker-prefix-vs-content split, so this reuses the fence idiom (`CodeBlockFenceElementGenerator`'s whole-line zero-size hide) rather than the heading/blockquote partial-prefix one. The drawn rule itself lives in `HorizontalRuleRenderer`, not here — a rule has no content of its own to size a rendered element from (unlike a bullet's "•" or a table's measured columns), so it has to span whatever width is actually on screen, which only a background renderer answers. `IsRendered` is the single shared gate both classes call, so the hidden text and the drawn line can never disagree about which lines are currently rendered.
  - **`HorizontalRuleRenderer.cs`** — draws the rule as a single horizontal line across every visible line `HorizontalRuleElementGenerator` is hiding, using `MarkdownLineColorizer`'s `HRuleBrushLight`/`Dark` (read through a constructor-supplied reference to the colorizer instance) so the drawn line and the raw text revealed under the caret read as the same color. Unlike `BlockquoteAccentBarRenderer` and `TableGridRenderer`, this one is deliberately **pinned to the viewport rather than tracking `HorizontalOffset`**: a rule has no document-relative anchor worth preserving under horizontal scroll (it represents "the whole row"), so it always fills whatever is currently on screen instead of appearing to scroll away when the user scrolls right to read a long line elsewhere.
  - **`TableRowElementGenerator.cs`** — per-**block** reveal like the code fences (caret anywhere in the table reveals the whole thing as raw source, so editing always happens on raw text and column widths never shift under the caret), with whole-line **visible** replacement: each header/body row line becomes a run of fixed-width `TextBlock` cells (header bold, delimiter-row colons honored as `TextAlignment`), and the delimiter row is hidden whole via the fence idiom — its blank band, bordered top and bottom by the renderer, reads as the separator zone under the header. Column widths are a whole-table property (the reason tables never fit the per-line/per-span shapes): the widest cell per column, measured via `FormattedText` with the editor's own typeface — exact, because cells render their raw text verbatim — computed once per table into a `TableLayout` and cached; **any** document change clears the whole cache (`ReferenceEquals` on `TextDocument.Version`) rather than tracking which table a change touched, so a stale width can't survive an edit — and a **font change** (the WYSIWYG document-font flip) also clears it, detected by comparing the captured typeface/em-size, since the version key can't see a font swap that changes every measured width without touching the document. The text properties needed for measurement are captured on every `GetFirstInterestedOffset` call because `TableGridRenderer.Draw` can reach `ComputeLayout` outside any construction context. `ColumnCount` is the max cell count across *all* rows, not the delimiter's count — a body row with extra cells gets extra columns, because **rendering must never hide cell content**. `TryGetRenderedTable` is the single shared is-it-rendered/what-size gate for both this class and the renderer. Rows carry a left `Margin` of `BlockquoteMarkerElementGenerator.IndentPerLevel` (referenced, not duplicated — the list-generator convention), and `TableGridRenderer` offsets its `x0` by the same constant, so the grid sits at the same pixel depth as bullets and blockquote content with the drawn lines exactly under the cells.
  - **`TableGridRenderer.cs`** — the `IBackgroundRenderer` half of the table rendering: header shading, a horizontal line at every row-band edge, and vertical column lines drawn as continuous strokes across the table's visible lines — the same generator/renderer split as blockquotes, for the same reason (per-line elements can't make lines touch across the inter-line space `TextView` owns). Unlike `BlockquoteAccentBarRenderer` (which shares only layout *constants*), this one holds a reference to the `TableRowElementGenerator` instance and asks `TryGetRenderedTable` per visible line, so the reveal decision and the column geometry can never diverge between the drawn grid and the row elements — including drawing nothing over a revealed (raw) table.
- **`Resources/Markdown.xshd`** — AvalonEdit XSHD grammar for *inline* Markdown highlighting (bold/italic/strikethrough/highlight/inline code/links/images/fenced code blocks/HTML comments/list markers). Embedded as a resource (see `.csproj`) and loaded at runtime via `Assembly.GetManifestResourceStream("MDEdit.Resources.Markdown.xshd")`, from `Editing/MarkdownHighlighting.Build`. **Its `<Color>` elements carry no visual attributes at all — names only** (Requirements.md §6): every colour, weight, style, decoration, family and size is written onto them at load time from `EditorPreferences`. That is not tidiness, it is required for "inherit" to mean inherit — `Build` clears each property before applying the user's style, so a value left in the file would either be dead weight or, if the clearing were ever removed, would silently resurface for an element the user had explicitly cleared. `MarkdownXshdTests.MarkdownXshd_DeclaresNoVisualAttributes` pins it, since a re-added attribute would read as configuration while changing nothing. Comments in the file note deliberate regex constraints (e.g. "no wildcard quantifiers", "min 2 chars") — these were tuned to avoid catastrophic backtracking / crashes in AvalonEdit's regex engine, so preserve that style when editing rules (see commit "Fix syntax highlighting crashes and rearchitect line-level highlighting").
  - Bold and Italic are `<Span>` elements (not flat `<Rule>`s) specifically so a nested nested `<Rule>` inside each can recognize the *opposite* delimiter family wrapped inside it (`**_text_**`, `_**text**_`) and color it `BoldItalic` explicitly (not `Italic`/`Bold` alone — that would risk the nested match's color overriding, rather than combining with, the outer span's weight/style). Flat same-family nesting (`**text**` inside `**text**`) is still unsupported and out of scope — CommonMark itself requires mixing delimiter families to nest emphasis unambiguously, so this covers the real cases. `MarkdownXshdTests.MarkdownXshd_LoadsWithoutError` in `MDEdit.Tests` loads this file through AvalonEdit's real `HighlightingLoader` (not just a build-time XML check) so a malformed grammar fails `dotnet test` rather than only surfacing when a `.md` file is opened.
  - Bold/Italic/emphasis matching is single-line only — `<Rule>` elements (and the content-class patterns above) cannot cross line breaks; only `<Span>` supports `multiline="true"` (used for fenced code blocks/HTML comments). Making bold/italic span multiple lines would need converting them to multiline Spans and making `MarkdownLineColorizer`/the marker-hiding generators aware of spans that start on one line and end on another (they're currently strictly per-`DocumentLine`) — a materially bigger change than the mixed-nesting fix above, not yet done.
  - Highlighting is swapped based on file extension in `UpdateHighlighting(path)`: `.md`/`.markdown` get the Markdown XSHD, anything else (including `.txt`) gets no highlighting, per Requirements.md §4.
- **`Resources/AppIcon.ico` / `AppIcon.png`** — both are `<Resource>` items (WPF pack-URI-resolvable, distinct from the `EmbeddedResource` used for the XSHD grammar). The `.ico` (multi-res, generated from the `.png`) drives `<ApplicationIcon>` in the csproj and `MainWindow`'s titlebar icon; the `.png` is used only in `AboutWindow` for the reason noted above.
- **`Resources/ToolbarIcons.xaml`** — toolbar icon geometry (Requirements.md §8), a plain `ResourceDictionary` of `Geometry` resources sourced from Tabler Icons' outline set (tabler.io/icons, MIT licensed) — stroke geometry in a 24x24 viewBox, not filled silhouettes, which is why `MainWindow.xaml`'s implicit `Path` style in `ToolBar.Resources` sets `Stroke`/`StrokeThickness="2"`/round line caps rather than `Fill`, matching the source SVGs' own `stroke="currentColor" stroke-width="2"`. No explicit csproj entry needed — same as `Themes/*.xaml`, the SDK's default glob already treats every `.xaml` file as a `Page` item. Merged once into `App.xaml`'s `MergedDictionaries` alongside the theme dictionary, but — unlike it — never touched by `ThemeService.Apply`'s swap, which only matches sources named `Themes/Light.xaml`/`Dark.xaml`; icon geometry is theme-independent, only the `Stroke` brush (`DynamicResource AppChromeForegroundBrush`) changes with theme. Every formatting toolbar button now renders one of these instead of the `TextBlock` label it used to, including the WYSIWYG/Source `ToggleButton` — its `Path`'s `Data` and the button's `ToolTip` are set imperatively in `MainWindow.UpdateLivePreviewState()` rather than a XAML trigger (matching this codebase's existing pattern of syncing this button's checked state from code-behind, not native/declarative binding), and deliberately show the mode a click would switch *to*, not the current one: `IconEye` + "Toggle to WYSIWYG view" while in Source, `IconEyeClosed` + "Toggle to code view" while in WYSIWYG — a closed eye reads more clearly here than reusing the Inline Code button's `</>` glyph for an unrelated purpose on the same toolbar, which is what shipped first and was corrected. Highlight's icon uses the plain default `AppChromeForegroundBrush` stroke like every other icon here — it briefly pinned its own yellow accent color the way its old swatch `TextBlock` did, but that read as inconsistent once every button was an outline icon rather than a filled letter, so it was reverted to match the rest. What the old swatch's color *did* carry over is the swatch itself: the Highlight button's icon now sits inside a small `Border` (`x:Name="BtnHighlightSwatch"`) whose `Background` is set imperatively in `MainWindow.ApplyTheme()` from `EditorPreferences.HighlightBackgroundLight`/`Dark` (Requirements.md §6) — not a fixed color — so it always matches whatever the user picked in Preferences. It updates live on both a direct theme switch and a Preferences change, since `ApplyEditorPreferences` calls `ApplyTheme()` at the end of every run; this is the same imperative-property-push pattern `MarkdownLineColorizer`'s brushes already use, not a `DynamicResource`, since `EditorPreferences` values are settings data rather than static theme-dictionary entries. The WYSIWYG toggle also pins `Background`/`BorderBrush` to `Transparent` as local values, specifically to beat the Fluent theme's default `IsChecked` accent-color fill (`Application.ThemeMode` otherwise paints a checked `ToggleButton` with the OS accent color — purple on the machine this was found on) — a local value on the same property outranks the theme's own trigger/visual-state value in WPF's property precedence, which is why this works without needing to touch the Fluent template itself. `IconSettings` is the toolbar's trailing entry, in its own final section after every formatting group — its `Button` reuses `MenuPreferences_Click` directly as its `Click` handler rather than a wrapper method, since the two are meant to be identical actions (same dialog, same live-apply/save-on-close behavior), just reached from two places.
- **`Resources/SearchPanelStyle.xaml`** — the Find (Ctrl+F) panel's illegibility fix, and a real multi-cause bug worth understanding in full before touching this area again; three independent problems stacked on top of each other, each masking confirmation that the previous fix had actually worked. A full `Style`+`ControlTemplate` override for AvalonEdit's `SearchPanel` *and* its `DropDownButton`, replacing the fixed `SystemColors`/hardcoded PNG icons AvalonEdit's own default template uses (none of which track this app's theme) with the same look as everywhere else in the app; the built-in Prev/Next `Image` controls (`prev.png`/`next.png`) became the same Stroke-`Geometry`-`Path` convention `Resources/ToolbarIcons.xaml` uses. Only two named parts are load-bearing (`PART_searchTextBox`, `PART_dropdownPopup`, per `SearchPanel.OnApplyTemplate`); everything else was free to restyle, and everything themed got an `x:Name` for the reason below. Merged once in `App.xaml` alongside `ToolbarIcons.xaml`.
  1. **`DynamicResource` doesn't reliably resolve inside this template.** The colors written directly in this XAML are a fallback, not what actually works. **The real fix is `MainWindow.ApplySearchPanelColors()`**: it resolves each brush once via `this.FindResource(...)` (from `MainWindow` itself, properly connected to `Application.Resources`) and assigns it as a local value via `Template.FindName` — the same "resolve from a properly-connected element, then push as a local value" pattern `BtnHighlightSwatch`/`MarkdownLineColorizer`'s brushes already use elsewhere in this codebase.
  2. **Calling that push once, right after `SearchPanel.Install`, wasn't enough — confirmed live, not just inferred:** a temporary diagnostic (a one-time `MessageBox` dumping `_searchPanel.Style`/`Template`, whether named parts resolved, the actual resolved brush values, and `Application.Resources.MergedDictionaries`) showed everything was *already correct* at that point, yet the icons still rendered blank. Cause: `SearchPanel.Open()`/`Close()` (AvalonEdit's own source) add/remove the panel's adorner from the `TextArea`'s `AdornerLayer` on demand — `layer.Add(adorner)` only happens inside `Open()`, and `IsClosed = true` (the default, set at the end of `AttachInternal`) means the adorner isn't added to the layer at all until the user's first Ctrl+F. Anything pushed before that (window `Loaded`/`ContentRendered` were both tried) doesn't survive the adorner's later, first real connection. **The fix is `_searchPanel.IsVisibleChanged`**, which fires on every actual `Open()`/`Close()` — colors get re-pushed onto the panel that's actually about to render. (The separate `ApplyTheme()` call site still matters too, for a theme switch while Find is already open.)
  3. **Even with correct, high-contrast colors confirmed live** (a second diagnostic round showed a dark `Background` and a light icon `Stroke` — provably correct values), **the Prev/Next/Close buttons still rendered with no visible border and no visible icon, except on hover.** Cause: Fluent's default `Button` template apparently doesn't paint its `ContentPresenter` in the resting state at all — a "reveal on hover" design that has nothing to do with color. `DropDownButton`'s arrow was visible throughout this entire investigation for exactly one reason: it already had a fully custom `ControlTemplate`, never relying on Fluent's default. **The fix is `SearchPanelFlatButtonStyle`**, a plain `Border`+`ContentPresenter` template (no Fluent involvement at all) applied to all three buttons via `Style="{StaticResource SearchPanelFlatButtonStyle}"`.
  - `SearchPanelStyleTests` checks that every named part resolves via `Template.FindName` — a typo there wouldn't throw, `ApplySearchPanelColors` would just silently skip that element — but by design it can't catch causes 2 or 3: both only manifest in an actually-shown, actually-*opened* window with a real Fluent theme applied, which no headless test in this suite constructs. Diagnosing those took shipping temporary, self-removing `MessageBox` diagnostics and iterating with a person actually running the app — the standing rule that this project's own code isn't launched/driven for verification held throughout; a live diagnostic report from the user running it themselves is what the rule leaves room for instead.
  - **A second, separate bug found while investigating, worth keeping even though it wasn't the actual cause of the illegibility**: `SearchPanel.Install(Editor)`'s return value used to be discarded. `SearchPanel.RegisterCommands(CommandBindingCollection)` additionally exposes `FindNext`/`FindPrevious`/`CloseSearchPanel` on whatever `CommandBindings` collection it's given — useful if MDEdit ever wants to trigger Find from outside the panel itself (e.g. a future Edit menu entry) — but `SearchPanel.AttachInternal` already registers those same commands directly on the panel, so the panel's own buttons were never actually broken by this. Fixed anyway: `_searchPanel = SearchPanel.Install(Editor); _searchPanel.RegisterCommands(CommandBindings);`.
- **`MDEdit.csproj`** build-time targets worth knowing about beyond the Authenticode one above: `SetVersionFromGit` sets `<Version>` using the same scheme the ClickOnce publish script uses — `Major.Minor.Build` read from `build/published-version.txt`, Revision from the git commit count (so the About dialog's version matches the deployed ClickOnce version; see Version numbering above). Both halves fall back to the SDK default rather than failing the build when git or the file is unavailable. Also a plain `<AssemblyMetadata Include="BuildDate">` item stamps the current UTC time into the assembly on every build — needed because deterministic builds (the SDK default) zero out the PE header timestamp that used to serve this purpose. Three `<Content>` items ship files beside the exe: `samples\**\*.md` (the release notes), plus `..\THIRD-PARTY-NOTICES.md` and `..\LICENSE` linked in as `LICENSE.txt` — see the licensing paragraph under **Project** for why those two are an obligation rather than a convenience, and why `Link=` matters. `ClearStaleReleaseNotesReadOnly` exists purely to unblock local rebuilds: running the app from a build folder marks its copy of `ReleaseNotes.md` read-only (`MainWindow.EnsureReleaseNotesAreReadOnly`), and the next build's content-copy step can't overwrite that, failing with `MSB3021`. It runs `attrib -R` on `$(OutDir)samples\*.md` — not the `Attrib` MSBuild task, which isn't registered in the .NET SDK's default task set — and is deliberately hung on `BeforeTargets="_CopyOutOfDateSourceItemsToOutputDirectory"`, the specific target that performs this copy (confirmed with `dotnet build -v:n`), because neither `BeforeTargets="Build"` nor `"CopyFilesToOutputDirectory"` actually run early enough: `Build` has no tasks of its own, so a hook on it fires only after its whole dependency chain — including the real copy — has already completed. A real ClickOnce install never hits this in the first place, since every published version lands in a brand-new folder with no read-only baggage carried over from a previous run. `<UseWindowsForms>true</UseWindowsForms>` is there solely for `System.Windows.Forms.ColorDialog` in `PreferencesWindow.xaml.cs` — the native OS color picker has no WPF equivalent, and this needs no NuGet package, just the framework reference. It comes with a real gotcha, though: combined with `ImplicitUsings`, the SDK silently adds global usings for `System.Windows.Forms` and `System.Drawing`, which collide project-wide with WPF's own `Color`/`Brush`/`FontFamily` and even `MDEdit.Editing.SelectionRange` (WinForms has its own `SelectionRange` type) — every file that used those names unqualified stopped compiling. The fix is `<Using Remove="System.Windows.Forms" />` / `<Using Remove="System.Drawing" />` in the csproj, which suppresses just those two implicit usings; `PreferencesWindow.xaml.cs` fully qualifies `System.Windows.Forms.ColorDialog` and `System.Drawing.ColorTranslator` at the point of use instead.

### Live-preview constructs

Each construct's generator makes two independent choices: **reveal scope** (how much of the document has to contain the caret before the raw syntax comes back) and **replacement** (what gets rendered where the hidden characters were). In every case the characters still occupy their document offsets — selection, undo, and the saved file are unaffected; only rendering changes.

| Construct | Generator | Reveal scope | Replacement |
| --- | --- | --- | --- |
| Heading | `HeadingMarkerElementGenerator` | per-line | zero-size hide (`"# "` prefix) |
| Emphasis, highlight | `EmphasisMarkerElementGenerator` | per-span | zero-size hide (symmetric marker) |
| Link | `LinkMarkerElementGenerator` | per-span | zero-size hide (asymmetric prefix + suffix) — also handles reference-form and unresolvable images, and every remote image while View → Load Remote Images is off, i.e. every span `ImageElementGenerator` declines |
| Image | `ImageElementGenerator` | per-span | visible rendered element (the picture, natural size clamped by `MaxImageHeight`; drawn broken-image placeholder + alt text on load failure; loading placeholder while a remote fetch is in flight; unresolvable — and every remote image while the opt-in is off — declines to `LinkMarkerElementGenerator`) |
| Underline | `UnderlineMarkerElementGenerator` | per-span | zero-size hide (asymmetric `<u>` + `</u>`) |
| Emoji | `EmojiElementGenerator` | per-span | visible rendered element (the emoji character) |
| Code fence | `CodeBlockFenceElementGenerator` | per-block | zero-size hide (whole line) |
| Blockquote | `BlockquoteMarkerElementGenerator` | per-line | blank spacer, bar drawn by `BlockquoteAccentBarRenderer` |
| Bullet list | `BulletListMarkerElementGenerator` | per-line | visible rendered element ("•" glyph) |
| Task list | `TaskListMarkerElementGenerator` | per-line | visible **drawn** element (a checkbox, replacing bullet *and* box) |
| Numbered list | `NumberedListMarkerElementGenerator` | per-line | visible rendered element (same `"1. "` text, for indent only) |
| Table | `TableRowElementGenerator` | per-block | visible rendered element (whole line → fixed-width cells; delimiter row hidden; grid drawn by `TableGridRenderer`) |
| Horizontal rule | `HorizontalRuleElementGenerator` | per-line | whole-line zero-size hide; line drawn by `HorizontalRuleRenderer` |

**Image rendering (Requirements.md §5) was scoped in two phases, and both are now done** — local images (`ImageElementGenerator` + `ImagePathResolver`), then remote `http(s)://` images behind an opt-in (`RemoteImageLoader`):
- It was the first inline element that isn't text-sized: the containing line grows to fit the picture, which works because AvalonEdit measures inline objects with an *infinite* constraint and `InlineObjectRun` reports the object's height as its baseline — so `MaxHeight` on the WPF `Image` (`MaxImageHeight`, 300px) is the sizing clamp, natural size below it, and no line-height API is involved. A wide image doesn't word-wrap (no inline object can — same as a table row); the raw text is always reachable via the caret reveal.
- **The decline-vs-placeholder contract** is the one rule everything follows: `ImageElementGenerator` *declines* a span (falls through to `LinkMarkerElementGenerator`'s marker-hiding, exactly the pre-image rendering) whenever the target isn't its to render — any `scheme://` URL (including `file://`), a relative path with no document directory (an unsaved document's image is *unresolvable*, not missing — it may become right the moment the user saves), or an unparseable path. The drawn broken-image placeholder (Border + Polyline shapes per the task-list-checkbox precedent, alt text beside the icon, styled from `GlobalTextRunProperties` so it needs no theme wiring) is reserved for a genuinely *resolved* local path that failed to load. `ImagePathResolver.TryResolve` (pure, unit-tested) encodes the decline half: title/`<...>` stripping, a scheme regex (deliberately not `Uri.TryCreate`, which claims `C:\x.png` with scheme `c`), and `Path.GetFullPath` resolution.
- The two generators coordinate by **registration order, which is load-bearing**: `_imageGenerator` is registered immediately before `_linkMarkerGenerator` (both advertise an image span's `Start`; AvalonEdit breaks the tie by registration order), a rendered image consumes the whole `[Start, End)` span so the link generator never sees inside it, and a declined span falls through with zero changes needed in `LinkMarkerElementGenerator` itself.
- `FindLinkSpans` now carries `IsImage` + `Url` on `LinkSpan` (the `EmojiSpan` carry-the-payload precedent; `Url` is null for reference links, which are never rendered as images). `LinkPatterns` became the `EmphasisPatterns`-style tuple table to carry the flag.
- Decoded bitmaps are cached by resolved full path, frozen (shareable across visual lines — a fresh `Image` element per `ConstructElement` call is mandatory, since `TextView` takes inline objects as visual children). The cache is deliberately **not** `TextDocument.Version`-keyed like `TableRowElementGenerator`'s layout cache — that would re-decode every image on every keystroke; it clears only when `DocumentDirectory` changes, which is also how cached failures (null entries, so a missing file isn't re-probed per redraw) recover. Known v1 limitation: an image edited on disk won't refresh until a different document is opened. Oversized sources get `DecodePixelHeight = DecodeHeightCap` (2× the display clamp) — applied only when the source is taller, since unconditional decode-scaling would upscale small images.
- The document-path feed is the **sixth MainWindow wiring touchpoint** (the first generator fed anything from `FileService`): `UpdateHighlighting(path)` — already the single funnel for every path change — sets `_imageGenerator.DocumentDirectory` under a change-guard and forces a full `TextView.Redraw()` when it actually changed. The redraw is required, not defensive: Save As gives an unsaved document's relative images a base directory, and nothing else repaints then (verified — `ExecuteSaveAs` triggers no redraw when the extension didn't change).
- The colorizer needed nothing: revealed raw `![alt](path)` already gets the per-span mono-font swap because `ApplyRevealedSourceFont` consumes the same `FindLinkSpans`, and a rendered span has no visible text left to style.
- **Remote images are gated on `AppSettings.LoadRemoteImages` (View → Load Remote Images), off by default** — the explicit product call phase 2 was waiting on, since fetching a remote URL just from having the document open discloses to its host that it was opened (the tracking-pixel concern email clients guard against). The setting is **top-level, deliberately not in `EditorPreferences`**: that object is replaced wholesale by PreferencesWindow's Cancel/Reset, and a privacy setting must not be revertible by a dialog that never showed it. The menu item carries the rationale in a `ToolTip` — the only place it reaches the user.
- **The guarantee the design is built around: with the opt-in off, MDEdit issues no network request of any kind for a document's content.** That's structural, not a runtime check, and is checkable in three greps: `HttpClient`/`System.Net.Http` appear in **exactly one file** (`RemoteImageLoader.cs`); that class is instantiated exactly once (a field of `ImageElementGenerator` — grep the bare type name, not `new RemoteImageLoader`, since it is target-typed `= new()`); and its only fetch-initiating member `GetOrStartFetch` has **exactly one call site**, reachable only via `IsRenderable`, whose remote clause evaluates the `RemoteEnabled` gate *before* the URL is even parsed. Two supporting properties: turning the setting off calls `RemoteImageLoader.Invalidate()`, which cancels in-flight requests and drops every cached bitmap, so it takes effect immediately rather than at the next document open; and fetching is **viewport-bounded for free**, since AvalonEdit only runs generators for laid-out lines — a document with 200 remote images makes one request per image actually scrolled to, which is a privacy property, not just performance. `RemoteEnabled` is a *single* gate consulted from `IsRenderable` (itself the single shared gate for both generator entry points) — deliberately not a second flag on the loader, since two gates that must agree is a standing failure mode here.
- **The late-arrival problem and its fix.** AvalonEdit captures an inline object's `DesiredSize` at construction time, so a bitmap that arrives after `ConstructElement` returned cannot resize its own line — it has to ask for a redraw that re-runs `ConstructElement` against the now-populated cache. MainWindow **pushes** that as an `Action` (`_imageGenerator.RequestRedraw`, a pass-through to the loader) rather than the generator capturing `CurrentContext.TextView`: that's the imperative-property-push convention every other generator follows, and `CurrentContext` is non-null only *during* a construction pass. The redraw is **full-view, not per-line** — the loader is URL-keyed and knows no offsets, the document may have been edited and the span moved by completion time, and one URL can appear on several lines; a full redraw only re-runs generators for viewport lines, so its cost is bounded. Completions are **coalesced** into one redraw per burst by a queued flag posted at `DispatcherPriority.Background`: every `Normal`-priority cache write drains before any `Background` item runs, so N images finishing together cost exactly one redraw — deterministic, no timer interval to tune, and `Background` also guarantees the redraw can't re-enter an in-progress layout pass.
- **Staleness is handled by a generation counter plus a `CancellationTokenSource`**, both reset by `Invalidate()`, which is called from exactly two setters: `LoadRemoteImages` (**both** directions) and `DocumentDirectory`. A completion whose captured generation no longer matches is discarded entirely — no cache write, no redraw. Deliberately **not** called from the `Enabled` (live-preview) setter — live preview off is transient with unchanged URLs, so refetching on every WYSIWYG toggle would be a real regression — and **not** on document edits, since a version-keyed remote cache would refetch on every keystroke. In-flight dedupe is lock-free because the `InFlight` mark is written synchronously, on the UI thread, *before* the fetch starts; all cache mutation happens on the UI thread via `Dispatcher.BeginInvoke`, so no lock is needed anywhere. Every `await` takes `ConfigureAwait(false)` — without it the decode would resume on the UI thread and defeat the design, which is also exactly why the completion needs the explicit dispatcher post.
- The loading placeholder shares the broken one's frame, sizing and alt-text label exactly (so a loading box resolving to broken never changes line height) and differs by **shape, not colour** — three dots at 0.6 opacity instead of the mountains-and-slash — since colour is theme-driven and can't be assumed to contrast in both. Rejected for it: an animated spinner (the hosted object is rebuilt on every redraw and torn down on scroll, so the animation would restart constantly and put a running clock per visible image into the render loop), a literal "Loading…" string (competes with the alt text, needs localizing), and reserving `MaxImageHeight` of blank space (most images are shorter than the cap, so it shows a huge empty box for a small icon). `ImageElementGenerator.DecodeFrozen` is shared by both paths so local and remote can never drift on decode settings; freezing is what lets a bitmap built on a background thread cross to the UI thread, and it's `CanFreeze`-guarded because an unfrozen one throws at render time, far from the cause.
- Network hygiene worth preserving in `RemoteImageLoader.CreateClient`: one `static readonly HttpClient` (never per-request — socket exhaustion), `UseCookies = false` and credentials left unset so no cookie or Windows integrated auth is ever offered to a third-party host, an honest `MDEdit/<version>` User-Agent (**not** a spoofed browser one), a 10s timeout, and an 8 MiB cap enforced by **streaming** (`ResponseHeadersRead` → status → content type → `Content-Length` early reject → capped read) rather than `MaxResponseContentBufferSize` — headers-first rejection costs no body bytes, and it makes the cap a pure unit-testable static. A `Content-Length` is never used to pre-size the buffer; a lying header would be a memory-DoS vector.

Reveal scope drives the redraw work in `MainWindow.OnCaretPositionChanged`: per-line and per-span need only the old and new caret line redrawn (span-grained constructs additionally need `_lastCaretOffset`, not just `_lastCaretLine`, since a caret move within one line can cross a span boundary), while per-block is the one scope whose reveal region can sit far outside those two lines — hence `RedrawEnclosingFenceLines` and `RedrawEnclosingTableLines`.

**Adding another construct** — the established order of work:

1. Add detection to `Editing/MarkdownSyntax.cs` first, and unit-test it there (see the test-file table above). Never re-implement detection inside a generator or the colorizer.
2. Pick a reveal scope and replacement from the table above, matching an existing construct wherever the new one behaves the same way.
3. Write the generator in `Editing/` as a `VisualLineElementGenerator` with an `Enabled` flag and caret state, modeled on the closest existing one.
4. Register it on `Editor.TextArea.TextView.ElementGenerators` in `MainWindow`.
5. Flip its `Enabled` in `UpdateLivePreviewState()`.
6. Re-sync its caret state in `ResetLivePreviewCaretTracking()` — otherwise it renders against a stale caret after New/Open.
7. Update `OnCaretPositionChanged` only if the scope isn't line-local; a per-block construct needs its own enclosing-region redraw the way fences do.
8. If the construct also needs color/weight/size (not just marker hiding), that half belongs in `MarkdownLineColorizer`, consuming the same `MarkdownSyntax` method.

**The extended-syntax constructs** — how each maps onto the shapes above, covering both the ones already done and the ones still planned (see §Project). All of them fit, except one:

- **Highlight is done** (`==text==`) and confirmed the prediction: adding `(new Regex(@"\G={2}[^=\n]+={2}"), 2, true)` to `EmphasisPatterns` gave it per-span marker hiding through the existing `EmphasisMarkerElementGenerator` for free, and a `Highlight` color + rule in `Markdown.xshd` (plus a `DarkHighlightColors` entry) gave it the background. No new generator, no `MainWindow` caret/redraw wiring. **Prefer this route for any remaining symmetric inline marker** — a new generator is the wrong instinct there.
- **Superscript and subscript are done** (`X^2^`, `H~2~O`) and took the same free ride plus one addition: they needed the colorizer to style a *span* rather than a whole line, which it had never done. That required telling runs apart, and `MarkerLength` can't — `^`/`~` are one character, exactly like italic's `_`. Hence `EmphasisKind` on the pattern table and `FindScriptSpans`, which **shares `FindEmphasisSpans`' single scan** (both project from `ScanLine`) rather than re-parsing, so the baseline styling and the marker hiding can never disagree. The `~` vs `~~` collision is handled purely by pattern order — subscript sits *below* strikethrough in `EmphasisPatterns`, and moving it would silently break strikethrough, so `MarkdownSyntaxScriptTests` pins that.
- **Task lists are done**, as predicted a variant of the bullet-list generator — per-line reveal, visible rendered element. Three things about it that aren't obvious:
  - `TryGetTaskListMarker` bounds the bullet character *through* the closing `]` (all five characters of `- [ ]`), and the generator replaces that whole range with **one** checkbox glyph. `BulletListMarkerElementGenerator` therefore has to check for a task and return −1, otherwise a task line renders "• ☐ todo" — two markers for one construct. A task line genuinely *is* a bullet line, so the exclusion belongs in the generator, not in `TryGetBulletListMarker`.
  - **The checkbox is drawn (a `Border` plus a `Polyline` tick), not a glyph — don't "simplify" it back.** U+2610/U+2611 (☐/☑) were the first attempt and looked wrong in practice: the editor font carries neither, so WPF font fallback resolved each character independently and the two states came out visibly different sizes. Drawing makes both states identical by construction, removes the dependency on any font happening to have the glyphs, and still scales with `FontRenderingEmSize` and follows the theme's foreground brush. This is the only generator that draws shapes rather than hosting text; the reason is glyph availability, not preference.
  - The command is the first three-way one: `MarkdownFormatter.TaskListItem` toggles an existing task, adds `[ ] ` to a plain bullet (inserting the full prefix would give `- [ ] - foo`), and otherwise inserts `- [ ] `. Being a document mutation it lives in `MarkdownFormatter`, not in the generator.
- **Emoji is done** and was the first generator to pair *per-span* reveal with a *visible* replacement (`EmojiElementGenerator`) — the other visible-replacement generators are all per-line. Two things settled along the way that are easy to re-litigate by accident:
  - **The catalogue is what makes detection safe.** The BCL has no shortcode table, so one ships as an embedded `Resources/Emoji.txt` (curated ~240 entries, not the full ~1,800 — everything here is versioned in git and carried in the ClickOnce payload; extending it is a data edit, and no code depends on the size). Because only catalogued names count, `10:30:45` and `3:4:5` can never be mistaken for emoji — a stronger guarantee than the pattern-only constructs get, so **don't "simplify" this into a bare regex**.
  - **Emoji render monochrome, not in colour**, verified in this app: WPF's text stack has no COLR/CPAL colour-font support. That is a platform limit, not a bug to keep re-investigating; colour would need an image-based rendering route entirely. It's documented in Requirements.md §5 so users aren't surprised.
  - `FindEmojiSpans` skips only inline code (a shortcode in backticks is literal); it deliberately does *not* skip emphasis or links, so `**:joy:**` still renders — same container reasoning as `FindUnderlineSpans`. `InlineCodePattern` is shared with `EmphasisPatterns` rather than duplicated, and **must stay declared above it**: static fields initialize in declaration order, so moving it below leaves the emphasis table holding a null regex at runtime, not merely a warning.
- **The emoji picker is done** (`EmojiPickerWindow`, Format → Emoji / the toolbar's 🙂 button) and, like the picker, needed no new generator — it's a catalogue feature, not a rendering one. `EmojiCatalog` gained `All`, an ordered `IReadOnlyList<(string Shortcode, string Emoji)>` built in the same `Load()` pass as the lookup dictionary (not a projection of `Dictionary` enumeration order, which isn't a documented guarantee) — `TryGet`/`Count` are unchanged. The window is a pure chooser (no settings/document dependency): it's the third owned dialog after `AboutWindow`/`PreferencesWindow`, same `Owner` + `ShowDialog()` convention, but simpler — no Cancel/Reset snapshot logic, since nothing persists across a cancelled pick. It builds one `Button` per catalogue entry imperatively into a `WrapPanel`, filtered live by `SearchBox.TextChanged` (substring match on shortcode, not a parsed category from `Emoji.txt`'s `#` comments — out of scope for v1) — the same imperative-child-per-item convention as `PreferencesWindow.BuildColorGrid`/`MainWindow.RebuildRecentFilesMenu`, not an `ItemsControl`/`DataTemplate`. **Pick-and-close, not a stay-open session**: clicking an emoji (or pressing Enter over the filtered list) sets `SelectedShortcode`, closes the dialog, and `MainWindow.BtnEmoji_Click` inserts it via the new `MarkdownFormatter.InsertEmoji` — which replaces any existing selection outright (the `Table`/`CodeBlock` shape, not `Wrap`'s fold-in-place one) and leaves the caret positioned right after the shortcode, matching where it would land had the user typed it. This replaced the old `BtnEmoji_Click => WrapSelection(":", ":")` stand-in entirely, rather than living alongside it.
- **The one remaining emoji follow-on (§3)** is about the catalogue rather than about rendering, and doesn't need a new generator either:
  - *Convert emoji to shortcodes* — needs the **reverse** map, and that is not simply the catalogue inverted: aliases collide (`+1` and `thumbsup` both give 👍, `-1` and `thumbsdown` both 👎), so one shortcode per character has to win deterministically. First-listed-in-file is the natural rule, since `Emoji.txt` is hand-ordered with the preferred name first — decide it once in `EmojiCatalog` rather than at each call site. Note this is also the first feature here that *mutates* the document rather than detecting or rendering (everything in `Editing/` except `MarkdownFormatter` is read-only), so it belongs beside `MarkdownFormatter` and should apply as one batched change so a single Ctrl+Z undoes the whole conversion.
- **Underline is done, and is the odd one: it is not Markdown at all.** Markdown has no underline syntax in any dialect (underlining is reserved for links by convention), so Requirements.md §3 specs it as literal inline HTML — `<u>text</u>` — riding on Markdown's pass-through of inline HTML. It is the only formatting command that emits HTML. Its markers are **asymmetric** (`<u>` is 3 characters, `</u>` is 4), so `EmphasisSpan`'s symmetric `MarkerLength` can't describe it and the `EmphasisPatterns` free ride was unavailable: it needed `UnderlineSpan` (mirroring `LinkSpan`'s four offsets), `FindUnderlineSpans`, and `UnderlineMarkerElementGenerator` on `LinkMarkerElementGenerator`'s template, plus the full five-touchpoint MainWindow wiring. The underline *effect* is a one-line XSHD `<Color underline="true">` — `XshdColor.Underline` is supported, and `MarkdownXshdTests` proves the grammar still loads. Deliberately strict: lowercase `<u>` only, no attributes, no whitespace in the tag, and the content class stops at `<` so a nested tag ends the run — this editor does not parse HTML, and anything looser starts guessing.
  - Unlike the emphasis and link scanners, which skip past each other's matches, `FindUnderlineSpans` is **not** skip-aware and shouldn't be: underline is a *container*, not an opaque run, so `<u>**bold**</u>` is meant to keep its bold. Both scanners find their own runs independently, and their markers never share an offset, so the generators can't collide. Verified by tests in both directions.
- **Tables are done, and were the one construct that genuinely didn't fit the existing shapes** — a grid's column widths depend on every row, so the layout is a whole-table property rather than line- or span-local. The solution: `MarkdownSyntax` table detection, `TableRowElementGenerator` + `TableGridRenderer` (the blockquote generator/renderer split applied a second time — see their bullets above), and pipe/delimiter dimming in `MarkdownLineColorizer` reusing the hrule brushes. **Deliberately no XSHD rule**: XSHD matching is line-local and can't know whether a `|` line has a matching delimiter below it, so an XSHD table rule would color row-shaped prose — the same reason headings/blockquotes/hrules are colorizer-styled. Three v1 boundaries are deliberate, not oversights:
  - **Cell text renders verbatim** — inline markers inside a rendered cell stay visible, because the row element consumes the whole line and the inline generators never run there. That's also what makes the `FormattedText` width measurement *exact*. Nesting inline rendering into cells is the natural follow-up, and whoever does it must make measurement account for hidden markers, or columns will misalign.
  - **Reveal is whole-table.** Per-row Typora-style reveal was considered and deferred: with the rest of the table still rendered while one row is edited, every keystroke changes a column max-width and forces a whole-block redraw, and the raw row's text can't line up with the rendered columns anyway.
  - **A row wider than the viewport doesn't word-wrap** — a single inline object can't. The raw text is always reachable via the per-block reveal.
  - The insert-table *command* (§3) is done, independent of all of this — `MarkdownFormatter.Table` plus a Format-menu entry and a toolbar button (no keyboard shortcut, matching Link/Code Block/Code — none of the toolbar's insert commands have one), following the existing insert-and-position-caret convention: a 2-column, 3-body-row starter with "Header 1" selected for immediate typing, the same placeholder-selection idiom as `Link`'s "link text". One addition beyond that precedent: since `IsTableRowLine` requires each row to start at column 0, `Table` normalizes onto its own lines — a leading newline when the cursor isn't at the start of its line, a trailing one when it isn't at the end — so the table always renders correctly regardless of where the cursor was. `CodeBlock` has this same latent limitation and was deliberately left as-is; normalizing there too is out of scope here.

## Git workflow

- Before running `git commit` (and before `git push`), show the proposed commit message and wait for explicit confirmation — do not commit or push on the same turn as drafting the message without that check-in. Exception: once the user has given an explicit go-ahead (e.g. supplied the commit message themselves, or said "commit and push"), that covers the rest of that task, including any incidental fixes needed to actually complete it (e.g. a build error hit mid-publish) — don't stop to re-confirm those, just use a reasonable one-line message and proceed. Only a genuinely new/separate change needs fresh confirmation.
- Commit messages are one line only, unless the change is an extraordinary case that genuinely warrants a body.

## Conventions

- Nullable reference types are enabled; keep new code nullable-aware.
- File-scoped namespaces (`namespace MDEdit;`) are used throughout.
- Keep formatting-insertion behavior consistent with the "wrap selection / insert-and-position-caret" pattern already established for existing commands when adding new ones.
