# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MDEdit is a WPF desktop Markdown editor (.NET, `net10.0-windows`) built around the AvalonEdit text editor control. See `Requirements.md` for the full product spec (document management, editing, Markdown formatting commands, syntax highlighting, keyboard shortcuts, toolbar, status bar).

**Line-based commands operate on every line a selection touches** — `ToggleLinePrefix` (bullet/numbered/blockquote), `TaskListItem`, and `Heading` in `MarkdownFormatter`. Four things about that implementation are deliberate and easy to break:
- They iterate **line numbers, not offsets or `DocumentLine` references**, re-fetching each line inside the loop. That is only safe because none of these commands add or remove line breaks, so numbers stay valid across every edit; offsets do not. The loop runs **bottom-up** so an edit never shifts a line still to be visited.
- **Numbered lists have their own method, `NumberedList` — they cannot use `ToggleLinePrefix`.** That method applies one fixed string to every line, so `"1. "` came out as `1.` on all of them. `NumberedList` collects the target line numbers first and takes each marker from the target's *index*, so counting is independent of the bottom-up iteration; a line already numbered is renumbered in place rather than given a second marker. `MainWindow.BtnNumberList_Click` calls it directly — don't route it back through `InsertLinePrefix`.
- Multi-line selections **normalize rather than flip**: the prefix is removed only when *every* affected line already has it, otherwise it's added to the ones that lack it — so a mixed block becomes uniform and a second press clears it. `TaskListItem` follows the same rule and cycles plain → all unchecked → all checked. Per-line flipping would leave a mixed block permanently mixed.
- Blank lines inside a multi-line selection are skipped, but the **single-line paths deliberately don't skip them** — inserting `- ` on an empty line is how a list gets started.
- Each multi-line command wraps its edits in `doc.RunUpdate()`, which groups them into **one undo action**; without it a three-line change would take three Ctrl+Z presses. `SelectedLineNumbers` also excludes a line the selection merely ends *at* the start of, matching what the user sees highlighted.

Several things are spec'd in Requirements.md but marked *(planned)* — **not yet implemented, and not bugs**: a Preferences window (View → Preferences, §6) for customizing the WYSIWYG/code fonts and the text/background colors of formatted spans — currently all fixed (Arial, the mono stack, and the per-theme brushes in `MarkdownLineColorizer`/`Markdown.xshd`) — with a Reset to Default action restoring all of it in one step, proper toolbar icons in place of today's plain text/symbol labels — possibly via an icon font such as Font Awesome (§8) — and two §3 items — an **emoji picker** and a **convert-emoji-to-shortcodes** command. Neither of the §3 items needs a new generator: both are catalogue work (see below). Highlight `==text==` was the first *extended* construct to land, and is the worked example: it needed **no new generator at all**, only a pattern added to `EmphasisPatterns` plus an XSHD color/rule, because its shape is identical to the emphasis family's.

Two Markdown documents exist for this, in different projects because they serve different purposes:

- **`MDEdit/samples/ReleaseNotes.md`** — the product introduction, and the **user-facing changelog**: its "Recent changes" section is updated before every publish (see **Publishing a new version** under ClickOnce deployment below — this is a standing requirement, not a nicety), **one short entry per published release, never one per commit**, with each release's changes as a bullet list rather than one paragraph. Deliberately written using only constructs MDEdit supports *today* so it renders correctly in WYSIWYG — no tables, task lists, or emoji. Keep it to what is *distinctive* about MDEdit: the greeting is a short "thanks for installing" line, not a feature tour — there is no usage/keyboard-shortcut/file-association walkthrough here, so don't reintroduce that kind of content when adding changelog entries. `MDEdit.csproj` ships it via `<Content Include="samples\**\*.md" CopyToOutputDirectory="PreserveNewest" />`, so it lands in `samples\` beside the exe and ClickOnce carries it in the payload, at `MainWindow.GetReleaseNotesPath()`'s `Path.Combine(AppContext.BaseDirectory, "samples", "ReleaseNotes.md")` — confirmed against a real ClickOnce publish log to land in the same relative place in the deployed version folder.

Requirements.md §10's first-run behavior is implemented: `MainWindow`'s constructor calls `MaybeShowReleaseNotesOnFirstRun()` whenever there's no file-association/command-line argument to open instead (that always wins — the `if (args.Length > 1) OpenFile(args[1]) else MaybeShowReleaseNotesOnFirstRun()` split). It shows the page once per **release**, comparing only `Major.Minor.Build` against `AppSettings.LastReleaseNotesVersionShown` via `Editing/ReleaseNotesGate.cs` (`GetReleaseVersion`/`ShouldShow`, unit-tested in `ReleaseNotesGateTests`) — deliberately never the full 4-part version or `Revision` alone, since per the versioning scheme above, `Revision` can repeat across different actual releases and would make the comparison unreliable in either direction. The "last shown" value is persisted *before* attempting to open the file, so a missing or unreadable `ReleaseNotes.md` fails silently exactly once per release rather than retrying on every launch forever. Help → Release Notes (`MenuOpenReleaseNotes_Click`) reaches it on demand, behaving exactly like File → Open (`CheckUnsavedChanges` guard, joins Recent Files, shows errors normally) — unlike the auto-open path, which passes `OpenFile`'s new `addToRecentFiles`/`showErrorOnFailure` parameters as `false` for both, since an automatic open on startup is not a user-initiated action and must neither clutter the MRU list nor pop an error dialog on first launch.

**The Save-As-instead-of-overwrite protection was deliberately rejected in favor of marking the installed file read-only via the OS attribute** (`MainWindow.EnsureReleaseNotesAreReadOnly`, called at both open sites, idempotent) — not the ClickOnce build/publish pipeline: whether attributes survive ClickOnce's deploy mechanism (which renames payload files to `*.deploy` and reconstructs them on the client) is unverified and not worth depending on, whereas applying it at open time is cheap, self-heals after every update (each new version lands in a fresh folder with default attributes), and needed zero publish-script changes. This composes for free with existing code: `FileService.Save`'s `File.WriteAllText` already throws `UnauthorizedAccessException` on a read-only file, so `ExecuteSave`'s `catch` only needed one new `catch (UnauthorizedAccessException)` clause ahead of the generic one, giving a message that points at Save As instead of surfacing the raw OS "Access to the path is denied" text.
- **`MDEdit.Tests/TestData/markdown-conformance-test.md`** — a standards-based CommonMark + extensions document written to the spec rather than to this implementation, so it deliberately contains constructs MDEdit does not support (setext headings, indented code blocks, reference links, footnotes, definition lists, H4–H6, multi-line emphasis). Its purpose is finding gaps, whether read by a future functional test or opened by hand. `MDEdit.Tests.csproj` copies `TestData\**\*.md` to the output directory, so a test can read it relative to its own working directory. **It relies on significant trailing whitespace** (two-space hard breaks in §2 and §21) — don't reformat it, and be aware that editing it in MDEdit and saving may strip those.

WYSIWYG is implemented as a **live-preview mode inside AvalonEdit itself** — not a WebView2/rendered-HTML view. The Markdown text is always the single source of truth; the toggle (View → Editor Mode → WYSIWYG) only changes how AvalonEdit *renders* that same text (larger heading fonts, syntax markers hidden except where the caret is). This was a deliberate choice over a `contenteditable`/WebView2 approach specifically to avoid a lossy HTML→Markdown round-trip — there is no round-trip, so there's nothing to lose. A WebView2 *read-only* rendered preview pane remains a possible separate future addition, not a replacement for this.

Every construct Requirements.md lists as *implemented* is covered, tables included; what remains from §3 are commands and catalogue features, not rendering. See **Live-preview constructs** at the end of Architecture below for the per-construct reveal-scope/replacement map and the checklist for adding another; the mechanism is built incrementally, one construct at a time.

## Build & Run

```
dotnet build MDEdit.slnx
dotnet run --project MDEdit/MDEdit.csproj
dotnet test MDEdit.slnx
dotnet test MDEdit.slnx --filter "FullyQualifiedName~MarkdownFormatterTests"   # single class; ~MethodName works too
```

`MDEdit.Tests` (xUnit, `net10.0-windows` — it needs the WPF-targeted AvalonEdit assembly) covers the logic pulled out of `MainWindow.xaml.cs` into `MDEdit/Editing/` specifically so it's testable without a running window: `MarkdownFormatter` (formatting commands), `MarkdownSyntax` (line-construct detection), `RecentFiles` (MRU list logic), and `StatusFormatter` (status-bar number formatting) — plus `Markdown.xshd`, loaded through AvalonEdit's real `HighlightingLoader`. `MDEdit.csproj` grants it `InternalsVisibleTo` so those `internal` classes are testable directly. Running `dotnet test` is fine to do yourself; do not launch/drive the actual GUI app to verify behavior — that's for the user to do and report back.

Release builds (`dotnet build -c Release` / `dotnet publish -c Release`) are Authenticode-signed automatically via an `AfterTargets="Build"` MSBuild target in `MDEdit.csproj` that runs `build/Sign.ps1`. It signs with whatever cert matches subject `CN=Maze Code Signing` in the CurrentUser store (matched by subject, not thumbprint, since the cert rotates yearly) and timestamps against `http://timestamp.digicert.com`. This requires network access and the cert being present — Release builds will fail without them. Debug builds are unaffected.

### ClickOnce deployment

`docs/` is a live GitHub Pages site (`https://cowwarrior.github.io/MDEdit/`) serving a ClickOnce deployment — this is why the repo is public rather than private.

### Version numbering

Versions are 4-part `Major.Minor.Build.Revision`, split between a value stored in the repo and one derived from git:

| Part | Source | Moves when |
| --- | --- | --- |
| Major | `build/published-version.txt` | `Publish-ClickOnce.ps1 -BumpMajor` (resets Minor and Build to 0) |
| Minor | `build/published-version.txt` | `Publish-ClickOnce.ps1 -BumpMinor` (resets Build to 0) |
| Build | `build/published-version.txt` | **every publish** |
| Revision | `git rev-list --count HEAD` | every commit — **never reset by anything** |

`build/published-version.txt` holds the `Major.Minor.Build` of the **last published** release (not the next one). The script increments it, publishes, and writes the new value back only on success — so a failed publish doesn't silently consume a number. Revision is never reset by a Major/Minor bump specifically so the 4-part version keeps increasing no matter what happens to the stored parts: a version that fails to increase strands installed clients on the old build with no error shown anywhere, which this project has already been bitten by once (see the `FormatVersion` note below).

**The publish script must pass `-p:MDEditReleaseVersion=<Major.Minor.Build>` to MSBuild, and this is not optional.** `published-version.txt` deliberately lags — it records the *last* published release and is written back only after a successful publish — so during a publish it still holds the previous value. Without the override, `SetVersionFromGit` reads that stale file and stamps the **assembly** one release behind the **deployment manifest**, which takes its version from `ApplicationVersion` instead. That shipped once: deployment `1.0.1.49` carrying an assembly reporting `1.0.0.49`, so the installed About dialog disagreed with the version ClickOnce had actually installed. ClickOnce updates still worked (they key off the manifest), which is exactly why it was easy to miss. Ordinary builds pass nothing and correctly fall back to the file.

Two consequences worth knowing. Two publishes with no commits between them repeat the Revision (`1.0.1.49`, `1.0.2.49`) — still increasing overall, because Build moved. And a local build reports the *last published* `Major.Minor.Build` with the current commit count, so it matches the shipped version exactly at the publish commit and drifts only in Revision afterwards.

**Publishing a new version — the required order:**

1. **Update `MDEdit/samples/ReleaseNotes.md`'s "Recent changes" section first**, before running the publish script. Add a `### Version <Major.Minor.Build>` block — the *release* number only, no Revision — for the version about to be published, newest first.
   - **One entry per published release, never per commit.** Several commits' worth of work collapse into a single entry; unpublished work accumulates into the next release's entry rather than getting its own. Revision numbers gap between releases and that is expected.
   - **Keep it to one or two short sentences.** Name what was added; skip the how-it-works, the syntax tour, and the caveats — those belong in the body of the document, if anywhere. A changelog nobody finishes reading is worse than none.
   - Write for users, in the document's voice, using only constructs MDEdit renders today.
   - Changes with no user-visible effect (refactors, tests, doc edits) don't belong there at all.
   - `git log --oneline` since the commit that last touched `build/published-version.txt` is the starting point — that commit *is* the previous publish — but don't paste commit subjects verbatim.
2. Commit that with the feature work. It ships in the payload (see the `Content` item in `MDEdit.csproj`), so it must be right before the script runs. **Commit before publishing** either way: Revision comes from the commit count, so publishing first stamps a version that excludes the work.
3. Run `build/Publish-ClickOnce.ps1` (standalone — see below), adding `-BumpMinor` or `-BumpMajor` when asked for one.
4. Commit and push the changes under `docs/` **plus `build/published-version.txt`**, conventionally `Publish ClickOnce version <full 4-part version>`.

- The script must be run standalone (not via `dotnet publish`): ClickOnce's `UpdateManifest` task only runs under the full-framework MSBuild bundled with Visual Studio (`MSBuild.exe`, located dynamically), not the cross-platform MSBuild `dotnet` uses (fails with MSB4803 otherwise).
- ClickOnce manifest signing (the separate XML-DSig signature over `MDEdit.application`/`*.manifest`, distinct from the Authenticode signing above) requires an RSA certificate — the same `CN=Maze Code Signing` cert is used, resolved by subject at publish time, never by thumbprint (it rotates).
- The publish script assembles `ApplicationVersion` as `<stored Major.Minor.Build>.<git rev-list --count HEAD>` (see Version numbering above) and passes the full 4-part version directly — **not** via the separate `ApplicationRevision` property. This MSBuild's `FormatVersion` task (`Microsoft.Build.Tasks.Core.dll`, VS 18) silently ignores `Revision` regardless of how many parts `ApplicationVersion` has, so every publish would otherwise produce the identical version `1.0.0.0` and installed clients would never see an update (verified empirically — confirmed and fixed after finding this in practice).
- The deploy is framework-dependent (`SelfContained=false`) — self-contained ClickOnce output is ~350MB, impractical to version in git. This means machines installing MDEdit need the [.NET 10 Desktop Runtime](https://dotnet.microsoft.com/download/dotnet/10.0) already present; there's no bootstrapper to auto-install it.
- `MDEdit/Properties/PublishProfiles/ClickOnce.pubxml` holds the static settings (URLs, product/publisher name, `SelfContained=false`, etc). It deliberately omits `ManifestCertificateThumbprint` and `ApplicationRevision` — the script supplies both at publish time.
- The script also deletes any `Application Files\MDEdit_*` folder under `docs/` other than the one it just published — ClickOnce publish only ever adds a version folder, never removes superseded ones.
- `.gitattributes` marks everything under `docs/` as binary (`-text`) except `*.html` — git's CRLF normalization would otherwise corrupt the byte-exact hashes ClickOnce embeds in the manifest.
- `docs/index.html` is the hand-maintained install landing page (the only file under `docs/` not regenerated by publish); it links to `MDEdit.application` and notes the .NET 10 Desktop Runtime prerequisite — update it by hand if install instructions change.
- **The pubxml's `FileAssociation` items (`.md`/`.markdown`/`.txt`) do nothing** — verified empirically (no registry keys or event-log activity at all after a fresh install) that ClickOnce's file-association registration was never wired up for Launcher-based .NET Core deployments, despite the tooling accepting the declaration without error. Real file association is handled entirely by `Services/FileAssociationService.cs` instead (see Architecture below); the pubxml entries are dead config left in place mostly as a documented dead end, not because anything depends on them.

## Architecture

The app is a single-window WPF application; almost all logic lives directly in `MainWindow.xaml.cs` rather than being split across MVVM layers — there is no ViewModel.

- **`MainWindow.xaml` / `MainWindow.xaml.cs`** — the entire UI (menu, toolbar, status bar, editor) and its code-behind. Command routing uses standard WPF `RoutedUICommand`s (`ApplicationCommands.New/Open/Save/...`) plus custom ones declared as `static readonly RoutedUICommand` fields (`SaveAsCommand`, `BoldCommand`, `ItalicCommand`) for actions with no WPF built-in. Heading shortcuts (Ctrl+1/2/3) and the Word-compatible subscript/superscript shortcuts (Ctrl+Shift+`_` / Ctrl+Shift+`+`, i.e. `Key.OemMinus`/`Key.OemPlus` with Control+Shift — both characters are already Shift-ed) are wired in `RegisterKeyBindings` via `InputBindings` + a local `RelayCommand` rather than `CommandBinding`, since there's no built-in command for them. Their menu `InputGestureText` is written by hand in XAML: WPF fills that in automatically only for a `RoutedUICommand`'s own gestures, never for `InputBindings`.
  - **`ReleaseConflictingEditorGestures()` must run before those bindings, and is not optional.** AvalonEdit declares gestures on its own editing commands — **Ctrl+I** is `IndentSelection` and **Ctrl+U** is `ConvertToLowercase` — and those resolve against the `TextArea`, which sits nearer the keyboard focus than this window, so they silently swallow the keystroke and MDEdit's Italic and Underline never fire. Ctrl+B was unaffected only because AvalonEdit claims no Ctrl+B, which is what made the failure look arbitrary. The fix clears those two commands' `InputGestures`; neither is exposed in MDEdit's UI. **Check this list before adding any new Ctrl-shortcut** — AvalonEdit also claims Ctrl+D (`DeleteLine`), Ctrl+Shift+U (`ConvertToUppercase`), and Insert (`ToggleOverstrike`), none of which MDEdit currently uses.
  - Formatting operations (bold/italic/strikethrough/code = `WrapSelection`; headings = `InsertHeading`; lists/blockquote = `InsertLinePrefix`; code block = `InsertCodeBlock`; links = `InsertLink`) all follow the same convention described in Requirements.md §3: wrap the selection if there is one, otherwise insert placeholder syntax and position the caret/selection for immediate typing. These are now thin wrappers around `Editing/MarkdownFormatter.cs` (see below); MainWindow just supplies the `TextDocument` + current selection and applies the returned caret/selection placement via `ApplyFormat`, which sets it with a single `Editor.Select(start, length)` call — not separate `SelectionStart`/`SelectionLength` assignments, since `TextEditor.SelectionStart`'s setter internally reuses whatever `SelectionLength` currently reports, which can be a stale, now-out-of-bounds value left over from AvalonEdit's selection-anchor bookkeeping after `MarkdownFormatter`'s `doc.Replace` (reproducible by wrapping a selection that reaches end-of-document; caused a real `ArgumentOutOfRangeException` crash, fixed and covered by `ApplyFormatSelectionTests`).
  - Live preview / WYSIWYG state: `_settings.LivePreview` (persisted) drives `UpdateLivePreviewState()`, which swaps `Editor.FontFamily` between the XAML mono stack (captured once into `_sourceFontFamily`, never duplicated in code) and `WysiwygFontFamily` (Arial — prose reads as a document in WYSIWYG; the two fields sit side by side as the seam for the planned §6 font picker), and flips `MarkdownLineColorizer.LivePreviewEnabled`, `HeadingMarkerElementGenerator.Enabled`, `EmphasisMarkerElementGenerator.Enabled`, `CodeBlockFenceElementGenerator.Enabled`, `LinkMarkerElementGenerator.Enabled`, `UnderlineMarkerElementGenerator.Enabled`, `EmojiElementGenerator.Enabled`, `BlockquoteMarkerElementGenerator.Enabled`, `BulletListMarkerElementGenerator.Enabled`, `TaskListMarkerElementGenerator.Enabled`, `NumberedListMarkerElementGenerator.Enabled`, `TableRowElementGenerator.Enabled`, `HorizontalRuleElementGenerator.Enabled`, `BlockquoteAccentBarRenderer.Enabled`, `TableGridRenderer.Enabled`, and `HorizontalRuleRenderer.Enabled`, and syncs the View → Editor Mode radio-style menu checkmarks (`MenuEditorModeSource`/`MenuEditorModeWysiwyg`, set manually like the Theme submenu — no native radio-group support used elsewhere in this codebase either) plus the toolbar's own `BtnEditorModeToggle` (a `ToggleButton`, the toolbar's first section, ahead of a `Separator` and every other group — the only stateful toggle on the toolbar, everywhere else being one-shot commands). Its `Click` handler (`BtnEditorModeToggle_Click`) reads back `IsChecked` rather than tracking a separate flag: WPF flips a `ToggleButton`'s `IsChecked` before raising `Click`, so by the time the handler runs it already holds the state the click just asked for, the same as the two Editor Mode menu handlers apply a fixed value each. `OnCaretPositionChanged` tracks both `_lastCaretLine` (heading, code-fence, blockquote, bullet-list, task-list, and horizontal-rule reveal, line-grained) and `_lastCaretOffset` (emphasis, link, underline, and emoji reveal, span-grained — a caret move within the same line can still move into/out of one of those runs) and redraws just the old and new line via `TextView.Redraw(DocumentLine)` whenever the offset changes at all; generator state is updated *before* those redraws so both lines render against the new caret position. Code-block fences and tables are the exceptions to "just the old/new caret line" — both are per-block constructs whose reveal region can sit well outside those two lines — so `OnCaretPositionChanged` additionally calls `RedrawEnclosingFenceLines()` (redraws just the block's two fence lines, the only lines whose appearance changes there) and `RedrawEnclosingTableLines()` (redraws the *whole* block — crossing a table's boundary flips every row between grid and raw source) for both the old and new caret line. Blockquotes and horizontal rules deliberately do *not* get this block-wide treatment despite the accent bar/drawn rule sharing the reserve-hide/draw-separately split with fences and tables — only the caret's own line reveals its raw text, matching the simpler per-line pattern; a horizontal rule occupies exactly one line to begin with, so there is no block to redraw beyond it. `ResetLivePreviewCaretTracking()` re-syncs all twelve generators after `NewDocument`/`OpenFile` reset the caret to line 1 (called wherever `UpdateHighlighting` is, for the same "just loaded a different document" reason).
  - Document dirty-state (`_isDirty`), title bar, and status bar text are kept in sync through `MarkDirty()` / `UpdateTitle()` / `UpdateStatusBar()` / `UpdateDocumentStats()`, called after edits, caret moves, and file operations.
  - **The status bar is a plain `Border` + `Grid`, deliberately not `StatusBar`/`StatusBarItem` — don't "restore" the proper control.** The themed one rendered *no text at all*, in either theme: this app opts into the experimental Fluent `ThemeMode` (see `ThemeService`), and Fluent's `StatusBarItem` wants more vertical room than the fixed `Height="22"` allowed, so the content was clipped away entirely. Symptom is total invisibility, including literal XAML text, which makes it look like a data-binding or layout-docking bug and sends you the wrong way — the docking was fine throughout (the editor `Border` follows the status bar in the root `DockPanel`, so the editor is the `LastChildFill` child and `Dock="Bottom"` works). Two details keep it working: `MinHeight` rather than `Height`, so content can never be clipped again; and `TextElement.Foreground` rather than `Foreground`, because `Border` has no `Foreground` property and the plain form silently does nothing. The divider line above it comes from the editor `Border`'s `BorderThickness="0,1"`, not from the status bar.
  - Status bar (Requirements.md §9) is split into **two** update methods on purpose. `UpdateStatusBar()` does caret position and selection size — cheap, and it runs on every caret move. `UpdateDocumentStats()` does size and character count, which means walking the whole document for a UTF-8 byte count, so it runs only on `TextChanged` and once at construction. **Don't merge them**: putting the byte count on the caret path would materialize `Document.Text` on every arrow-key press. Selection is additionally hooked to `TextArea.SelectionChanged`, because a selection can change without the caret moving. The byte count is the size a *save* would produce — it includes `Encoding.UTF8.GetPreamble().Length`, since `FileService` writes through `File.WriteAllText`, which emits the BOM; without that it would disagree with Explorer by exactly 3 bytes. The filename and dirty marker are deliberately absent from the status bar (the title bar has both). The character count itself goes through `Editing/CharacterCounter.Count`, not raw `Editor.Document.TextLength`, so it can charge each line break a user-chosen weight (`AppSettings.LineBreakCharWeight`, 0/1/2, set from View → Line Breaks Count — `MainWindow.SetLineBreakCharWeight`/`ApplyLineBreakCharWeight`) instead of whatever that line break actually is in the raw text. The computation sums each `DocumentLine.DelimiterLength` (0, 1, or 2 — an LF, a CRLF, or none) across the document, subtracts that real total from `TextLength`, and adds back `lineBreakCount * weight` — so mixed line endings in one document (an LF-only line next to a CRLF one) are still charged identically under one weight, rather than each keeping its own actual width. Default is 2, matching a literal CRLF, so upgrading from a version without this setting doesn't change what's displayed.
  - `CheckUnsavedChanges()` is the single choke point for the "save/discard/cancel" prompt required before New, Open, and window Close.
  - The constructor checks `Environment.GetCommandLineArgs()` for a file path (`args[1]`) and opens it via `OpenFile(path)` — needed because `FileAssociationService` launches MDEdit as `"MDEdit.exe" "%1"`; without this, double-clicking an associated file opened an empty window.
  - `ApplySettings()` applies loaded `AppSettings` (word wrap, line numbers) on startup; the corresponding menu click handlers save back to `SettingsService` immediately on toggle, not just on close.
  - MRU (File → Recent Files, Requirements.md §1): the list is `AppSettings.RecentFiles` (persisted), the list *logic* is `Editing/RecentFiles.cs` (pure, unit-tested), and the menu is built at runtime by `RebuildRecentFilesMenu()` — `MenuRecentFiles` is declared empty in XAML and its items are cleared and regenerated on every change, so there is nothing static to keep in sync. Entries are added by `AddToRecentFiles`, called from `OpenFile` (inside the `try`, so a file that failed to open never lands in the list) and from `ExecuteSaveAs`; plain `Save` doesn't, since that path is already in the list. `OpenRecentFile` checks `File.Exists` *before* `CheckUnsavedChanges` — a stale entry shouldn't make the user answer a save prompt for a file that isn't there — and offers to drop the entry when missing. Two details worth preserving when editing the menu build: file names are inserted with `"_"` doubled (WPF eats a single underscore as an access-key marker, mangling names like `my_notes.md`), and the full path goes in the `ToolTip` since file names alone are frequently ambiguous. `ApplySettings()` runs the persisted list through `RecentFiles.Sanitize` rather than trusting it — `settings.json` is hand-editable, and the cap may have changed between versions.
- **`AboutWindow.xaml` / `.xaml.cs`** — small owned dialog for Help → About. - **`MarkdownLineColorizer.cs`** — an AvalonEdit `DocumentColorizingTransformer` registered on `Editor.TextArea.TextView.LineTransformers`. Handles *line-level* styling that XSHD span/rule matching can't express well: heading color/weight by `#` count, blockquote italics (via `MarkdownSyntax.TryGetBlockquoteMarkerLength`, shared with `BlockquoteMarkerElementGenerator` so the two never disagree on what counts as a blockquote line), horizontal rules (`LightHRuleBrush`/`DarkHRuleBrush` are `internal`, not `private`, specifically so `HorizontalRuleRenderer` can draw the WYSIWYG rule in the exact same color as the raw text revealed under the caret). This runs alongside (not instead of) the XSHD highlighting below, and none of it is gated by `LivePreviewEnabled` except the heading font scaling noted next — headings/blockquotes/hrules are colored this way regardless of editor mode. When `LivePreviewEnabled` is set, headings are additionally scaled up in `FontRenderingEmSize` per level (`HeadingScale`) — Typora-style larger heading text; this is purely a rendering effect via `ChangeLinePart`, the underlying document text is untouched. This class also owns the **revealed-source font swap** (`ApplyRevealedSourceFont`, live-preview-gated, fed `CaretLine`/`CaretOffset` + `SourceFontFamily` by MainWindow): revealed markdown renders in the mono source font, at two grains matching the reveal scopes exactly — **whole line** for the caret's line when it carries a line-scoped construct (heading/blockquote/bullet/task/numbered/horizontal-rule) and for every line of a table whose block contains the caret; **per span** for whichever inline runs the caret is inside on its own line (emphasis, links, underline, emoji), using the same inclusive-of-both-edges rule as the marker generators so the mono region and the revealed markers can never disagree. The per-span swap is acceptable precisely because the span's layout already shifts at that same instant (its markers appear) — the font change rides the same transition; plain prose lines deliberately stay in the document font so paragraphs don't jiggle while arrowing through them. It runs *before* the color/weight styling, which rebuilds each run's `Typeface` from its current family and so preserves the swap. Code needs nothing here — `Markdown.xshd`'s `InlineCode`/`CodeBlock` colors pin `fontFamily` to the mono stack in every mode (AvalonEdit's `HighlightingColorizer.ApplyColorToElement` applies `HighlightingColor.FontFamily` at render time — verified against its source), which is the entire reason the WYSIWYG font flip needs no code-block handling anywhere. `StyleScriptSpans` is the one *span*-level thing this class does (everything else styles a whole line): it raises/lowers superscript and subscript content via `SetBaselineAlignment` and shrinks it by `ScriptScale`, and is deliberately **not** gated on `LivePreviewEnabled` — the baseline shift *is* the construct, the same way bold renders bold in source mode. Heading/blockquote/hrule lines `return` before reaching it, so a script inside one of those renders plain; that's accepted, since those lines style themselves as a single unit and a later per-span change would fight the line-wide typeface.
- **`Editing/` folder** — UI-free classes factored out specifically to be unit-testable (see `MDEdit.Tests` above) and to anchor the live-preview implementation. The generator bullets below explain each construct in detail; **Live-preview constructs** at the end of this section summarizes them in one table and gives the checklist for adding a new one:
  - **`StatusFormatter.cs`** — status-bar number formatting (`FormatFileSize`/`FormatCharacterCount`/`FormatSelectionCount`). Each takes an optional `IFormatProvider` defaulting to `CurrentCulture`, so the UI localizes the decimal separator and thousands grouping while tests pin `InvariantCulture`.
  - **`RecentFiles.cs`** — MRU list transformations (`Add`/`Remove`/`Sanitize`), returning a new `List<string>` rather than mutating, with `MaxEntries` as the single cap. Paths are normalized with `Path.GetFullPath` and compared `OrdinalIgnoreCase` so one file reached by different spellings (case, `.`/`..`, a relative command-line argument) collapses to one entry. Persistence and the menu belong to MainWindow; this file is pure list logic, covered by `RecentFilesTests`.
  - **`MarkdownFormatter.cs`** — the actual logic behind every formatting command (`Wrap`, `Heading`, `ToggleLinePrefix`, `CodeBlock`, `Link`, `Table`), operating on an AvalonEdit `TextDocument` plus a plain `SelectionRange` struct rather than the live `TextEditor`, so tests can drive it without a window.
  - **`MarkdownSyntax.cs`** — shared line-construct detection. `MarkdownLineColorizer` (coloring/sizing) and the marker-hiding generators both call into this rather than each having their own regex/parsing, specifically so they can never disagree about what counts as a given construct. **Extend this file first when adding live-preview support for another construct** — colorizer and generator(s) should both consume it.
    - **Block constructs** — `TryGetHeadingLevel` (ATX heading + marker length); `TryGetBlockquoteMarkerLength` (leading `` `>` `` run, including nested `` `> > ` ``, plus a `depth` out param — the nesting level, used to draw one indent bar per level; see the `BlockquoteMarkerElementGenerator` bullet below); `IsFenceDelimiterLine`/`TryGetEnclosingFenceBlock` (fenced-code-block detection — see the `CodeBlockFenceElementGenerator` bullet below); `IsHorizontalRule` (whole-line `---`/`* * *` detection — moved here from `MarkdownLineColorizer`'s private helper so bullet detection can exclude hrule lines using the exact same definition the colorizer styles them with); the table family — `IsTableRowLine`/`IsTableDelimiterLine` (deliberately stricter than GFM: both outer pipes required at column 0, three-dash minimum in delimiter cells — "a | b" prose must never render as a table row), `TryGetTableBlock` (header + directly-adjacent delimiter with matching cell count + every contiguous row line below; the *topmost* valid header in the contiguous run wins, so row-shaped prose sitting above a real table is excluded rather than poisoning the pairing), and `GetTablePipeOffsets`/`GetTableCells`/`GetTableAlignments` (escape-aware `\|` splitting and the delimiter row's colon alignments — pipe offsets are shared with `MarkdownLineColorizer`'s pipe dimming so the two can't disagree).
    - **List markers** — `TryGetBulletListMarker`/`TryGetNumberedListMarker` are line-start-only with optional nesting indent, deliberately stricter than `Markdown.xshd`'s unanchored ListMarker rules since replacing a mid-sentence `"a - b"` dash or `"version 1. note"` with list rendering would corrupt prose.
    - **Inline spans** — `FindEmphasisSpans` (bold/italic/bold+italic/strikethrough/highlight/superscript/subscript/inline-code runs on a line, as `EmphasisSpan { Start, End, MarkerLength }`), `FindUnderlineSpans` (`<u>…</u>`, as `UnderlineSpan { Start, ContentStart, ContentEnd, End }` — its own scan, since it's HTML rather than an emphasis marker), and `FindScriptSpans` (just the superscript/subscript runs, as the `ScriptSpan { ContentStart, ContentEnd, IsSuperscript }` the colorizer needs — same scan, filtered by `EmphasisKind`) and `FindLinkSpans` (links/images, as `LinkSpan { Start, TextStart, TextEnd, End }` — see the `LinkMarkerElementGenerator` bullet below).
    - *Emphasis lexer* — `FindEmphasisSpans` mirrors `Markdown.xshd`'s exact patterns and precedence (bold+italic before bold before italic; character-class exclusion instead of wildcard quantifiers, to avoid catastrophic backtracking — same reasoning as the XSHD comments) via a tiny `\G`-anchored, non-overlapping single-pass lexer, so the two never drift apart. Inline code's content is never recursed into — it's literal per CommonMark's code-over-emphasis precedence, which the lexer's leftmost-wins scan also provides at the top level, same as AvalonEdit's earliest-match rule resolution.
    - *Mixed-delimiter nesting* — the lexer recurses one level into each match's inner content to find a nested run of the *opposite* delimiter (e.g. `_**bold**_`, `**_italic_**` — CommonMark forbids nesting the same delimiter inside itself, so this is the standard way authors combine bold+italic as two runs instead of `***text***`). This falls out for free with no extra filtering, since a match's content can never contain its own delimiter (excluded by the pattern's own content class), so re-scanning that content with the same pattern list can only ever find an other-delimiter run; the same mechanism covers strikethrough wrapping/wrapped-by emphasis (`~~**text**~~`, `**~~text~~**`).
    - *Mutual skip-awareness* — `FindEmphasisSpans` and `FindLinkSpans` each try the other's pattern table first at every scan position (without recording a match, just to advance past it), mirroring how `Markdown.xshd`'s Link rule is a flat `<Rule>` with no nested `RuleSet` (unlike Bold/Italic's `<Span>`): `[**bold**](url)` is one opaque link with no separately-colored nested Bold, and `**[link](url)**` is one opaque Bold run with no separately-colored nested Link, in both the real syntax highlighter and here. Both scanners also skip a leading bullet-list marker before scanning (`LeadingBulletMarkerLength`) — mirroring the XSHD's rule order, where ListMarker precedes every emphasis/link rule, so on `* item*` the leading `* ` is a list marker rather than the opener of an italic run swallowing the whole line.
    - *Document-wide exception* — `TryGetEnclosingFenceBlock` is the one method here that isn't purely line-local: fence pairing (which same-kind `` ``` ``/`~~~` line closes which) is a document-wide parity property, so it walks from the start of the document. Callers check the O(1) `IsFenceDelimiterLine` first so this cost is only paid for actual fence lines, not the majority of lines in a document.
  - **`HeadingMarkerElementGenerator.cs`** — an AvalonEdit `VisualLineElementGenerator` (registered on `Editor.TextArea.TextView.ElementGenerators`) that hides a heading's `"# "` marker text using a zero-size `InlineObjectElement`, on every line except the one the caret is currently on (**per-line** reveal — a heading marker only ever exists at a line's start, so line-granularity is sufficient). The marker characters still occupy their document offsets (selection/undo/the saved file are unaffected) — only the visual rendering collapses them to nothing.
  - **`EmphasisMarkerElementGenerator.cs`** — same zero-size-`InlineObjectElement` hiding technique, but **per-span** reveal instead of per-line: several bold/italic runs can share one line, so only the specific run the caret is inside (inclusive of both edges, so landing exactly on a boundary doesn't flicker) stays visible; hiding every marker on the line just because the caret is elsewhere on it would be distracting mid-sentence. This was the template for `LinkMarkerElementGenerator`.
  - **`BlockquoteMarkerElementGenerator.cs`** — same per-line reveal convention as `HeadingMarkerElementGenerator` (only the caret's own line shows its `` `>` `` marker, even for a multi-line blockquote — deliberately *not* the fence pair's per-block reveal, since a blockquote marker's meaning and `MarkdownLineColorizer`'s italic styling are entirely local to its own line), but the **replacement isn't zero-width** like every other marker generator: the hidden marker is replaced with a blank horizontal spacer sized `depth × IndentPerLevel` (`LeadingIndent`/`LeadingGap`/`BarWidth`/`TrailingGap`/`IndentPerLevel` are `internal const`s on this class — the knobs to tweak if the indent/bar sizing needs adjusting; `LeadingIndent` is a one-time shift of the whole construct, tuned by eye so the level-1 bar lines up with the list generators' "•" glyphs), reserving room for the accent bar(s) `BlockquoteAccentBarRenderer` draws separately. This class only reserves space; it does not draw anything itself (`Height = 0` on the spacer, same zero-visual-height idiom the other generators use for a plain hide). This split reserve-space/draw-separately approach is blockquote-specific, not a general template — no other construct uses it.
  - **`BlockquoteAccentBarRenderer.cs`** — an AvalonEdit `IBackgroundRenderer` (registered on `Editor.TextArea.TextView.BackgroundRenderers`, not `ElementGenerators`) that draws the actual accent bar(s) as one continuous vertical line per nesting level, spanning every consecutive run of blockquote lines currently visible — not one short bar per document line. This split (reserve indent space in the element generator, draw the bar separately here) exists because an `InlineObjectElement` is confined to its own line's content flow: the vertical gap between lines (line spacing/leading) belongs to `TextView`'s own layout, not to any single line's content, so no per-line element, however tall, can ever make adjacent bars touch — confirmed by checking `TextView.cs`, which measures inline embedded objects with an *infinite* constraint (`Element.Measure(new Size(double.PositiveInfinity, double.PositiveInfinity))`) rather than the line's actual height. A background renderer instead draws directly in the `TextView`'s shared pixel space (`Draw(TextView, DrawingContext)`, layer `KnownLayer.Background`), using `TextView.VisualLines` (the currently-visible `VisualLine`s) plus `VisualTop`/`Height`/`VerticalOffset`/`HorizontalOffset` to convert document-relative positions into on-screen coordinates, so it can draw a single rectangle from the top of the first line in a run to the bottom of the last with no gap. It processes one nesting level at a time (`for level in 1..maxDepth`, each its own contiguous-run scan) rather than all levels in one pass, so a depth transition mid-blockquote (e.g. `"> a"` followed by `">> b"`) still renders level 1's bar as continuous through the transition while level 2's bar only covers the deeper sub-run. Reads the same `LeadingIndent`/`LeadingGap`/`BarWidth`/`IndentPerLevel` constants from `BlockquoteMarkerElementGenerator` so the drawn bar always lines up with the space reserved there.
  - **`TaskListMarkerElementGenerator.cs`** — bullet-list variant for `- [ ]`/`- [x]`, replacing bullet and box together with a single drawn checkbox at the shared `IndentPerLevel` depth. Never mutates the document; toggling is `MarkdownFormatter.TaskListItem`'s job.
  - **`BulletListMarkerElementGenerator.cs` / `NumberedListMarkerElementGenerator.cs`** — per-line reveal like `HeadingMarkerElementGenerator`, but the third replacement variant after zero-size hide and blank spacer: a **visible rendered element** (an `InlineObjectElement` hosting a `TextBlock` styled from `CurrentContext.GlobalTextRunProperties` — editor typeface/size/foreground, so it follows theme and font with no `ApplyTheme` wiring). Bullets replace the single `-`/`*`/`+` marker character with a "•" glyph — a plain hide was deliberately rejected: unlike a heading's `# `, the bullet marker *is* the construct's visual, so collapsing it would leave list items indistinguishable from plain text. Numbered markers replace their digits+`.` range with the **exact same text** — `1. ` already renders identically to its source form, so the element exists only to carry the indent. Both set `Margin` left to `BlockquoteMarkerElementGenerator.IndentPerLevel` (referenced, not duplicated) so list items sit at the same pixel depth as blockquote content. The following space and any leading nesting indent remain real rendered text (nested items get the source whitespace's natural width on top of the fixed indent, not a quantized per-level depth).
  - **`CodeBlockFenceElementGenerator.cs`** — same zero-size-`InlineObjectElement` technique again, but on the **whole line** (a fence line like `` ```csharp `` has no separate "marker prefix" vs. "content" the way a heading does — the entire line *is* the marker) and with **per-block** reveal: both the opening and closing fence of a code block stay visible whenever the caret is anywhere inside that block (on either fence line or any content line between), not just when the caret is literally on a fence line — otherwise the fences would flicker away while simply typing code in the middle of the block. This is the first live-preview construct where what's hidden and what triggers a redraw aren't confined to the caret's own line, since a fence pair can be many lines apart; see the `MainWindow.OnCaretPositionChanged`/`RedrawEnclosingFenceLines` note above.
  - **`EmojiCatalog.cs`** — shortcode→emoji lookup, loaded once (lazily) from the embedded `Resources/Emoji.txt`. Missing resource yields an empty catalogue rather than throwing, so a packaging slip degrades to "no emoji" instead of taking the editor down; `MarkdownSyntaxEmojiTests` asserts a non-trivial entry count so that degradation can't pass silently.
  - **`EmojiElementGenerator.cs`** — per-span reveal with a *visible* replacement (the emoji character), the first generator to combine those. Replaces the whole `:joy:` run rather than hiding markers around content — unlike emphasis, there's no inner text to keep.
  - **`UnderlineMarkerElementGenerator.cs`** — `LinkMarkerElementGenerator`'s two-independently-sized-regions approach applied to `<u>`/`</u>`, with the same per-span reveal. Hides the tags only; the underline itself comes from the XSHD's `Underline` color, so this class needs no theme wiring.
  - **`LinkMarkerElementGenerator.cs`** — `EmphasisMarkerElementGenerator`'s per-span reveal convention applied to links/images, but with an **asymmetric** hidden region instead of a symmetric marker: `[` (or `![`) as the prefix and `](url)`/`][ref]` as the suffix, since the URL/reference portion has no fixed width the way `**`/`_` do — so this constructs two independently-sized `InlineObjectElement`s per link (`LinkSpan.TextStart - Start` and `LinkSpan.End - TextEnd`) rather than reusing one `MarkerLength` at both ends.
  - **`HorizontalRuleElementGenerator.cs`** — per-**line** reveal like `HeadingMarkerElementGenerator`/`BlockquoteMarkerElementGenerator` (caret elsewhere hides the line, caret on the line reveals the raw `---`/`* * *` text), but the hidden range is the **whole line** — a horizontal rule has no separate marker-prefix-vs-content split, so this reuses the fence idiom (`CodeBlockFenceElementGenerator`'s whole-line zero-size hide) rather than the heading/blockquote partial-prefix one. The drawn rule itself lives in `HorizontalRuleRenderer`, not here — a rule has no content of its own to size a rendered element from (unlike a bullet's "•" or a table's measured columns), so it has to span whatever width is actually on screen, which only a background renderer answers. `IsRendered` is the single shared gate both classes call, so the hidden text and the drawn line can never disagree about which lines are currently rendered.
  - **`HorizontalRuleRenderer.cs`** — draws the rule as a single horizontal line across every visible line `HorizontalRuleElementGenerator` is hiding, using `MarkdownLineColorizer`'s `LightHRuleBrush`/`DarkHRuleBrush` (made `internal` for this reuse) so the drawn line and the raw text revealed under the caret read as the same color. Unlike `BlockquoteAccentBarRenderer` and `TableGridRenderer`, this one is deliberately **pinned to the viewport rather than tracking `HorizontalOffset`**: a rule has no document-relative anchor worth preserving under horizontal scroll (it represents "the whole row"), so it always fills whatever is currently on screen instead of appearing to scroll away when the user scrolls right to read a long line elsewhere.
  - **`TableRowElementGenerator.cs`** — per-**block** reveal like the code fences (caret anywhere in the table reveals the whole thing as raw source, so editing always happens on raw text and column widths never shift under the caret), with whole-line **visible** replacement: each header/body row line becomes a run of fixed-width `TextBlock` cells (header bold, delimiter-row colons honored as `TextAlignment`), and the delimiter row is hidden whole via the fence idiom — its blank band, bordered top and bottom by the renderer, reads as the separator zone under the header. Column widths are a whole-table property (the reason tables never fit the per-line/per-span shapes): the widest cell per column, measured via `FormattedText` with the editor's own typeface — exact, because cells render their raw text verbatim — computed once per table into a `TableLayout` and cached; **any** document change clears the whole cache (`ReferenceEquals` on `TextDocument.Version`) rather than tracking which table a change touched, so a stale width can't survive an edit — and a **font change** (the WYSIWYG document-font flip) also clears it, detected by comparing the captured typeface/em-size, since the version key can't see a font swap that changes every measured width without touching the document. The text properties needed for measurement are captured on every `GetFirstInterestedOffset` call because `TableGridRenderer.Draw` can reach `ComputeLayout` outside any construction context. `ColumnCount` is the max cell count across *all* rows, not the delimiter's count — a body row with extra cells gets extra columns, because **rendering must never hide cell content**. `TryGetRenderedTable` is the single shared is-it-rendered/what-size gate for both this class and the renderer. Rows carry a left `Margin` of `BlockquoteMarkerElementGenerator.IndentPerLevel` (referenced, not duplicated — the list-generator convention), and `TableGridRenderer` offsets its `x0` by the same constant, so the grid sits at the same pixel depth as bullets and blockquote content with the drawn lines exactly under the cells.
  - **`TableGridRenderer.cs`** — the `IBackgroundRenderer` half of the table rendering: header shading, a horizontal line at every row-band edge, and vertical column lines drawn as continuous strokes across the table's visible lines — the same generator/renderer split as blockquotes, for the same reason (per-line elements can't make lines touch across the inter-line space `TextView` owns). Unlike `BlockquoteAccentBarRenderer` (which shares only layout *constants*), this one holds a reference to the `TableRowElementGenerator` instance and asks `TryGetRenderedTable` per visible line, so the reveal decision and the column geometry can never diverge between the drawn grid and the row elements — including drawing nothing over a revealed (raw) table.
- **`Resources/Markdown.xshd`** — AvalonEdit XSHD grammar for *inline* Markdown highlighting (bold/italic/strikethrough/highlight/inline code/links/images/fenced code blocks/HTML comments/list markers). Embedded as a resource (see `.csproj`) and loaded at runtime via `Assembly.GetManifestResourceStream("MDEdit.Resources.Markdown.xshd")` in `LoadSyntaxHighlighting()`. Comments in the file note deliberate regex constraints (e.g. "no wildcard quantifiers", "min 2 chars") — these were tuned to avoid catastrophic backtracking / crashes in AvalonEdit's regex engine, so preserve that style when editing rules (see commit "Fix syntax highlighting crashes and rearchitect line-level highlighting").
  - Bold and Italic are `<Span>` elements (not flat `<Rule>`s) specifically so a nested nested `<Rule>` inside each can recognize the *opposite* delimiter family wrapped inside it (`**_text_**`, `_**text**_`) and color it `BoldItalic` explicitly (not `Italic`/`Bold` alone — that would risk the nested match's color overriding, rather than combining with, the outer span's weight/style). Flat same-family nesting (`**text**` inside `**text**`) is still unsupported and out of scope — CommonMark itself requires mixing delimiter families to nest emphasis unambiguously, so this covers the real cases. `MarkdownXshdTests.MarkdownXshd_LoadsWithoutError` in `MDEdit.Tests` loads this file through AvalonEdit's real `HighlightingLoader` (not just a build-time XML check) so a malformed grammar fails `dotnet test` rather than only surfacing when a `.md` file is opened.
  - Bold/Italic/emphasis matching is single-line only — `<Rule>` elements (and the content-class patterns above) cannot cross line breaks; only `<Span>` supports `multiline="true"` (used for fenced code blocks/HTML comments). Making bold/italic span multiple lines would need converting them to multiline Spans and making `MarkdownLineColorizer`/the marker-hiding generators aware of spans that start on one line and end on another (they're currently strictly per-`DocumentLine`) — a materially bigger change than the mixed-nesting fix above, not yet done.
  - Highlighting is swapped based on file extension in `UpdateHighlighting(path)`: `.md`/`.markdown` get the Markdown XSHD, anything else (including `.txt`) gets no highlighting, per Requirements.md §4.
- **`Resources/AppIcon.ico` / `AppIcon.png`** — both are `<Resource>` items (WPF pack-URI-resolvable, distinct from the `EmbeddedResource` used for the XSHD grammar). The `.ico` (multi-res, generated from the `.png`) drives `<ApplicationIcon>` in the csproj and `MainWindow`'s titlebar icon; the `.png` is used only in `AboutWindow` for the reason noted above.
- **`MDEdit.csproj`** build-time targets worth knowing about beyond the Authenticode one above: `SetVersionFromGit` sets `<Version>` using the same scheme the ClickOnce publish script uses — `Major.Minor.Build` read from `build/published-version.txt`, Revision from the git commit count (so the About dialog's version matches the deployed ClickOnce version; see Version numbering above). Both halves fall back to the SDK default rather than failing the build when git or the file is unavailable. Also a plain `<AssemblyMetadata Include="BuildDate">` item stamps the current UTC time into the assembly on every build — needed because deterministic builds (the SDK default) zero out the PE header timestamp that used to serve this purpose. `ClearStaleReleaseNotesReadOnly` exists purely to unblock local rebuilds: running the app from a build folder marks its copy of `ReleaseNotes.md` read-only (`MainWindow.EnsureReleaseNotesAreReadOnly`), and the next build's content-copy step can't overwrite that, failing with `MSB3021`. It runs `attrib -R` on `$(OutDir)samples\*.md` — not the `Attrib` MSBuild task, which isn't registered in the .NET SDK's default task set — and is deliberately hung on `BeforeTargets="_CopyOutOfDateSourceItemsToOutputDirectory"`, the specific target that performs this copy (confirmed with `dotnet build -v:n`), because neither `BeforeTargets="Build"` nor `"CopyFilesToOutputDirectory"` actually run early enough: `Build` has no tasks of its own, so a hook on it fires only after its whole dependency chain — including the real copy — has already completed. A real ClickOnce install never hits this in the first place, since every published version lands in a brand-new folder with no read-only baggage carried over from a previous run.

### Live-preview constructs

Each construct's generator makes two independent choices: **reveal scope** (how much of the document has to contain the caret before the raw syntax comes back) and **replacement** (what gets rendered where the hidden characters were). In every case the characters still occupy their document offsets — selection, undo, and the saved file are unaffected; only rendering changes.

| Construct | Generator | Reveal scope | Replacement |
| --- | --- | --- | --- |
| Heading | `HeadingMarkerElementGenerator` | per-line | zero-size hide (`"# "` prefix) |
| Emphasis, highlight | `EmphasisMarkerElementGenerator` | per-span | zero-size hide (symmetric marker) |
| Link / image | `LinkMarkerElementGenerator` | per-span | zero-size hide (asymmetric prefix + suffix) |
| Underline | `UnderlineMarkerElementGenerator` | per-span | zero-size hide (asymmetric `<u>` + `</u>`) |
| Emoji | `EmojiElementGenerator` | per-span | visible rendered element (the emoji character) |
| Code fence | `CodeBlockFenceElementGenerator` | per-block | zero-size hide (whole line) |
| Blockquote | `BlockquoteMarkerElementGenerator` | per-line | blank spacer, bar drawn by `BlockquoteAccentBarRenderer` |
| Bullet list | `BulletListMarkerElementGenerator` | per-line | visible rendered element ("•" glyph) |
| Task list | `TaskListMarkerElementGenerator` | per-line | visible **drawn** element (a checkbox, replacing bullet *and* box) |
| Numbered list | `NumberedListMarkerElementGenerator` | per-line | visible rendered element (same `"1. "` text, for indent only) |
| Table | `TableRowElementGenerator` | per-block | visible rendered element (whole line → fixed-width cells; delimiter row hidden; grid drawn by `TableGridRenderer`) |
| Horizontal rule | `HorizontalRuleElementGenerator` | per-line | whole-line zero-size hide; line drawn by `HorizontalRuleRenderer` |

Reveal scope drives the redraw work in `MainWindow.OnCaretPositionChanged`: per-line and per-span need only the old and new caret line redrawn (span-grained constructs additionally need `_lastCaretOffset`, not just `_lastCaretLine`, since a caret move within one line can cross a span boundary), while per-block is the one scope whose reveal region can sit far outside those two lines — hence `RedrawEnclosingFenceLines` and `RedrawEnclosingTableLines`.

**Adding another construct** — the established order of work:

1. Add detection to `Editing/MarkdownSyntax.cs` first, and unit-test it there (see the test-file table above). Never re-implement detection inside a generator or the colorizer.
2. Pick a reveal scope and replacement from the table above, matching an existing construct wherever the new one behaves the same way.
3. Write the generator in `Editing/` as a `VisualLineElementGenerator` with an `Enabled` flag and caret state, modeled on the closest existing one.
4. Register it on `Editor.TextArea.TextView.ElementGenerators` in `MainWindow`.
5. Flip its `Enabled` in `UpdateLivePreviewState()`.
6. Re-sync its caret state in `ResetLivePreviewCaretTracking()` — otherwise it renders against a stale caret after New/Open.
7. Update `OnCaretPositionChanged` only if the scope isn't line-local; a per-block construct needs its own enclosing-region redraw the way fences do.
8. If the construct also needs color/weight/size (not just marker hiding), that half belongs in `MarkdownLineColorizer`, consuming the same `MarkdownSyntax` method.

**The extended-syntax constructs** — how each maps onto the shapes above, covering both the ones already done and the ones still planned (see §Project). All of them fit, except one:

- **Highlight is done** (`==text==`) and confirmed the prediction: adding `(new Regex(@"\G={2}[^=\n]+={2}"), 2, true)` to `EmphasisPatterns` gave it per-span marker hiding through the existing `EmphasisMarkerElementGenerator` for free, and a `Highlight` color + rule in `Markdown.xshd` (plus a `DarkHighlightColors` entry) gave it the background. No new generator, no `MainWindow` caret/redraw wiring. **Prefer this route for any remaining symmetric inline marker** — a new generator is the wrong instinct there.
- **Superscript and subscript are done** (`X^2^`, `H~2~O`) and took the same free ride plus one addition: they needed the colorizer to style a *span* rather than a whole line, which it had never done. That required telling runs apart, and `MarkerLength` can't — `^`/`~` are one character, exactly like italic's `_`. Hence `EmphasisKind` on the pattern table and `FindScriptSpans`, which **shares `FindEmphasisSpans`' single scan** (both project from `ScanLine`) rather than re-parsing, so the baseline styling and the marker hiding can never disagree. The `~` vs `~~` collision is handled purely by pattern order — subscript sits *below* strikethrough in `EmphasisPatterns`, and moving it would silently break strikethrough, so `MarkdownSyntaxScriptTests` pins that.
- **Task lists are done**, as predicted a variant of the bullet-list generator — per-line reveal, visible rendered element. Three things about it that aren't obvious:
  - `TryGetTaskListMarker` bounds the bullet character *through* the closing `]` (all five characters of `- [ ]`), and the generator replaces that whole range with **one** checkbox glyph. `BulletListMarkerElementGenerator` therefore has to check for a task and return −1, otherwise a task line renders "• ☐ todo" — two markers for one construct. A task line genuinely *is* a bullet line, so the exclusion belongs in the generator, not in `TryGetBulletListMarker`.
  - **The checkbox is drawn (a `Border` plus a `Polyline` tick), not a glyph — don't "simplify" it back.** U+2610/U+2611 (☐/☑) were the first attempt and looked wrong in practice: the editor font carries neither, so WPF font fallback resolved each character independently and the two states came out visibly different sizes. Drawing makes both states identical by construction, removes the dependency on any font happening to have the glyphs, and still scales with `FontRenderingEmSize` and follows the theme's foreground brush. This is the only generator that draws shapes rather than hosting text; the reason is glyph availability, not preference.
  - The command is the first three-way one: `MarkdownFormatter.TaskListItem` toggles an existing task, adds `[ ] ` to a plain bullet (inserting the full prefix would give `- [ ] - foo`), and otherwise inserts `- [ ] `. Being a document mutation it lives in `MarkdownFormatter`, not in the generator.
- **Emoji is done** and was the first generator to pair *per-span* reveal with a *visible* replacement (`EmojiElementGenerator`) — the other visible-replacement generators are all per-line. Two things settled along the way that are easy to re-litigate by accident:
  - **The catalogue is what makes detection safe.** The BCL has no shortcode table, so one ships as an embedded `Resources/Emoji.txt` (curated ~240 entries, not the full ~1,800 — everything here is versioned in git and carried in the ClickOnce payload; extending it is a data edit, and no code depends on the size). Because only catalogued names count, `10:30:45` and `3:4:5` can never be mistaken for emoji — a stronger guarantee than the pattern-only constructs get, so **don't "simplify" this into a bare regex**.
  - **Emoji render monochrome, not in colour**, verified in this app: WPF's text stack has no COLR/CPAL colour-font support. That is a platform limit, not a bug to keep re-investigating; colour would need an image-based rendering route entirely. It's documented in Requirements.md §5 so users aren't surprised.
  - `FindEmojiSpans` skips only inline code (a shortcode in backticks is literal); it deliberately does *not* skip emphasis or links, so `**:joy:**` still renders — same container reasoning as `FindUnderlineSpans`. `InlineCodePattern` is shared with `EmphasisPatterns` rather than duplicated, and **must stay declared above it**: static fields initialize in declaration order, so moving it below leaves the emphasis table holding a null regex at runtime, not merely a warning.
- **The two planned emoji follow-ons (§3)** are both about the catalogue rather than about rendering, and neither needs a new generator:
  - *Emoji picker* — a browsable/searchable list that inserts the **shortcode**, not the character, so picked emoji are indistinguishable from typed ones. `EmojiCatalog` currently exposes only `TryGet`/`Count`, so it needs a way to enumerate entries; keep the dictionary internal and hand out a projection rather than the live map. UI-wise this is the second owned dialog in the app — `AboutWindow` is the only precedent to follow.
  - *Convert emoji to shortcodes* — needs the **reverse** map, and that is not simply the catalogue inverted: aliases collide (`+1` and `thumbsup` both give 👍, `-1` and `thumbsdown` both 👎), so one shortcode per character has to win deterministically. First-listed-in-file is the natural rule, since `Emoji.txt` is hand-ordered with the preferred name first — decide it once in `EmojiCatalog` rather than at each call site. Note this is also the first feature here that *mutates* the document rather than detecting or rendering (everything in `Editing/` except `MarkdownFormatter` is read-only), so it belongs beside `MarkdownFormatter` and should apply as one batched change so a single Ctrl+Z undoes the whole conversion.
- **Underline is done, and is the odd one: it is not Markdown at all.** Markdown has no underline syntax in any dialect (underlining is reserved for links by convention), so Requirements.md §3 specs it as literal inline HTML — `<u>text</u>` — riding on Markdown's pass-through of inline HTML. It is the only formatting command that emits HTML. Its markers are **asymmetric** (`<u>` is 3 characters, `</u>` is 4), so `EmphasisSpan`'s symmetric `MarkerLength` can't describe it and the `EmphasisPatterns` free ride was unavailable: it needed `UnderlineSpan` (mirroring `LinkSpan`'s four offsets), `FindUnderlineSpans`, and `UnderlineMarkerElementGenerator` on `LinkMarkerElementGenerator`'s template, plus the full five-touchpoint MainWindow wiring. The underline *effect* is a one-line XSHD `<Color underline="true">` — `XshdColor.Underline` is supported, and `MarkdownXshdTests` proves the grammar still loads. Deliberately strict: lowercase `<u>` only, no attributes, no whitespace in the tag, and the content class stops at `<` so a nested tag ends the run — this editor does not parse HTML, and anything looser starts guessing.
  - Unlike the emphasis and link scanners, which skip past each other's matches, `FindUnderlineSpans` is **not** skip-aware and shouldn't be: underline is a *container*, not an opaque run, so `<u>**bold**</u>` is meant to keep its bold. Both scanners find their own runs independently, and their markers never share an offset, so the generators can't collide. Verified by tests in both directions.
- **Tables are done, and were the one construct that genuinely didn't fit the existing shapes** — a grid's column widths depend on every row, so the layout is a whole-table property rather than line- or span-local. The solution: `MarkdownSyntax` table detection, `TableRowElementGenerator` + `TableGridRenderer` (the blockquote generator/renderer split applied a second time — see their bullets above), and pipe/delimiter dimming in `MarkdownLineColorizer` reusing the hrule brushes. **Deliberately no XSHD rule**: XSHD matching is line-local and can't know whether a `|` line has a matching delimiter below it, so an XSHD table rule would color row-shaped prose — the same reason headings/blockquotes/hrules are colorizer-styled. Three v1 boundaries are deliberate, not oversights:
  - **Cell text renders verbatim** — inline markers inside a rendered cell stay visible, because the row element consumes the whole line and the inline generators never run there. That's also what makes the `FormattedText` width measurement *exact*. Nesting inline rendering into cells is the natural follow-up, and whoever does it must make measurement account for hidden markers, or columns will misalign.
  - **Reveal is whole-table.** Per-row Typora-style reveal was considered and deferred: with the rest of the table still rendered while one row is edited, every keystroke changes a column max-width and forces a whole-block redraw, and the raw row's text can't line up with the rendered columns anyway.
  - **A row wider than the viewport doesn't word-wrap** — a single inline object can't. The raw text is always reachable via the per-block reveal.
  - The insert-table *command* (§3) is done, independent of all of this — `MarkdownFormatter.Table` plus a Format-menu entry and a toolbar button (no keyboard shortcut, matching Link/Code Block/Code — none of the toolbar's insert commands have one), following the existing insert-and-position-caret convention: a 2-column, 3-body-row starter with "Header 1" selected for immediate typing, the same placeholder-selection idiom as `Link`'s "link text". One addition beyond that precedent: since `IsTableRowLine` requires each row to start at column 0, `Table` normalizes onto its own lines — a leading newline when the cursor isn't at the start of its line, a trailing one when it isn't at the end — so the table always renders correctly regardless of where the cursor was. `CodeBlock` has this same latent limitation and was deliberately left as-is; normalizing there too is out of scope here.

## Git workflow

- Before running `git commit` (and before `git push`), show the proposed commit message and wait for explicit confirmation — do not commit or push on the same turn as drafting the message without that check-in. Exception: once the user has given an explicit go-ahead (e.g. supplied the commit message themselves, or said "commit and push"), that covers the rest of that task, including any incidental fixes needed to actually complete it (e.g. a build error hit mid-publish) — don't stop to re-confirm those, just use a reasonable one-line message and proceed. Only a genuinely new/separate change needs fresh confirmation.
- Commit messages are one line only, unless the change is an extraordinary case that genuinely warrants a body.

## Conventions

- Nullable reference types are enabled; keep new code nullable-aware.
- File-scoped namespaces (`namespace MDEdit;`) are used throughout.
- Keep formatting-insertion behavior consistent with the "wrap selection / insert-and-position-caret" pattern already established for existing commands when adding new ones.
